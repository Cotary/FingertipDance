# 复刻 SOP · 可执行工具

> 配套文档：`../40-设计稿复刻可行性研究.md`
> 这里不是方案描述，是**能直接跑的工具**。

## 这套工具解决什么问题

一句话：**把"像不像设计稿"从肉眼判断，变成一条能自动判红的数字。**

设计稿复刻的返工，从来不是"AI 画得不像"，而是**没人知道差多少、差在哪**。
项目里踩过的三个 bug 全是这一类：

| 曾经的 bug | 肉眼能否发现 | 像素闸门能否发现 |
|---|---|---|
| 渐变线长度算短 45%，整盘系统性偏亮 | ❌ 看不出 | ✅ 分块 Δ 立刻超限 |
| 侧壁色被抽成全局常量，frost 蓝侧壁永远错 | ⚠️ 要并排比才看出 | ✅ 单元素 Δ 超限 |
| `dim` 半径多乘 0.5 | ❌ 完全看不出 | ✅ 分块 Δ 超限 |

## 四个脚本

```
baseline.mjs --build      从设计稿建基线（真值图库 + computed style 快照）
bake.mjs --ninepatch      烘焙贴图 + 九宫格切片参数
verify.mjs                烘焙图回画后与真值比对（验证整条链路）
selftest.mjs              闸门自标定（注入已知偏差，验证闸门不瞎）
```

### 1. 建基线

```bash
node baseline.mjs --build
```

产出 `baseline/`：
- `<id>.png` —— 元素真值图（DPR 3，含阴影外扩）
- `<id>.style.json` —— 该元素的 computed style（`background`/`box-shadow`/`border-radius`/`innerHTML`）
- `manifest.json` —— 清单与截图坐标

**为什么同时存 style**：出错时要能回答"为什么设计稿是这样"。只看图看不出是哪个 CSS 属性。

**自动跳过无限动画元素**：`.pc.hint`、`.pc.hintcell` 都是 1.8s 呼吸，`box-shadow` 逐帧变，截图尺寸不稳定（实测 426 vs 420）。这类归动效验收，工具会自动检测 `animation-iteration-count: infinite` 并跳过。

### 2. 烘焙

```bash
node bake.mjs --ninepatch
```

产出 `baked/`：`<id>.png` + `baked.manifest.json`（含逻辑尺寸、外扩量、九宫格切片）。

**关键实现决策**：
- **烘焙倍率 = 运行时倍率 = 3**，不做超采样。实测超采样会把 1px 描边糊掉（图标分块 Δ 8.9 vs 原生 0）。
- **外扩量用共享的 `calcPad()`**，与 baseline 严格一致。曾经两边各写一份，导致 28 个元素全部报"尺寸不符"。
- **九宫格切片只覆盖圆角本身**，不把阴影外扩算进去。

### 3. 回画验证

```bash
node verify.mjs
```

把烘焙贴图按逻辑尺寸画回 canvas，与真值比对。**这一步验证的是"截图→存储→绘制"整条链路**，中间任何一环错（尺寸算错、乘了两次 dpr、平滑设置错）都会在这里暴露。

当前状态：**26/26 全部 Δ = 0（无损）**。

### 4. 闸门自标定

```bash
node selftest.mjs
```

**一个没标定过的检测器，它的"通过"毫无价值。** 这个脚本向基线图注入已知偏差，检查闸门是否按预期判红：

| 用例 | 注入 | 期望 | 实测 |
|---|---|---|---|
| identity | 无 | 通过 | ✅ Δ=0 通过 |
| bright2 | 整体 +2 | 通过（阈值下沿） | ✅ mean 1.73 通过 |
| bright5 | 整体 +5 | 拒绝 | ✅ mean 4.33 拒绝 |
| **corner** | 角落 1% 偏 +30 | 拒绝 | ✅ 分块 16.04 拒绝 |
| hueShift | 整体偏色（模拟用近似色） | 拒绝 | ✅ mean 7.0 拒绝 |
| wrongSize | 尺寸不符 | 拒绝 | ✅ 拒绝 |

**corner 这个用例抓出了闸门的真实盲区**：最初只看"全图均值 + 差>8 占比"，
这个用例是 mean 0.25 / pct8 0.96%，**全绿通过**——但人眼一眼能看出。
加了 8×8 分块检测才堵住。这就是为什么闸门必须被标定。

## 两个必须知道的坑（都实际踩过）

### 坑 1：`omitBackground` 不会让父容器透明

`screenshot({ omitBackground: true })` 只让**页面根节点**透明，父容器的
background 仍然会被截进去。而外扩区（装阴影用的 30-50px）整个落在父容器里，
于是贴图里带住了父容器的卡面和相邻文字。

实测后果：`tile.pale` 的贴图里是一整张「未铺·天青釉」状态卡，不是棋子。

**修法**：`withIsolatedElement()` —— 截图前把元素临时剪到 `position:fixed`
干净容器，其余节点 `visibility:hidden`，根节点背景清空；截完放回原位。
**baseline 与 bake 必须共用这一个实现**（各写一份就可能各错一次、且错得一样）。

### 坑 2：自比对全绿 ≠ 正确

上面那个 bug 之所以没被发现，是因为 baseline 和 bake **犯了同一个错**：
两边都截了同一张卡，逐像素比对 Δ=0，闸门全绿。

**闸门只能证明"两边一样"，不能证明"两边都对"。**

所以：
- 第一次建库必须**人眼复核**几张贴图（不能只看数字）
- 元素边界要由 S0 的资产清单确定，不能只依赖 CSS 选择器碰运气
- `verify.mjs` 的 Δ=0 只保证"转格式无损"，不保证"截对了东西"

## 判据与阈值

| 指标 | 阈值 | 为什么 |
|---|---|---|
| `mean` 均值 Δ | ≤ 2 | 浏览器自己重渲染两次的固有差异约 0.5-1，留一倍余量 |
| `pct8` 差>8 占比 | ≤ 2% | 允许抗锯齿边缘，不允许整片偏 |
| `block` 最差分块 | ≤ 4 | 堵住"局部改坏但全局均值被摊薄"的盲区 |
| `max` | 不参与判定 | 抗锯齿处单点差异能到 40+，用它会永远失败 |

## 完整流程

```bash
# 首次 / 设计稿更新后
node baseline.mjs --build
node bake.mjs --ninepatch
node verify.mjs          # 应全绿
node selftest.mjs        # 应全绿

# 日常：每次改完渲染代码
node baseline.mjs --check --shots <游戏截图目录>
```

`--check` 会输出 `report/pixel-gate.md`，失败项给出**具体坐标和 RGB 差值**：

```
| 坐标 | 设计稿 rgba | 我们 rgba | Δ |
| (37,52) | rgba(213,227,216,255) | rgba(198,215,203,255) | 24.1 |
```

拿这个坐标去对照 `baseline/<id>.style.json`，通常能直接定位是哪条 CSS 没抄对。

## 环境依赖

Playwright 通过 `PLAYWRIGHT_PATH` 环境变量指定（默认指向本机 npx 缓存）。
本项目的游戏本体不依赖它——它只是设计期工具。

## 游戏侧的两个验证台

这两个不比对像素，用来肉眼确认**画出来的语义对不对**（有些错，像素闸门抓不到）。

```
games/line/tools/design-replica/
  shoot.html + shoot.mjs    单格出图（按 baseline/manifest.json 的尺寸与 pad）
  trail-check.html + trail-shot.mjs   连线验证台：画真实一小盘 + 真实连线
```

### 连线验证台为什么必须有

像素闸门只能比单格。**连线的错不会体现在单格上**——比如"传送门把两格用一条弧线连起来"，
每一格都是对的，整条线的语义却是错的。这类问题只能看整图。

`trail-check.html` 直接调用生产的 `drawCoverPlate / Cells / Trail / Marks`，
不是另画一份（另画一份验的就不是真实效果）。它构造 5×5 盘，
两端传送门几何上隔着两格，**若线还画跨格弧线，一眼就能看出来**。

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:50003/   # 先确认 dev server
cd games/line/tools/design-replica && node trail-shot.mjs         # → trail-check.png
```

与之配套的**逻辑锁**在 `test/cover-visual.test.ts`：它用会记录 `lineTo` 坐标的桩，
断言"没有任何一条描边同时经过 A 和 B 的中心"，以及"线终止于 A、起始于 B"。
注入旧实现（画跨格线）时这条测试立刻判红 —— 已实测。

## 已知边界

| 项 | 说明 |
|---|---|
| 无限动画元素 | 不进静态基线，归动效验收（逐帧比对） |
| 3D 翻面 | Canvas2D 无法表达，需降级或用 WebGL 单画布 |
| 震动毫秒 | 微信只有 light/medium/heavy 三档，平台限制 |
| 字体 | 需做子集（735 个汉字），否则微信 4MB 首包装不下 |
