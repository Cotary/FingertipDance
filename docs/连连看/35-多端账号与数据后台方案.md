# 35 — 多端账号与数据后台方案

> 目标一句话：**一个 uid 一份数据，登录即到手；微信 / 抖音 / H5 共用一套库，后台按平台切片看同一份事实。**
>
> 本文是设计稿 + 施工顺序。**不改现有接口语义**，只做加法与迁移；所有 DDL 都必须可重复执行
> （`migrate.go` 每次启动都会把 `migrations/*.sql` 从头跑一遍，没有 schema_migrations 表）。

---

## 0. 现状体检（先看清已经有什么）

### 0.1 已经上后端的

| 数据 | 位置 | 评价 |
|---|---|---|
| 最高已通关 `max_level` | `users.max_level` | ✅ 权威，客户端 `currentLevel = max_level + 1` |
| 累计用时 / 步数 | `users.total_time_ms` / `total_steps` | ✅ 仅首次通关累加，防刷 |
| 每关最优记录 | `level_records(uid, mode, level_idx)` | ✅ 主键天然幂等，路径可回放复核 |
| 星级 | 由 `level_records` **派生**（`/api/progress/stars`） | ✅ 不落表是对的，改算法不用洗数据 |
| 已解锁皮肤 | `users.unlocked_skins` JSONB | ⚠️ 能用，但不可查询、不可审计、不可发来源 |
| 跳过限流 | `skips(uid, mode, level_idx, day)` | ✅ 服务端为准 |
| 埋点 | `events` | ⚠️ **没有平台维度**，见 §0.3 |
| 好友 / 总榜 | `friends` / Redis `rank:global` | ✅ 依赖 uid |

### 0.2 只在本机的（换台设备就没了）

| 数据 | 现状 | 后果 |
|---|---|---|
| 当前装备皮肤 `currentSkin` | `localStorage.progress` | 换机回到默认皮肤 |
| 当前装备主题 `currentTheme` | 同上 | 换机主题丢失，音色也跟着丢（音色 = 主题） |
| 广告解锁的主题 `unlockedThemes` | 同上 | **花钱看广告解锁的东西换机就没了**，这是客诉级问题 |
| 声音开关 `sound_off` | 独立 key | 换机重新开声音 |
| 广告观看次数 | `users.ad_watch_cnt` **有列但没有任何写路径** | 恒为 0（BUG，收益核算拿不到数） |
| 昵称 / 头像 | 表有列，登录请求从不带，也没有修改接口 | 恒为空 |
| 每日跳过预检 | `skip_{UTC日期}_{关号}` | 客户端用 UTC、服务端用本地时区（`time.Now().Format`），跨零点会打架 |

### 0.3 结构性的三个问题

1. **`users` 与 `openid` 是一对一。**
   `openid_hash` 是唯一键，登录只认「微信 + 单个 appid」。
   加抖音 = 加一批新用户；加 H5 = 再加一批。同一个人在三个端是三个 uid，
   进度、皮肤、好友全不通。**这是"一个后台看多端"最根本的阻碍，不是加个字段能解决的。**

2. **一半数据没有归属地。**
   装备、主题、声音只写 `localStorage`，服务端根本不知道。
   现在的 `progress.sync()` 是"整体覆盖"语义，客户端与服务器谁赢没有规则，
   所以才会有注释里那个「服务端少返一个字段 → 本地数组变 undefined → 渲染循环中断」的坑。

3. **`events` 没有 platform / app_id / app_version。**
   后台想按端看 DAU、留存、关卡漏斗，现在只能看一坨总数。

## 1. 三条铁律（先立规矩，再谈实现）

1. **账号是账号，身份是身份。**
   `users.id`（uid）是唯一主键；微信 openid / 抖音 openid / 手机号 / 游客设备号都只是
   `user_identities` 里的**一种登录方式**。一个 uid 可以有 N 个身份。

2. **登录是「绑定」，不是「注册」。**
   第一次进游戏就先给一个**游客账号**（有 uid、能存档）。
   之后无论微信登录、抖音登录还是手机号，都是把这个真实身份**绑到已有账号上**，
   不是新建一个。"先玩后登录"才不会掉进度。

3. **"上后端"的判据只有一条：换台设备还应不应该在？**
   - 应该在 → 上后端（进度、星级、皮肤、主题、装备、声音、昵称）
   - 只跟这台设备有关 → 留本地（地图滚动位置、关卡表缓存、埋点缓冲）
   - 能从别处推导 → 不落库（星级、里程碑主题、当前关号）

## 2. 身份模型

### 2.1 三层结构

```
users                 账号（uid）——所有业务数据的唯一归属
  └─ user_identities  登录身份（provider + app_id + open_id [+ union_id]）
  └─ user_devices???  不建表：设备号就是一条 provider='guest' 的身份
```

### 2.2 各端到底能拿到什么

| 端 | 客户端登录 API | 服务端换取 | 稳定标识 | unionid 条件 |
|---|---|---|---|---|
| 微信小游戏（现有） | `wx.login()` → `code` | `sns/jscode2session` | `openid`（按 appid 隔离） | 需绑定微信开放平台；**小游戏首次可能不返回** |
| 抖音小游戏 | `tt.login()` → `code` + `anonymousCode` | `POST /api/apps/v2/jscode2session` | `openid`；`anonymous_openid` 标识设备 | 同开发者多应用才一致，且需绑定 |
| 微信 H5 | 公众号网页授权 `snsapi_userinfo` | `sns/oauth2/access_token` | 公众号下的 `openid` | 需开放平台绑定 + 用户授权 |
| 抖音 H5 | 抖音开放平台网页授权 | `/oauth/access_token/` | `open_id` | 以官方文档为准 |
| 纯浏览器 H5 / 小程序 web-view | 无原生身份 | —— | 设备号（uuid） | 无 |

**三条硬事实，决定了方案不能只靠 unionid：**

- 微信**小游戏**第一次 `code2session` 经常**不返回 unionid**（要先关注/授权过同开放平台的公众号或小程序）。
  把它当必填 → 大量用户永远登不进同一个账号。
- 微信小游戏和公众号网页授权是**两个 appid**，openid 天然不同；没有 unionid 就是两个人。
- 抖音的 unionid 只在**同一开发者、同一宿主**下一致，跨抖音/抖音极速版都可能不同。

所以需要**三把钥匙**，按可靠性排序自动尝试，剩下的人工兜底。

### 2.3 三把钥匙

| 钥匙 | 覆盖面 | 成本 | 用途 |
|---|---|---|---|
| **unionid** | 同开放平台内自动打通 | 0（登录即得） | 自动识别"同一个人" |
| **手机号** | 跨生态唯一 | 短信费 + 频控 + 合规 | 微信 ↔ 抖音 ↔ H5 的最终桥梁 |
| **迁移码** | 100% 覆盖 | 0 | 没有 unionid、不愿给手机号时的兜底 |

迁移码：服务端生成 8 位（去掉 0/O/1/I），10 分钟有效、一次性；老设备"出示"，新设备"输入"。
这不是土办法，是**跨生态账号体系的标准兜底**（Steam / 主机游戏都在用）。

### 2.4 登录时序（游客优先，绑定升级）

```
冷启动
 ├─ ① 读本地快照 → 立刻渲染（不等网络）
 ├─ ② platform.login() → { provider, code?, anonymousCode?, deviceId }
 ├─ ③ POST /api/v2/auth/login
 │     ├─ 查 (provider, app_id, open_id)        → 命中即该账号
 │     ├─ 查 (provider='guest', device_id)      → 命中即该游客账号
 │     ├─ 有 unionid → 查 unionid 映射          → 命中即该账号（并考虑合并游客）
 │     └─ 都没有 → 新建游客账号（uid）
 ├─ ④ 响应直接带**全量快照**（进度/设置/解锁/星级）——不再多打一次接口
 └─ ⑤ 覆盖本地快照，进大厅；失败的写请求进 outbox
```

**关键点：第 ③ 步里，"抖音匿名身份"只能用一次。**
同一台手机，A 用户玩过游客局 → 绑定成 A 的账号；之后 B 用户在同一台手机登录，
不能再把这份游客进度并给 B。落库时给这条 guest 身份打 `claimed_at`，已认领的不再参与合并。

### 2.5 合号规则（必须有明确裁决表，否则一定出事故）

| 数据 | 裁决 | 理由 |
|---|---|---|
| `max_level` | 取 **max** | 进度只能前进 |
| `level_records` | 逐关取**更优**（undo 少 / steps 少 / time 少） | 等价于"两台设备各打了一半" |
| 星级 | 不单独合，随记录重算 | 派生数据不参与合并 |
| 已解锁皮肤/主题 | **并集** | 已获得的东西不能收回 |
| 设置（声音/装备） | 以 `updated_at` 更晚的为准（LWW） | 用户最后一次操作最可信 |
| `total_time_ms` / `total_steps` | 相加（同一关只算一次） | 统计口径，宁可略大 |
| `scores` 流水 | 保留两边，uid 改写到目标账号 | 只增不改的分析表 |
| `events` | **不迁移** | 迁了会重复计数；老 uid 留作历史 |
| 好友关系 | 并集，重复取 accepted | —— |
| 目标 uid 选择 | 进度高者优先；有支付后**必须**选有订单的账号 | 钱的归属优先于等级 |

- 被合并的 uid 写 `users.merged_into = 目标uid`，**不物理删除**；
  老分享链接、老 token 里的 uid 仍能解析到目标账号。
- 每次合并写 `account_merges` 审计行（谁并谁、原因、前后数据摘要）。
- 「两个都已绑定的真实账号」合并，默认返回 `4013` 让用户确认一次，
  不要静默合并 —— 这是唯一可能"把别人的号并进来"的路径。

```sql

CREATE TABLE IF NOT EXISTS user_identities (
  id            BIGSERIAL PRIMARY KEY,
  uid           BIGINT       NOT NULL,
  provider      VARCHAR(16)  NOT NULL,   -- guest | wechat | douyin | phone

  union_id      VARCHAR(128),            -- 可空，拿不到就是 NULL
  claimed_at    TIMESTAMP,               -- guest 身份被真实身份认领的时间（只能用一次）
  created_at    TIMESTAMP    NOT NULL,

);
CREATE INDEX IF NOT EXISTS idx_identities_uid ON user_identities (uid);
CREATE UNIQUE INDEX IF NOT EXISTS uk_identities_union
  ON user_identities (provider, union_id) WHERE union_id IS NOT NULL;

-- ── 2. users：兼容列降级 + 账号状态 ──

ALTER TABLE users ALTER COLUMN openid_hash DROP NOT NULL;
ALTER TABLE users DROP CONSTRAINT IF EXISTS users_openid_hash_key;
CREATE UNIQUE INDEX IF NOT EXISTS uk_users_openid_hash
  ON users (openid_hash) WHERE openid_hash IS NOT NULL;

ALTER TABLE users ADD COLUMN IF NOT EXISTS status         SMALLINT NOT NULL DEFAULT 0; -- 0正常 1注销中 2封禁
ALTER TABLE users ADD COLUMN IF NOT EXISTS token_version  INTEGER  NOT NULL DEFAULT 0;
ALTER TABLE users ADD COLUMN IF NOT EXISTS first_platform VARCHAR(16) NOT NULL DEFAULT 'unknown';
ALTER TABLE users ADD COLUMN IF NOT EXISTS merged_into    BIGINT;
ALTER TABLE users ADD COLUMN IF NOT EXISTS phone_enc      VARCHAR(256);
ALTER TABLE users ADD COLUMN IF NOT EXISTS phone_hash     CHAR(64);
CREATE UNIQUE INDEX IF NOT EXISTS uk_users_phone_hash
  ON users (phone_hash) WHERE phone_hash IS NOT NULL;

-- ── 3. 账号级偏好：KV 而不是加列 ──
-- 加一个开关就改表，迟早要 ALTER 到天亮；key 由服务端白名单约束。
CREATE TABLE IF NOT EXISTS user_settings (
  uid        BIGINT      NOT NULL,
  key        VARCHAR(32) NOT NULL,
  value      JSONB       NOT NULL,
  updated_at TIMESTAMP   NOT NULL,
  PRIMARY KEY (uid, key)
);

-- ── 4. 解锁表：带来源，可审计、可补发 ──
CREATE TABLE IF NOT EXISTS user_unlocks (
  uid        BIGINT      NOT NULL,
  kind       VARCHAR(8)  NOT NULL,   -- skin | theme
  item_id    VARCHAR(32) NOT NULL,
  source     VARCHAR(16) NOT NULL,   -- default | level | ad | event | legacy_claim | gift
  level_idx  INTEGER     NOT NULL DEFAULT 0,
  created_at TIMESTAMP   NOT NULL,
  PRIMARY KEY (uid, kind, item_id)
);

-- 历史皮肤从 JSONB 平滑搬过来（幂等）
INSERT INTO user_unlocks (uid, kind, item_id, source, created_at)
SELECT u.id, 'skin', s.value, 'level', now()
FROM users u, jsonb_array_elements_text(u.unlocked_skins) AS s(value)
ON CONFLICT DO NOTHING;

-- ── 5. 广告流水：ad_watch_cnt 的真相来源 ──
CREATE TABLE IF NOT EXISTS ad_events (
  id         BIGSERIAL PRIMARY KEY,
  uid        BIGINT      NOT NULL,
  platform   VARCHAR(16) NOT NULL,
  placement  VARCHAR(32) NOT NULL,   -- skip | hint | theme
  ad_type    VARCHAR(16) NOT NULL,   -- rewarded | interstitial | banner
  completed  BOOLEAN     NOT NULL,
  client_id  VARCHAR(64) NOT NULL,   -- 客户端幂等号
  created_at TIMESTAMP   NOT NULL,
  UNIQUE (uid, client_id)
);
CREATE INDEX IF NOT EXISTS idx_ad_events_uid_time ON ad_events (uid, created_at);

-- ── 6. 迁移码 ──
CREATE TABLE IF NOT EXISTS transfer_codes (
  code       CHAR(8) PRIMARY KEY,
  uid        BIGINT    NOT NULL,
  expires_at TIMESTAMP NOT NULL,
  used_at    TIMESTAMP,
  created_at TIMESTAMP NOT NULL
);

-- ── 7. 合号审计 ──
CREATE TABLE IF NOT EXISTS account_merges (
  id         BIGSERIAL PRIMARY KEY,
  from_uid   BIGINT      NOT NULL,
  to_uid     BIGINT      NOT NULL,
  reason     VARCHAR(32) NOT NULL,   -- unionid | phone | transfer_code | manual
  detail     JSONB       NOT NULL,
  created_at TIMESTAMP   NOT NULL
);
```

## 4. 接口设计

统一响应包装不变：`{ code, msg, data }`。v2 与 v1 并存，v1 不动。

### 4.1 `POST /api/v2/auth/login`

```jsonc
// 请求
{
  "provider": "wechat_minigame",   // wechat_minigame | douyin_minigame | wechat_h5 | douyin_h5 | guest
  "code": "一次性凭证",             // guest 时可空
  "anonymousCode": "抖音设备凭证",   // 可选
  "deviceId": "本机 uuid",          // guest / h5 必填
  "appId": "多 appid 时显式指定",    // 可选，默认取服务端配置
  "platform": "wx | dy | h5",       // 冗余维度，写会话与埋点
  "appVersion": "0.1.0"
}

// 响应 = 会话 + 全量快照（一次 RTT 拿完，冷启动只打这一个接口）
{
  "token": "...",
  "uid": 123,
  "isNew": false,
  "account":  { "nickname": "", "avatar": "", "createdAt": 1730000000 },
  "progress": { "maxLevel": 12, "totalTimeMs": 930000, "totalSteps": 340, "adWatchCnt": 3 },
  "settings": { "sound_on": true, "current_skin": "wood", "current_theme": "neon" },
  "unlocks":  { "skins": ["wood","mint"], "themes": ["neon"] },
  "stars":    { "1": 3, "2": 2, "3": 1 },   // 1000 关约 7KB，gzip 后 ~1KB
  "merged":   null,                          // 或 { "fromUid": 88, "reason": "unionid" }
  "serverTime": 1730000000000
}
```

服务端内部流程：

```
provider → IdentityProvider.Exchange(code)
  → { openID, unionID?, anonymousID? }
  → resolve(uid):
       1) identity(provider, app_id, open_id)
       2) guest identity(device_id)      [未被认领过]
       3) identity(provider, union_id)
       4) 新建账号（游客，first_platform = platform）
  → 若同时命中 2) 和 1)/3)，走合并（§2.5），写 account_merges
  → 更新 last_login_at / 写 user_active_daily
  → 签发 JWT（uid + platform + token_version）
  → 返回快照
```

### 4.2 `GET /api/v2/bootstrap`

回前台 / 切场景时对账用。字段与登录响应一致（无 token、无 isNew）。

### 4.3 写接口

| 接口 | 作用 | 幂等 / 冲突 |
|---|---|---|
| `PATCH /api/v2/settings` | 声音、装备皮肤、装备主题 | `updatedAt` LWW；服务端夹紧未来时间 |
| `PATCH /api/v2/profile` | 昵称、头像 | 昵称走内容安全，失败不落库 |
| `POST /api/v2/ad/complete` | 广告完播上报 | `clientId` 唯一；同事务累加 `ad_watch_cnt` |
| `POST /api/v2/claim/legacy` | 老客户端一次性上报本地主题 | 仅迁移窗口开放，写 `source='legacy_claim'` |
| `POST /api/v2/auth/transfer-code` | 生成迁移码 | 每 uid 每分钟 1 次 |
| `POST /api/v2/auth/redeem` | 用迁移码并号 | 一次性，成功后码作废 |
| `POST /api/v2/auth/bind` | 绑手机号（可选期） | 手机号哈希唯一 |

`PATCH /api/v2/settings` 的形状：

```jsonc
// 请求
{ "items": [
  { "key": "sound_on",      "value": false,       "updatedAt": 1730000000000 },
  { "key": "current_theme", "value": "abyss",     "updatedAt": 1730000000500 }
] }
// 响应
{ "applied": [ ... ], "rejected": [ { "key": "sound_on", "reason": "stale" } ] }
```

**为什么必须带 `updatedAt`**：A 设备关声音（10:00），B 设备开声音（10:05）在离线状态下，
网络恢复时如果谁后到谁赢，结果就是随机。LWW 至少是"用户最后一次操作生效"，可解释。

### 4.4 离线 outbox（弱网 / 飞行模式）

小游戏经常在地铁里玩。写请求失败不能丢，也不能重复：

```jsonc
// 本地队列，每条带 opId
{ "opId": "uuid", "type": "setting|progress|ad", "payload": {...}, "at": 1730000000000 }
```

- 进度上报本身已是幂等（`(uid, mode, level_idx)` 主键 + 保留更优）；
- 设置按 LWW，重放无害；
- 广告按 `clientId` 唯一，重放无害；
- 恢复网络 / 回前台 / 下次启动时按顺序重放，成功即出队；
- 队列上限 200 条，超了丢最旧的并记一条 `sync_dropped` 埋点（可观测）。

P2 再考虑合并成 `POST /api/v2/sync` 批量接口，P1 直接复用现有写接口即可。

### 4.5 新增错误码

| code | 含义 | 客户端动作 |
|---|---|---|
| 4010 | 身份冲突（该手机号/unionid 已绑定其他账号） | 弹「合并到哪个账号」 |
| 4011 | 需要绑定（游客账号触发受限功能） | 引导登录 |
| 4012 | 凭证无效 / 过期（code 只能用一次） | 重新 `login()` |
| 4013 | 合并需确认 | 二次确认弹层 |
| 4014 | 迁移码无效 / 已用 / 过期 | 提示重新生成 |
| 4015 | 账号已注销 / 封禁 | 展示状态页 |

### 4.6 兼容策略

- `/api/login`（v1）**保留**，内部转调新 resolve 流程，响应字段只增不减。
- JWT 只加 claim（`platform`），鉴权仍只看 `sub`，老 token 继续有效。
- `users.openid` 老数据不动；老用户首次走 v2 登录时，若 identity 未命中，
  用 `openid_hash` 回查，命中就**懒插入**一条 identity（provider=wechat，app_id 取配置），
  不需要一次性洗库脚本。

### 5.1 平台层

```
src/platform/
  types.ts     Platform 增加 provider / deviceId / anonymousCode
  index.ts     __TARGET__ 增加 'douyin' | 'h5'

```

- 抖音的 canvas / 存储 / 广告 API 与微信高度同构，适配层可以复制 `wechat.ts` 改前缀。
- **H5 不重写渲染层**；微信小程序如果必须上，用 `web-view` 套 H5，不为小程序重写 Canvas。
- `platform.name` 目前只有 `'web' | 'wechat'`，代码里所有比较都要过一遍（含广告、分享、震动）。

### 5.2 数据层

现在的 `ProgressStore` 是"本地结构 + 服务端整体覆盖"，建议演进成：

```
src/data/
  account.ts   AccountStore：单一状态（progress/settings/unlocks/stars）
  remote.ts    v2 接口
  outbox.ts    离线队列
  sync.ts      启动 / 回前台 / 网络恢复时的对账
```

规矩：

1. UI **不许**再直接 `storage.set`。所有修改走 `account.commit(patch)`：
   改内存 → 写缓存 → 入队。
2. 服务端快照用 `applySnapshot()` **整块替换**，不要在 UI 层做字段级 merge。
3. 保留 `progress.sync` 的 `undefined` 过滤逻辑（那是踩过的坑），但新代码不再用它。
4. 星级：本地只做"通关后单关 +1"，进大厅时用服务端快照校准。

### 5.3 启动时序（改 `main.ts` 的 `boot()`）

```
restore() → 渲染大厅（0 网络）
  → 并行：login() + fetchConfig()
  → applySnapshot()
  → 拉关卡表（版本号一致就跳过）
  → outbox.flush()
```

现在 `boot()` 是串行 await 登录才继续，弱网下首屏白等 10 秒。
**快照先渲染、网络后到**，是这次必须一起改的。

## 6. 后台：一个页面看三端

### 6.1 数据从哪来

```
原始层：events（带 platform）/ level_records / scores / ad_events / user_active_daily
   ↓ 每日 04:00 定时任务（跟 leaderboard.RefreshAll 同一个 goroutine 里加一个）
汇总层：platform_daily
   ↓
后台页面：只读汇总层 + 少量实时查询（Redis 在线数）
```

**不要**让后台直接扫 `events`（它增长最快，见 17 号文档：1 万用户 360MB）。

### 6.2 页面结构

```
┌ 时间范围 [近7天 ▾]   平台 [全部 | 微信 | 抖音 | H5] ┐
├ 4 张指标卡：DAU / 新增 / 人均通关 / 广告完播率        │
├ 趋势折线：三端分线（同一张图，按平台着色）             │
├ 关卡漏斗：level_start → level_pass（按关号，可筛模式）  │
├ 分端对比表：DAU / D1 / D7 / 人均关卡 / 广告/DAU        │
└ 实时：在线人数（Redis key 计数）
```

### 6.3 关键 SQL

```sql
-- 分端 DAU
SELECT day, platform, active_users
FROM platform_daily
WHERE day BETWEEN $1 AND $2
ORDER BY day, platform;

-- 分端新增
SELECT date_trunc('day', created_at)::date AS day, first_platform, count(*)
FROM users
WHERE created_at >= $1
GROUP BY 1, 2;

-- D1 留存（按首登日 cohort）
WITH first_day AS (
  SELECT uid, min(day) AS d0 FROM user_active_daily GROUP BY uid
)
SELECT f.d0, a.platform,
       count(DISTINCT f.uid) AS cohort,
       count(DISTINCT CASE WHEN a.day = f.d0 + 1 THEN a.uid END) AS d1
FROM first_day f
JOIN user_active_daily a ON a.uid = f.uid
WHERE f.d0 BETWEEN $1 AND $2
GROUP BY 1, 2;

-- 关卡流失（哪一关掉人最多）
SELECT level_idx,
       count(*) FILTER (WHERE skipped = 0) AS passed,
       avg(time_ms) AS avg_ms,
       avg(undos)   AS avg_undos
FROM level_records
WHERE mode = 1
GROUP BY level_idx
ORDER BY level_idx;
```

### 6.4 实现选型

| 方案 | 做法 | 适合 |
|---|---|---|
| **A. 内置轻后台**（推荐） | `internal/admin` + 一个静态页（ECharts CDN 或内联），`/admin` 挂 Basic Auth，只读接口 5 个 | 一个人维护、2C4G、要能随时改指标 |
| B. Metabase / Superset | Docker 起一个，连**只读 PG 角色**，指标用 SQL 保存问题 | 运营要自助拖拽、指标频繁变 |

两者都建立在「同一张表 + platform 列」上，不冲突：先 A 上线，B 以后接同一个库即可。

**权限与脱敏**

- 后台用**独立只读 PG 角色** `admin_ro`，只授 `SELECT`，物理上不能改业务数据。
- 手机号只展示后四位（`phone_enc` 不解密）；openid 不展示。
- 后台账号 `admin_users`（bcrypt），角色 `viewer / operator`；操作类动作（补发、封禁）写 `admin_audit`。
- `/admin` 走 nginx IP 白名单，不暴露在公网裸奔。

## 8. 坑清单（都是这个项目已经验证过的）

1. **迁移每次启动重跑。** 没有 schema_migrations，所有 DDL 必须 `IF NOT EXISTS`；
   `ALTER COLUMN DROP NOT NULL` 可重复，`DROP CONSTRAINT IF EXISTS` 也可重复，但**不要写 `ADD CONSTRAINT` 不带判重**。
2. **小游戏首次拿不到 unionid。** 不要把它设成 NOT NULL，也不要"没有 unionid 就拒绝登录"。
3. **`openid` 不能当账号主键。** 现在 `openid_hash` 是唯一键，多端必然要拆，越晚拆成本越高。
4. **游客身份只能用一次。** 同一台手机换账号，不能把上一个人的进度并过去。
5. **设置冲突用 LWW，但只在用户主动操作时写。** 启动时"顺手同步一次"会把另一台设备的操作覆盖掉。
6. **`progress.sync` 是整体覆盖。** 服务端少返字段 → 本地数组变 `undefined` → 渲染循环中断（已发生过）。新接口必须返回完整快照，或明确字段级 patch。
7. **星级是派生数据，不要落表。** 落表就要在改算法时洗 1000 关 × N 用户。
8. **广告计数只能服务端加。** 客户端上报 `completed=true` 必须带 `clientId` 幂等，并做小时级频控，否则可刷。
9. **跳过日期时区。** 客户端用 `toISOString()`（UTC），服务端用 `time.Now()`（本地），跨零点会不一致；统一按服务端时区，客户端只做展示。
10. **合并不迁 events。** 迁了会把同一批事件算两遍，留存/漏斗全错。
11. **后台不要直查 events。** 它是增长最快的表，先落 `platform_daily`。
12. **JWT 里加 platform 只为分析。** 鉴权只看 uid，否则多端 token 会互相踢。

## 10. 一页总结

```
现在：微信单端 + 一半数据在本机 + 埋点不分端
目标：uid 为轴，身份可叠加，数据可跨端，后台可切片

做法：
  1) users 拆出 user_identities（游客先建号，登录是绑定）
  2) 装备/主题/声音/广告解锁 全部搬进 user_settings / user_unlocks
  3) 登录响应直接带全量快照，客户端本地只做缓存 + outbox
  4) events / active / daily 三处都带 platform，后台只读汇总层
  5) 三把钥匙：unionid 自动、手机号跨生态、迁移码兜底
```
