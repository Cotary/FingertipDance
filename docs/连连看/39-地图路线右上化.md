# 39 · 地图路线「右上化」：为什么旧路读起来像弹簧

> 触发：玩家反馈「地图的路左右乱晃，不像一条往山上走的路」。
> 改的是 `games/line/src/ui/mapview.ts` 的 `nodeX`（几何公式整体重写）
> + `pickMapNode`（顺带修掉一个老 bug：命中死带）。

---

## 一、症状与诊断

反馈是「路在原地晃」。看着像画得不好，实际是一个**统计量**的问题。

先量一遍旧版（`CENTER_X = 353` + 对称三角波 + 两层正弦摆动）：

| 指标 | 实测值 | 含义 |
|---|---|---|
| 第 1 关 x | 229 | 左 |
| 第 1000 关 x | 518 | 右 |
| **每 15 关窗口的中位数在往右走的比例** | **32 / 65 = 49%** | 几乎正好一半 |

第一眼是「整条路从左到右」，所以没人会说不它在向右。
但**每滚一屏，路的中位位置只有一半的时候在往右挪**，
另外一半时间它在往回退 —— 拖导轨时视线里的路就停在原地打转。

**这就是「弹簧」的来源。**

### 病根：三层叠加，全是零均值

| 层 | 旧参数 | 净漂移 |
|---|---|---|
| 三角波（走势腿） | 上升 16 关 / 下降 12 关，振幅 180 | 上行总距 = 下行总距 → **0** |
| 正弦摆动 | 振幅 86，周期 6.8 关 | 零均值 |
| 第二谐波 | 振幅 10，2.31 rad/关 | 零均值 |

三层加起来，**任一时刻路都在横着来**，没有任何一层负责「往上走」。
三角波只是让路在屏幕中部荡，正弦只是让荡得没那么规律。

## 二、新几何：基线 + 非对称折返

```
x(i) = BASE0 + (BASE1 − BASE0)·(i/999)     // 基线：从左下持续爬到右上
     + tri(i)                               // 折返：每 8 关一次，上下不对称
     （再经 7 点滑动平均圆角）
```

| 参数 | 值 | 理由 |
|---|---|---|
| `ROUTE_BASE0` / `ROUTE_BASE1` | 190 / 500 | 基线两端。决定整条路的左右跨度 |
| `ROUTE_UP` / `ROUTE_DOWN` | **6 / 2** | 折返的上下段长度 —— **本题的关键** |
| `ROUTE_AMP` | 130 | 折返振幅。峰谷差 260 |
| `ROUTE_SMOOTH` | 0.8 关 | 圆角窗口 ≈ 半径 55px |

### 关键在「不对称」

折返的上升段和下降段**故意不等长**：

```
上升段斜率 = 2·AMP/6 ≈ 43 px/关   （缓坡）
下降段斜率 = 2·AMP/2 = 130 px/关  （陡崖，一回头就到底）
```

于是**每 8 关里有 6 关在向右走、只有 2 关在向左退** —— 右行占比 75%。

| 公式 | 右行占比 |
|---|---|
| 纯正弦 | 50% |
| 旧版对称三角波（16/12） | 57% |
| **新版非对称三角波（6/2）** | **75%** |

「路在原地晃」的感觉来自**左行占比太高**：
50% 的时间在往回退，拖导轨时视线里的路自然停在原地打转。
把左行压到 25% 之后，路才真的读作「一直往右上爬」。

顺带还解决了「坡太缓不像山」：旧的 16/12 只差 4 关，上下坡几乎一样缓；
新的 6/2 差 4 关但**绝对差值大得多**（130 vs 43 的斜率差），
回头弯一眼就能看出来。

### 为什么仍然用三角波而不是正弦

正弦在波峰附近斜率趋近 0，路径会**贴着头顶竖着走四五个节点**
（两颗粒子上下叠着），比直线更难看。三角波的斜率是常数，节点永远在往前走。

## 三、实测（改完之后）

| 指标 | 旧版 | 新版 |
|---|---|---|
| x 范围 | 104..611 | 80..610 |
| 第 1 关 / 第 1000 关 x | 229 / 518 | 80 / 500 |
| **右行占比** | **50%** | **75%** |
| **窗口中位数往右走的比例** | **32 / 65 = 49%** | **65 / 65 = 100%** |
| 每关 \|dx\| 中位 | 48 | 44（没有一关原地不动） |
| 一屏里的弯数 | — | 2~4（既有测试要求 2~5） |
| 一屏横向跨度下限 | 233 | 222（既有测试要求 ≥180） |
| 固定半径下相邻节点命中圈不相交的对 | 315 / 399 | 321 / 399 |
| ↳ 修完之后仍然点不中的中点 | 315 处 | **0** |
| 珠子边到卡左缘 / 导轨手势区 | — | 10px / 20px（都不切边） |

新公式的各项常数是用**数值搜索**在「函数形状固定」的前提下定出来的：
`test/mapview.test.ts` 里的断言就是搜索时用的约束集。

## 四、顺带修掉的一个老 bug：命中死带

新几何比旧几何横向跨度更大（陡崖段相邻两关能差 110+），
这暴露了 `pickMapNode` 里一个一直存在的漏洞。

**旧版就有**：用真实 `nodeY` 量前 400 关，有 **315 对**相邻节点的命中圈**不相交**
（两枚半径 36 的圆心距 > 72，最大圆心距 147）。
也就是说**四分之三的地图上**，按在两关正中间会两边都落空 —— 按下去毫无反应。

旧几何的横向幅度小，315/399 这个比例一直被当成「正常」；
新几何把它照出来了（321/399）—— 不是新几何造成的病，
是**同一个洞在新几何下更显眼**。

**修法**：命中判定加一档「路面走廊」。

```
① 直接命中节点圆盘（半径 max(36, 视觉半径 + 8)）
② 落在两关之间的「路面」上 → 归给最近的那一关
   （点到线段距离 ≤ 22px）
```

路面是玩家**看得见**的东西，所以「按在路面上」就该按到旁边那一关。
`CORRIDOR = 22` 比路面本身（外晕 18）略宽一点，够手指粗，
又不会把远处的关捞进来。

修完：可见区里**每一对**相邻关的中点都能被捞到（死带 0）。

> 顺带说明：旧公式里的 `CENTER_X`（中轴常量）在这次重写中一并删掉了 ——
> 新公式没有「中轴」这个概念，路是「从左下爬到右上」的，没有对称中心。

## 五、验证

```
npm run typecheck          # 通过
npx vitest run             # 43 文件 / 376 用例全过
npm run build              # 通过
```

新增断言（`test/mapview.test.ts`）：

| 用例 | 守的是什么 |
|---|---|
| 整条路持续向右上 | 窗口中位数往右走的比例 ≥ 70%（实测 100%） |
| 起点在左下、终点在右上 | `nodeX(1) < 170`、`nodeX(1000) ≥ 499` |
| 整条路不切卡边、也不压导轨手势区 | 珠子边留在 `[44, 656]` 内 |

拖右侧导轨时路随之右移 —— 均符合预期。
