## 3. 命令约定

**客户端（`games/line/`）**

| 用途 | 命令 |
|---|---|
| 安装依赖 | `npm install` |
| 开发服务器 | `npm run dev` （→ http://localhost:5173） |
| 类型检查 | `npm run typecheck` （`tsc --noEmit`） |
| 单元测试 | `npm test` （vitest run） |
| 单测 watch | `npm run test:watch` |
| 生成关卡表 | `npm run level:gen -- --count 1000 --out data/levels.json` |
| 批量体检 | `npm run level:audit -- --file data/levels.json` |
| 构建 | `npm run build` |

**后端（`server/`）**

| 用途 | 命令 |
|---|---|
| 编译 | `go build ./...` |
| 单测 | `go test ./...` |
| 本地起服务 | `go run ./cmd/http --config ../deploy/config.local.yaml` |
| 起依赖（MySQL+Redis） | `docker compose -f deploy/docker-compose.yml up -d mysql redis` |

**Go 代码风格**
- 包名小写单字（`core`, `modules`, `games`），不用 `utils` / `common` / `helpers` 这种名字
- 文件名小写下划线：`leaderboard.go`（不用 `Leaderboard.go`）
- 导出类型注释以类型名开头：`// LevelTable 提供关卡的只读访问。`
- 错误用 `fmt.Errorf("...: %w", err)` 包装，不用 `errors.New(fmt.Sprintf(...))`
- handler 逻辑放 `internal/games/line/`，gin handler 只做「解析参数 → 调业务 → 写响应」

## 4. TypeScript 风格

- `strict: true`，禁止 `any`（确实需要时用 `unknown` + 收窄）
- 禁止 `enum`（用 `as const` 对象 + `typeof` 推导，避免运行时开销与 tree-shaking 问题）
- 导出统一 `export function` / `export const` / `export interface`
- 纯函数优先：**`core/` 下所有函数必须无副作用、无 `Date.now()`、无 `Math.random()`**
  - 随机一律通过 `rng.ts` 提供的 `Rng` 实例传入
  - 时间一律由调用方传入 `nowMs` 参数
- 注释用中文，只解释「为什么」，不解释「做了什么」

## 5. 关键数据类型约定

```ts
// core/types.ts
export const Dir = { UP: 0, DOWN: 1, LEFT: 2, RIGHT: 3 } as const;
export type Dir = (typeof Dir)[keyof typeof Dir];
export const DIRS: Dir[] = [Dir.UP, Dir.DOWN, Dir.LEFT, Dir.RIGHT];

export const CellType = {
  BLOCK: 0,    // 阻挡块，不可进入
  BRICK: 1,    // 普通砖块，进入即点亮
  ONEWAY: 2,  // 单向块，需配合 dir
  START: 3,    // 起点
  END: 4,      // 终点
} as const;
export type CellType = (typeof CellType)[keyof typeof CellType];

export interface Cell {
  type: CellType;
  dir: Dir;    // 仅 type === ONEWAY 时有效
}

export interface Level {
  idx: number;      // 1..1000
  seed: number;     // 32 位
  w: number;        // 列数
  h: number;        // 行数
  grid: Cell[][];   // grid[y][x]
  shortest: number; // 理论最少步数（BFS 得出）
  turns: number;    // canonical 路径转弯数
  blocks: number;
  oneways: number;
  diff: number;     // 0..100
  unlockSkin: string | null;
}
```

**方向语义（必须统一，别搞反）**
- `Dir.UP` 表示「移动方向朝上」，即从 `(x, y+1)` 走到 `(x, y)`
- 单向块 `dir = UP` ⇒ **只能从下方进入**
- 箭头图形朝上 ⇒ 只能向上进入 ⇒ 表示"流向朝上" ⇒ 玩家必须从下面走进来

## 6. 坐标与几何

- 格子 `(x, y)`，`x` = 列（向右增大），`y` = 行（**向下增大**）
- 索引 `idx = y * w + x`
- 邻接：`nx = x + DX[dir]`, `ny = y + DY[dir]`，其中 `DX = [0, 0, -1, 1]`, `DY = [-1, 1, 0, 0]`
- 设计分辨率 750×1334，棋盘区域左右各留 **40px** 安全边距

## 8. 每日工作总结文档（**每次做完必写**）

> **规则：每完成一轮工作（无论大小），必须写一份当天日期命名的工作总结文档。**

### 8.1 命名与位置

- **文件名**：`YYYY-MM-DD.md`（日期用**实际完成当天**的日期，如 `2026-11-06.md`）
- **位置**：`docs/连连看/工作总结/`
- 同一天多次工作 → 追加到当天同一个文件里，**不要新建第二个同名文件**

### 8.2 必写章节

```markdown
# YYYY-MM-DD 工作总结

## 一、今日目标
（开工时想解决什么问题 —— 没有目标也要写「例行巡检」）

## 二、做了什么
（按「模块 / 文件」组织，每条写清**做了什么**和**为什么这么做**，
  不要写成流水账「改了 A、改了 B」）

## 三、关键决策与取舍
（哪些方案被否了、为什么否；这次改动牺牲了什么）
**必须写「否决的方案」** —— 只写做了什么，下次的人会重复走同一条弯路。

## 四、验证结果
（跑过的命令 + 关键输出数字，例如「go test ./... 全过（9 个包）」
  「vitest 159/159 通过」）
**没有验证过的部分必须显式写「未验证」**，不要含糊。

## 五、遗留问题与下一步
（明确的下一步动作，含文件路径 / 关号 / 优先级）
```

### 8.3 为什么要有这条

- 这个项目跨了 **TypeScript 客户端 + Go 服务端 + 关卡生成器 + 数据表** 四层，
  一次改动的影响面往往超出当次范围。日期文档是唯一能追溯「为什么现在长这样」的地方。
- 「否决的方案」尤其重要：大量返工来自重复尝试已被否掉的路子。

### 8.4 与 README 进度表的关系

- `README.md` 的「执行进度」表记录 **TASK 级别的完成状态**（打勾 + 产出物路径）
- 本目录的日期文档记录 **每天做了什么**（细节、决策、遗留问题）
