# 双平台小游戏 + 数据后台 · 总体设计

> 2026-11-20 起。目标：一套代码同时发布**微信小游戏**与**抖音小游戏**，
> 一套后端同时服务两端，配一个简易但可靠的数据后台看运营数据。

---

## 零、先给结论（三件事）

1. **代码不用分两套。** 现有架构已经把平台差异收进 `src/platform/`，
   编译期用 `__TARGET__` 选实现。加抖音 = **新增一份 `douyin.ts`**，
   不需要 fork 游戏逻辑。真正需要"两套"的只有：
   **平台密钥/广告位 ID（配置）**、**小游戏工程脚手架（game.js/game.json）**。
2. **广告数据能拿到，但不在游戏进程里拿。** 微信有
   `publisher_adpos_general`（广告汇总，90 天窗口），抖音有
   `traffic-master-advertising-data`（按日期/广告位/宿主/OS/渠道筛选）。
   两者都是**服务端对服务端**拉，需要各自的开放平台凭证。
   → 后台的广告页做「平台 API 同步 + 手动补录」双轨。
3. **后台不要上重框架。** 一个 Go 服务 + 一套服务端渲染的 HTML
   就够看数据。要的是「打开就能看懂」，不是又一个中台。

---

## 一、双平台：差异到底在哪

先把「哪些必须分、哪些绝对不能分」钉死。**分错了就会出现两套逻辑各自跑偏**。

| 维度 | 必须共用（一套） | 必须分开（两套） |
|---|---|---|
| 游戏逻辑 | 关卡、规则、渲染、UI、动效、音效 | — |
| 网络协议 | HTTP API、错误码、JSON 结构 | — |
| 数据模型 | 用户、进度、成绩、挑战 | — |
| 平台能力 | 接口形状（`Platform` 契约） | 登录 / 分享 / 广告 / 存储 / 振动 / 画布 |
| 构建产物 | TypeScript 源码 | 工程脚手架（`game.js` / `game.json` / 后台配置） |
| 运营配置 | 配置**结构** | 配置**内容**（appid、广告位 ID、域名） |

**判定标准**：如果一个差异会改变「玩家看到的画面」或「服务端收到的数据」，
它属于**共用**层，必须靠抽象抹平；如果差异只是「调用哪个宿主 API」，
它属于**平台层**，各写一份。

## 二、抖音接入：平台层新增一份实现

### 2.1 现有抽象已经够用

`src/platform/types.ts` 定义的 `Platform` 接口：
`login / request / storage / ad / share / vibrate / getCanvas / resizeCanvas / onResize / openDataAvailable`。

抖音小游戏（`tt.` 命名空间）与微信（`wx.`）**高度同形**，差异如下：

| 能力 | 微信 | 抖音 | 处理 |
|---|---|---|---|
| 登录 | `wx.login` → code | `tt.login` → code（另有 anonymousCode） | 各自实现 |
| 存储 | `wx.getStorageSync` | `tt.getStorageSync` | 同名同义，直接换前缀 |
| 请求 | `wx.request` | `tt.request` | 同上 |
| 激励视频 | `wx.createRewardedVideoAd` | `tt.createRewardedVideoAd` | 同上 |
| 插屏 | `wx.createInterstitialAd` | `tt.createInterstitialAd` | 同上 |
| 振动 | `wx.vibrateShort({type})` | `tt.vibrateShort({type})` | 同上 |
| 画布 | `wx.createCanvas` | `tt.createCanvas` | 同上 |
| 分享（好友） | `wx.shareAppMessage` | `tt.shareAppMessage` | 抖音**支持自定义 query** |
| 分享（朋友圈） | 2022 起**不可定制**，只能开菜单 | 抖音**无朋友圈**，改为「分享到抖音/好友」 | 能力矩阵不同，见 2.3 |
| 分享（录屏） | 无 | `tt.getGameRecorderManager` 可录屏投稿 | 抖音独有，可选接入 |

### 2.2 关键设计：平台能力矩阵

分享这块两平台差异大，不能用同一个「好友/朋友圈」二选一。
改成**查询能力**而不是**假设能力**：

```ts
interface Platform {
  /** 该平台支持的分享通道。UI 只渲染这里列出来的。 */
  readonly shareChannels: ShareChannel[];
}

type ShareChannel = 'friend' | 'timeline' | 'douyin' | 'record';
```

- 微信：`['friend', 'timeline']`（timeline 只是打开菜单）
- 抖音：`['friend', 'douyin']`（douyin = 分享到抖音，走 `tt.shareAppMessage` 的频道参数）
- Web：`['friend']`（系统分享面板）

**分享面板不再写死四个渠道**，而是「平台报什么就画什么」。
这样加平台不用改 UI 代码。

### 2.3 抖音的坑（提前记下来）

1. **`tt.login` 有 `anonymousCode`** —— 抖音允许匿名登录。
   我们的服务端 `users` 表以 `openid` 唯一，抖音要用 `openid`（真有）
   还是 `anonymousOpenid`？**决策：优先真 openid，拿不到才降级匿名**，
   并在 users 表加 `platform` 列区分（见 3.1）。
2. **小游戏包大小限制更紧**：抖音主包 4MB（微信 4MB 但可分包到 20MB）。
   当前产物需实测，超了要把关卡表外置（已有 `/api/levels-v3` 接口，天然支持）。
3. **域名白名单**：抖音后台要单独配 request 合法域名，与微信不共用。
4. **抖音无 `onShareTimeline`**，朋友圈按钮不该出现 —— 靠 2.2 的能力矩阵自然解决。

## 三、后端：一套服务两端

### 3.1 数据模型要加的三样东西

现有 `users` 表以 `openid_hash` 唯一。接抖音后必须能回答
「这个人是微信来的还是抖音来的」，`events` 也必须带平台维度。

```sql
-- 008_platform.sql

-- 用户归属平台。0=未知(老数据) 1=微信 2=抖音 3=Web
ALTER TABLE users ADD COLUMN IF NOT EXISTS platform SMALLINT NOT NULL DEFAULT 0;
ALTER TABLE users ADD COLUMN IF NOT EXISTS platform_uid VARCHAR(128) NOT NULL DEFAULT '';

-- 埋点也带平台：否则「抖音的分享率高还是微信高」这种问题答不了
ALTER TABLE events ADD COLUMN IF NOT EXISTS platform SMALLINT NOT NULL DEFAULT 0;

-- 广告收益（平台侧同步来的，不是我们埋点）
CREATE TABLE IF NOT EXISTS ad_revenue (
  id          BIGSERIAL   PRIMARY KEY,
  platform    SMALLINT    NOT NULL,
  day         DATE        NOT NULL,
  ad_type     VARCHAR(32) NOT NULL DEFAULT '',   -- banner/interstitial/rewarded
  placement   VARCHAR(64) NOT NULL DEFAULT '',   -- 广告位 id 或名称
  impressions BIGINT      NOT NULL DEFAULT 0,
  clicks      BIGINT      NOT NULL DEFAULT 0,
  revenue_fen BIGINT      NOT NULL DEFAULT 0,    -- 统一用「分」，避免浮点
  source      VARCHAR(16) NOT NULL DEFAULT 'api', -- api=自动拉 / manual=手工录
  fetched_at  TIMESTAMP   NOT NULL,
  UNIQUE (platform, day, ad_type, placement)     -- 重复拉同一天要幂等
);
```

**为什么金额用「分」（整数）**：浮点累加会漂（0.1+0.2≠0.3），
对账差一分钱查半天。全链路整数，只在展示层除 100。

**为什么 `UNIQUE` 约束包含 `placement`**：平台接口按广告位返回明细，
同一天多个广告位各一行；重拉同一天要能 upsert 覆盖，不能追加成两倍。

### 3.2 平台身份如何进入系统

现在的登录只有微信一条线。改成：

```
POST /api/login
  { code, platform: "wechat" | "douyin" | "web" }

服务端：
  1. 按 platform 选 code2session 实现
  2. 拿到 openid
  3. users 表按 openid_hash 查（**不按 platform 分表**）
     - 命中 → 更新 last_login、若 platform 为空则补上
     - 未命中 → 插入，写 platform
```

**为什么不按平台分表**：同一个自然人可能在两端都玩，
但我们的 `openid` 两端格式不同，本来就是两个账号。
分平台列而不分表，好处是查询/统计代码只有一套。
（将来真做「跨端同人合并」再加 `union_id`，现在不做。）

### 3.3 广告数据同步

```
微信：GET https://api.weixin.qq.com/publisher/stat
        ?action=publisher_adpos_general&access_token=..&start_date=&end_date=
抖音：POST https://minigame.zijieapi.com/mgplatform/api/apps/ad/income/query
        { start_date, end_date, page_no, page_size }
```

两个同步器的共同点，也是必须处理好的几点：

1. **access_token 要缓存**（微信 7200s，抖音类似），不能每次拉都换。
2. **单次时间窗有限**（微信 90 天），要按窗口切片，从「上次同步到的日期」往后拉。
3. **幂等**：靠 3.1 的 `UNIQUE` + `ON CONFLICT DO UPDATE`。
4. **失败不能影响主服务**：同步走独立 goroutine + 定时器，
   失败只记日志和「上次同步时间」，不阻塞任何游戏接口。
5. **必须可手工补录**：平台数据可能延迟一天、也可能因为权限没开拿不到。
   后台要能手动录一行，`source='manual'` 区分。

### 3.4 后台 API（只读为主）

```
GET /api/admin/stats/overview   总览：注册数/DAU/新增/留存(次留)/付费(暂无)
GET /api/admin/stats/platform   分平台：注册、活跃、关卡进度分布
GET /api/admin/players          玩家列表（分页/搜索/按平台筛）
GET /api/admin/players/:id      单个玩家详情（进度、成绩、挑战、广告观看）
GET /api/admin/levels           每关详情（通过率、平均重来、卡点排行）
GET /api/admin/ads              广告数据（按天/平台/广告位）
POST /api/admin/ads/sync        手动触发一次平台数据同步
POST /api/admin/ads/manual      手工补录一行
```

**鉴权**：独立于玩家 JWT。用 `admin` 表 + 单独的 token（scope=admin），
**绝不复用玩家 token** —— 玩家 token 泄露不该等于后台沦陷。

## 四、后台前端：服务端渲染，不引前端框架

### 4.1 为什么不上 React/Vue

要看的就四类数据：总览数字、平台对比、玩家列表、关卡明细。
这类「表格 + 几个数」的界面，服务端渲染 + 少量原生 JS 最省事：

- 没有构建步骤 —— 改一行 HTML 刷新就见效，不用等打包
- 没有依赖升级焦虑 —— 后台不是产品，不该占维护预算
- 首屏快 —— 直出 HTML，不需要等 JS 水合

代价是交互弱一点（筛选要刷新页面），但后台**本来就该刷新页面**。

### 4.2 页面结构

```
/admin/login          登录
/admin                总览（核心数字 + 趋势）
/admin/platform       平台对比（微信 vs 抖音）
/admin/players        玩家列表（搜索 / 分平台 / 分页）
/admin/players/:id    玩家详情
/admin/levels         关卡明细（通过率 / 卡点）
/admin/ads            广告数据（收入 / 展示 / 点击 / eCPM）
```

**总览要回答的三个问题**（这是设计的锚点，别堆没用的图）：
1. **有多少人在玩** —— 注册总数、今日新增、DAU、次留
2. **玩到哪了** —— 进度分布直方图（第 1-10 关多少人、11-50…）
3. **钱从哪来** —— 广告收入按平台拆，eCPM 对比

### 4.3 视觉

复用游戏的主题色（秘色天青）做成**深色数据台**：
深釉底 + 鎏金数字 + 青瓷表格线。
好处是运营看后台和看游戏是同一个世界的，不用切换脑子。
但不做动效、不做动画 —— 后台要的是**读数快**。

## 六、明确不做（避免反复摇摆）

- **不做跨端同人合并**：两端 openid 不同就是两个账号。真要做需要 union_id + 手机号绑定，不在本期。
- **不做实时数据**：统计按小时/天聚合，不追求秒级。
- **不做自定义报表**：固定七页够用。
- **不做 A/B 实验平台**：文案池手动替换。
- **不做付费/内购统计**：当前没有虚拟支付。
- **不在客户端拉广告数据**：广告收益是平台侧数据，客户端不可能拿到，别试。

## 七、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 抖音小游戏包超 4MB | 无法发布 | 关卡表外置（已有接口）；实测后决定是否分包 |
| 广告数据接口权限没开 | 广告页空白 | 手工补录兜底；页面显式提示「未同步」而非显示 0 |
| 抖音 openid 与微信混用 | 数据串 | `platform` 列 + `openid_hash` 仍唯一，登录时写死来源 |
| 后台泄露 | 全部运营数据 | 独立 admin token + 内网/白名单；不做注册入口 |
| 两端埋点字段不一致 | 无法横向对比 | `events.platform` 统一；后台按平台 GROUP BY |

### 实测结论

**1. tree-shaking 真的把两个平台隔开了。**
`grep` 两个包：

```
line-dy/dist/game.js  → tt.login ×2, tt.createRewardedVideoAd ×1, 无 wx.*
line-wx/dist/game.js  → wx.login ×2, wx.createRewardedVideoAd ×1, 无 tt.*
```

这两个包都是 **473KB / gzip 120KB** —— 远低于抖音主包 4MB 限额，
**不需要分包**，关卡表也不必外置（但 `/api/levels-v3` 接口本来就在，将来变大可切）。

**2. 权限边界确实不可穿透。**

```
玩家 token → /api/admin/stats/overview  → {"code":4001,"msg":"管理员令牌无效"}
后台 token → /api/admin/stats/overview  → 正常返回数据
```

**3. 广告数据的能力边界（这是你问的那个问题）。**

| | 能拿到 | 需要什么 | 粒度 |
|---|---|---|---|
| 微信 | ✅ `publisher_adpos_general` | access_token（appid+secret 换） | 按天 + 广告位，**单次 ≤90 天** |
| 抖音 | ✅ `traffic-master-advertising-data` | openapi client_token | 按天 + 广告位 + **宿主 App + OS + 归因渠道** |

两者都是**服务端对服务端**，客户端拿不到（客户端只知道「看了几次」，
不知道「值多少钱」）。数据通常 **T+1**。

后台的策略是**双轨**：
- 「立即同步」按钮 → 走平台接口（`modules/adrev`）
- 「手工补录」表单 → 接口拿不到时录入，`source='manual'` 且**不会被同步覆盖**

未同步时广告页显示 **0 但带明确提示**，不让人误以为「这几天没赚钱」。

**4. 后台 6 页已可用**（真实数据 463 注册 / 平均 177 关）。

### 已发现并修掉的两个显示 bug

- **eCPM 单位错**：`sumRev` 是「分」，直接除以曝光再 ×1000 会放大 100 倍
  （1250 分 / 1200 次 = 1041.67，真实值 1.04 元）。已改为先除 100。
  这类错**不报错、看着像个数**，所以补了 `TestYuanToFen` /
  `TestYuanToFenNoFloatDrift` 锁住精度。
- **进度分布被悬殊值压扁**：430 人「未开始」把其余各段压成 1~2px。
  改为**已开始玩家内部占比**，并标注分母（「占全体」/「占已开始」）。

  抖音需要用 `configureDouyinAds` 注入另一套。等抖音后台建好广告位再扩字段。
- **抖音录屏分享**（`tt.getGameRecorderManager`）：抖音独有能力，本期不做。
