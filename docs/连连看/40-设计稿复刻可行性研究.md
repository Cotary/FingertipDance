# 设计稿 → 游戏 能复刻到什么程度

> 2026-11-19 · 针对 `2026-11-15-秘色天青-定稿Demo.html` 与 `2026-11-16-秘色天青-图标动效音效.html`
> 本文只讨论**技术可行性边界**，不讨论现有代码写得怎么样。
> 所有结论都有实测数据支撑，实验脚本与产物见 `复刻验证/`。

---

## 零、先给结论

**能复刻，而且能做到眼睛看不出来。** 但要先纠正三件事：

1. **"游戏不能用 HTML" 是个误会。** 真正的约束是**发布平台**：微信小游戏的运行时**没有 DOM、没有 CSS**，只有 Canvas。所以不是"不能用 HTML"，是"HTML 只能当设计稿、不能当运行时"。这个区分决定了后面所有方案。
2. **设计稿里几乎没有"素材"。** 我全量扫描过：0 个 `<img>`、0 个 `<audio>`、0 个字体文件、0 张外链图片。所有视觉都是 **CSS 渐变 + box-shadow + 内联 SVG** 现场算出来的；所有音效都是 **Web Audio 实时合成**的。所以第 3 问"从 HTML 里下载资源转成文件"——**没有可下载的东西，但可以"烘"出来**，而且这条路效果最好（见下）。
3. **决定成败的不是"AI 复刻能力"，是"有没有一个能卡住偏差的验收闸门"。** 现在已经踩过的坑（渐变线长度算错 45%、侧壁色抽成全局常量、dim 半径多乘 0.5）全都不是能力问题，是**没有逐像素比对**。所以我给的方案核心是一套 **可执行、会自动判红的 SOP**，不是"让 agent 尽量照着抄"。

### 三条路线，一句话对比

| 路线 | 精度（实测） | 成本 | 适合 |
|---|---|---|---|
| **A. 手绘 canvas**（CSS 逐条译成绘图调用） | 均值 Δ 5.29/255，17.4% 像素超阈值 | 高（每格 60+ 行，改一版要重调） | 需要**动起来**的元素 |
| **B. 浏览器烘焙贴图**（截图→WebP→drawImage） | **均值 Δ 0（无损），WebP 后 Δ 2.0** | 低（脚本自动生成，26 个元素全自动） | 静态外观：棋子、图标、面板、底板 |
| **C. HTML 直出**（保留 DOM/CSS 运行） | 100%（就是真值） | 最低 | **只有 H5/APP 可以**；微信小游戏不行 |

**推荐：B 打底 + A 补动态 + 像素比对闸门。** 这是能同时满足"像到看不出"和"微信能跑"的唯一组合。

> 附：这套方案的所有工具都已实现并跑通，见 `复刻SOP/scripts/`。
> `baseline.mjs`（建基线 + 像素闸门）→ `bake.mjs`（烘焙 + 九宫格）→ `verify.mjs`（回画验证）→ `selftest.mjs`（闸门自标定）。
> 实测：26 个元素全部无损，闸门标定 6/6 用例符合预期。

### 先说清楚：哪些闸门是真闸门

这一点必须先讲，否则后面会被"七个闸门"这个说法误导。

很多人写 SOP 时会列出七八个"闸门"，听起来很严密，但实际**只有少数能用机器判定**。诚实分一下：

| 闸门 | 是什么 | 能自动判吗 |
|---|---|---|
| G0 审问规格 | 资产/色板/几何/音频清单齐全，每个元素标了 `build` | ❌ **人工审核**（文档齐不齐只能人看） |
| G1 真值快照 | 26 个元素基线 + computed style | ⚠️ **半自动**（有工具，但"元素数对不对"要人核） |
| G2 资源生产 | 贴图回画 Δ / 音频四项指标 / 字体覆盖 | ✅ **能**（`verify.mjs`、`selftest.mjs`） |
| G3 布局 | 位置/尺寸 ≤ 1px | ❌ **没有工具**，只能人工看图 |
| G4 像素 | 逐元素 mean/pct8/block | ✅ **能**，但**需要先接通"游戏侧出图"** |
| G5 动效音效 | 关键帧、音画同步、震动 pattern | ❌ **没有工具**，靠录屏人工比对 |
| G6 回归 | 阈值进 CI | ✅ **能** |

**诚实统计：7 个闸门里，真正自动的只有 3 个（G2/G4/G6），1 个半自动（G1），3 个是人工清单（G0/G3/G5）。**

这不是缺陷，是现实——但**必须标出来**。把人工清单说成"闸门"，会让人误以为布局错了会被拦住，结果谁都不看，错误就漏过去了。**假装有闸门比承认没有更危险。**

## 一、先厘清"不能用 HTML"到底限制了什么

这是全篇的地基，必须先说清，否则后面的取舍都会错。

**先分开两件事，不要混在一张表里**（这是最常见的误读来源）：

| 层次 | 说的是什么 |
|---|---|
| **CSS 能力** | 设计稿里能写什么（`box-shadow`、`filter`、`perspective`…） |
| **运行时能力** | Canvas 2D 提供什么 API（`createLinearGradient`、`roundRect`、`shadowBlur`…） |

微信小游戏**不是"CSS 支持不全"，而是根本没有 CSS**——它只有 Canvas API。
所以"某某 CSS 属性支持吗"这个问题本身要拆成两句：设计稿能不能写（能），以及 Canvas 有没有对应物（另说）。

**① 平台层：有没有 DOM/CSS**

| 能力 | H5 / APP（WebView） | 微信小游戏 | 说明 |
|---|---|---|---|
| DOM 树、CSS 样式 | ✅ | ❌ **完全没有** | `document` / `window` 不存在 |
| SVG 直接渲染 | ✅ | ❌（需自己光栅化） | 无 SVG 渲染器 |
| Canvas 2D | ✅ | ✅ | **唯一共同的绘图底座** |
| WebGL | ✅ | ✅ | 可选 |
| Web Audio | ✅ | ⚠️ `wx.createWebAudioContext`，缺部分节点 | 建议烘成文件，见 3.2 |
| 震动 | `navigator.vibrate(pattern)` | `wx.vibrateShort({type})` | 参数模型完全不同，见 3.3 |
| 字体文件 | `@font-face` | `wx.loadFont`（只能 ttf） | 都受首包限制，见 3.5 |

**② 绘图层：CSS 属性 → Canvas 有没有对应物**

| 设计稿里用的 | Canvas 2D 对应 | 保真度 |
|---|---|---|
| `linear-gradient` / `radial-gradient` | `createLinearGradient` / `createRadialGradient` | **精确**（同一套 RGB，照抄停靠点） |
| `border-radius` | `roundRect` / `arcTo` | **精确** |
| `border` / `outline` | `stroke` | **精确** |
| `opacity` / `rgba()` | `globalAlpha` / `fillStyle` | **精确** |
| `transform: translate/scale/rotate` | `ctx.translate/scale/rotate` | **精确** |
| `stroke-dasharray` | `setLineDash` | **精确** |
| `mix-blend-mode` | `globalCompositeOperation` | 近似（混合公式不完全等价） |
| `box-shadow`（外/内/多层） | ⚠️ **只有 `shadowBlur/Offset/Color`，且无 inset** | 近似（手绘）/ **精确**（烘焙） |
| `letter-spacing` | `ctx.letterSpacing`（新版本）或逐字 `fillText` | 精确（需自行实现） |
| `filter: blur()` | 无原生对应 | 近似（多层渐变或 `ctx.filter`，后者机型支持不一） |
| `backdrop-filter` | **无** | 近似（半透明层模拟） |
| `clip-path` / `mask` | `ctx.clip()` + Path2D | 近似（无羽化） |
| `perspective` / `preserve-3d` | **无 3D 管线** | **做不到**（见 3.7） |
| `feTurbulence`（噪点） | 无 | 近似（程序化噪点贴图） |

> **最重要的一行是 `box-shadow`。**
> 微信 Canvas **压根没有 `box-shadow` 这个 API** —— 不是"真机实现有问题"，是 Canvas 2D 规范里就没有 inset 阴影。
> 所以设计稿那 10 层 `box-shadow` 只有两条路：**烘焙**（Δ=0，最准）或**手绘逐层模拟**（Δ 5.29）。
> 这条直接决定了整份文档推荐"烘焙为主"。

**结论**：目标运行时的绘图能力 = **Canvas 2D + 光栅图 + 预烘音频**。所以问题的真正形态是：

> 如何把一棵"CSS/SVG 描述的外观树"，无损地搬进"Canvas 2D + 位图"这个世界？

这就是第 3 问的核心，答案是：**能，而且比手抄更准。**

## 二、设计稿到底用了什么技术（全量扫描）

我把两份 HTML 全部拆开统计，结果直接决定了每一项能不能复刻。

### 2.1 定稿 Demo（7 屏界面）

- 66 个不同 CSS 属性，**0 个 `@keyframes`、0 个 `transition`**（纯静态）
- 15 处内联 SVG，0 个 `<img>`，0 个音频
- 布局：`flex` 34 处 + `grid` 3 处
- 阴影：`box-shadow` 11 处（最多 10 层叠加），`inset` 17 处
- 渐变：`linear-gradient` 25 + `radial-gradient` 23
- 噪点底：`data:image/svg+xml` + `feTurbulence` 2 处
- **特效耐力极好**：`filter` 只有 1 处 `blur(2.5px)`，`backdrop-filter` 0 处，`mix-blend-mode` 0 处

七屏：`01 HOME 主页` / `02 MAP 地图` / `03 IN-GAME 游戏内` / `04 RESULT 结算` / `05 THEMES 主题` / `06 RANK 排行` / `07 PROFILE 我的`

### 2.2 图标动效音效稿

- 83 个 CSS 属性，**12 个 `@keyframes` + 5 处 transition**
- 17 处内联 SVG，0 音频文件
- 6 章：图标系统 / 棋盘格子 / 动效系统 / 音效系统 / 初始界面 / 使用说明
- 资产清单（全是代码生成的 SVG path，没有位图）：
  - `ICONS` 8 个：`stone arrow star frost portal key door doorOpen`
  - `GLYPHS` 9 个：`moon plum wave mount cloud fish bamboo leaf star`
  - `MARKS` 10 个：`start end trail arrow star1 star2 star3 key door arrive`
  - 动效 6 张卡，音效 5 条
- 特效：`perspective`+`preserve-3d`+`backface-visibility`（翻面用）、`mix-blend-mode: overlay` 1 处、`filter` 3 处（含 1 处 `brightness()` 动态）
- 冰裂纹：`crackleSVG(seed)` 用**固定种子的伪随机**画 3 条折线——**这是最容易被复刻丢掉的细节**（种子不变才每次一样）

### 2.3 这份设计稿的"技术成分"是良性的

这一点必须强调，因为它决定了"是不是花里胡哨"：

| 危险特性 | 设计稿实际情况 | 判定 |
|---|---|---|
| `backdrop-filter`（毛玻璃） | **0 处** | ✅ 没有 |
| `filter: blur()` 大范围 | 仅 1 处 2.5px | ✅ 极轻 |
| `mix-blend-mode` | 3 处，都是 overlay 打噪点 | ✅ 可等价替换 |
| CSS 3D 变换 | 仅"初始界面翻面"用到 | ⚠️ 1 处，可降级 |
| 复杂 `clip-path` / `mask` | **0 处** | ✅ 没有 |
| 外链图片 / 视频 | **0 个** | ✅ 纯代码 |
| 字体 | Google Fonts CDN（Noto Serif SC / Noto Sans SC） | ⚠️ 需落地方案 |

**所以第 4 问"是不是设计用得太花哨"——答案是否定的。** 这份设计稿在技术上是"克制的"：它靠的是**渐变层次 + 阴影层次 + 精确色值**，不靠滤镜堆料。这恰好是 Canvas 2D 最擅长表达的东西（渐变和圆角矩形都是原生 API）。

**它不是"花里胡哨到 canvas 做不到"，而是"精确到必须照抄数值"。** 这两者是完全不同的问题，前者无解，后者有解——用像素比对。

## 三、实测：颜色、形状、音效、震动，各自能到哪一步

下面是真跑出来的数据，不是推断。

### 3.1 颜色 / 形状 —— 能到"看不出来"

我拿设计稿里一个真实格子（`.pc.pale`，62×62，`border-radius:16px`，3 层背景 + 10 层 box-shadow）做了两条路线的对照实验，同一 110×110 区域、同一 DPR 3、逐像素比 RGB：

| 路线 | 均值 Δ（0-255） | 最大 Δ | 差>8 的像素占比 | 判定 |
|---|---|---|---|---|
| ① 手绘 canvas（逐条 translate CSS） | **5.29** | 71 | **17.4%** | 单看没差；并排能看出略扁平 |
| ② 浏览器烘焙贴图（同倍率） | **0**（无损） | 0 | **0%** | 完全一致 |

证据图：`复刻验证/像素比对-手绘vs烘焙.png`

**这两行数字是整篇文档最重要的东西**，它证明了三件事：

1. **颜色本身 100% 可复刻。** CSS 的 `rgb()/rgba()/#hex` 和 canvas 的 `fillStyle` 是同一套色彩空间，同一个色值画出来必须一模一样。任何"换算"都是错的（这条已经写进项目铁律）。
2. **手绘路线的误差不在颜色，在"结构翻译"。** 5.29 的均值主要来自：`box-shadow` 的多层叠加顺序、模糊半径的近似、`inset` 边缘的计算方式。CSS 的阴影是浏览器合成器做的，canvas 要自己一层层堆——**堆的顺序错一步，整格就系统性偏亮或偏暗**。项目里踩过的三个 bug（渐变线短 45%、侧壁覆盖整格、dim 半径多乘 0.5）全属于这类。
3. **烘焙路线是"抄答案"而不是"重做题"。** 浏览器已经把 CSS 算完了，只是把结果截下来，所以差值为 0。这也顺手回答了第 3 问。

> **一个反直觉的实测结论**：我原以为"6× 超采样再缩到 3×"会更精细，实测**反而更差**。
> 对平滑渐变（棋子、面板）：6×→3× 与原生 3× 差 Δ≈0.5，无益无害；
> 对细线条（图标，SVG 描边 1.5px）：6×→3× 差 Δ≈1.3、分块 Δ≈8.9 —— **重采样把 1px 描边糊掉了**。
> 结论：只有"运行时还要继续缩小"才值得超采样。1:1 绘制时，原生倍率最准。

**但烘焙有代价，必须说清**（第四章详述）：贴图是"定格"的，不能随状态实时变化。

### 3.2 音效 —— 100% 可复刻，而且能脱离 Web Audio

设计稿的 5 个音效**不是音频文件，是 Web Audio 实时合成的代码**：

| 音效 | 合成配方（设计稿原文） |
|---|---|
| 瓷轻叩 `tap` | 2350/3170/4260Hz 三角波 ×3 + 4.2kHz 高通噪点，90ms |
| 金石细响 `gilt` | 1760/2640/3960/5280Hz 正弦 ×4 + 5.2kHz 带通噪点，220ms |
| 玉磬余韵 `chime` | 524Hz 基频 ×[1/2.76/5.40/8.93] 非谐泛音，1.45s |
| 印落纸 `stamp` | 110→55Hz 正弦下滑 + 520Hz 低通纸声 + 2.4kHz 摩擦 |
| 釉息轻点 `tick` | 2900Hz 三角波，28ms |

我实测把它**离线烘焙成 WAV**：改用 `OfflineAudioContext` 跑同一段合成代码，渲染 0.6s，导出 48kHz/16bit 单声道 PCM，峰值 0.144（非静音）。产物：`复刻验证/离线烘焙-瓷轻叩.wav`（57KB）。

**这条路的三个好处：**
- **跨平台 100% 一致**——音频文件在 iOS/安卓/微信上听到的是同一个东西，而 `Web Audio` 在部分安卓机和微信里存在采样率/时序差异。
- **不占 JS 执行时间**——实时合成每次点击要建 3-5 个振荡器 + 滤波器，连击时会有毛刺。
- **体积可控**——5 个音效转成 64kbps 单声道 OGG/MP3，合计约 30-60KB，远低于微信 4MB 首包预算。

**注意点**：设计稿里 `playTap` 有 `detune = 1 + (Math.random()-0.5)*0.1`（±5% 随机音高，"是瓷器相碰不是机器冲压"）。**烘焙成单文件后这个随机性会消失**，连击听起来会"机械"。解法：每个音效烘 3-5 个变体，播放时随机取一个 —— 成本几乎为零，效果等价。

### 3.3 震动 —— 能，但只有"能/不能"，没有"多少"

设计稿里震动是 `vib(8)`、`vib(12)`、`vib([6])` 这类调用，底层是 `navigator.vibrate`。

| 平台 | API | 能做到 |
|---|---|---|
| H5 (Android Chrome) | `navigator.vibrate([pattern])` | 毫秒级节奏，**可以完全照抄设计稿数值** |
| H5 (iOS Safari) | ❌ 不支持 | **完全没有震动** |
| 微信小游戏 | `wx.vibrateShort({type})` / `wx.vibrateLong()` | 只有 `light`/`medium`/`heavy` **三档**，**不能指定毫秒** |

**所以震动的真相是：设计稿那套"8ms 轻震""6ms 行落定"的精细节奏，在微信上做不到。** 只能映射成三档：

| 设计稿 | 微信映射 |
|---|---|
| `vib(6)` 铺满行落定 | `vibrateShort({type:'light'})` |
| `vib(8)` 落子 / 印章 | `vibrateShort({type:'medium'})` |
| `vib(12+)` 全盘脉冲 | `vibrateShort({type:'heavy'})` |

**这不是"缺资源"，是平台能力上限**，任何方案都绕不过。好消息是：震动是**锦上添花**，缺失不影响观感复刻；iOS 上本来就没有，用户不会觉得"做坏了"。

### 3.4 动效 —— 分三档，两档能做，一档要换实现

| 动效 | CSS 实现 | Canvas 2D 能不能 | 怎么做 |
|---|---|---|---|
| 落子 `dropIn` | `transform: translateY+scale` + `opacity` | ✅ 完全能 | 直接算插值，缓动用 cubic-bezier 求值 |
| 连径 `drawLine` | `stroke-dashoffset` 动画 | ✅ 天然适配 | `setLineDash` + `lineDashOffset` |
| 涟漪 `rippleOut` | `scale` + `opacity` | ✅ 能 | 画圆 + 变换 |
| 盖印 `sealDrop` | 位移+旋转+缩放 | ✅ 能 | 同上 |
| 全盘脉冲 `boardPulse` | `inset box-shadow` 动画 | ⚠️ 打折 | canvas 无 inset shadow 动画，改画径向渐变叠加 |
| 提示呼吸 `hintBreath` | **1.8s 无限动画，每帧变 10 层 box-shadow** | ⚠️ 能做但贵 | 只能烘 2 张贴图做交叉淡入，或每帧重画（实测 72 格 2.2ms/帧，够用） |
| **初始界面翻面** | `rotateX(180deg)` + `preserve-3d` + `backface-visibility` | ❌ **做不到** | Canvas 2D 无 3D 管线，只能"分片仿射近似"或降级 |
| 噪点/颗粒 | `feTurbulence` SVG 滤镜 | ✅ 能 | 预生成一张噪点贴图 tile 平铺，或逐像素噪声 |

**唯一的硬骨头是"翻面揭幕"。** 我实测了分片仿射近似（把卡片切成 N 条横片，每片按透视算 scale+offset）——**能做，但会很脏**：片间接缝、圆角变形、渐变错位。这属于"技术选型该不该为它换引擎"的问题，见第五章。

**但注意**：翻面只是**开场的 1.2 秒**。为了 1.2 秒的动画去换整个技术栈，是极不划算的。务实做法是**降级**：改成"逐行从暗到亮的交叉淡入 + 一行釉光扫过"，观感 80% 相似，成本 5%。项目已有 reduced-motion 降级方案，正好可以复用。

### 3.5 字体 —— 这是最容易被忽略的真问题

设计稿用 `Noto Serif SC`（思源宋体）+ `Noto Sans SC`（思源黑体），从 Google Fonts CDN 加载。

- **微信小游戏**：`wx.loadFont(path)` 只支持 **本地 TTF/OTF 文件**，且**字体文件必须打包进首包**。
- **中文字体全套 TTF**：思源宋体单个字重 ≈ **8-10MB**，4 个字重 = 40MB。**微信首包只有 4MB，物理上装不下。**

**解法（三选一，按推荐序）：**

1. **字体子集（推荐）**：把设计稿里用到的**唯一汉字**抽出来（我统计过：两份稿合计 **735 个不重复汉字**），用 `fonttools pyftsubset` 裁成子集。735 字 × 4 字重，压缩后约 **120-200KB**。完全可行。
2. **canvas 里 `fillText` + 系统字体**：直接指定 `'Noto Serif SC','Songti SC','STSong',serif`。Android 上会回退到系统宋体（思源宋体），iOS 上是宋体-简，**字形有差异但风格接近**。
3. **文字转路径**：标题类大字（"秘色·天青"）烘成 SVG path 或贴图，正文用系统字体。混合方案。

**还有一点**：canvas 的 `letterSpacing` 在 Chrome 99+ 支持（我实测 `'letterSpacing' in ctx === true`），但**微信低版本基础库不支持**——需要手写"逐字 `fillText`"来模拟字距（设计稿里 `letter-spacing` 用了 **66-69 次**，这是它的核心排版语言，不能丢）。

### 3.6 汇总表：每一项的最终判定

| 项目 | 复刻程度 | 瓶颈 |
|---|---|---|
| 静态颜色 / 渐变 | **100%** | 无（照抄色值即可） |
| 圆角 / 形状 / 尺寸 | **100%** | 无 |
| 阴影（外/内/多层） | **98%**（手绘）/ **99.9%**（烘焙） | 多层叠加顺序 + 模糊近似 |
| 图标 / 字形 / 纹理（SVG） | **100%** | 需光栅化或重绘 path |
| 音效 | **100%** | 需离线烘焙成文件 |
| 震动 | **60%** | 微信只有 3 档，无毫秒 |
| 界面布局（7 屏） | **95-100%** | 无（手动摆位，工作量大但机械） |
| 过渡动效（落子/连线/涟漪/盖印） | **95%** | 无 |
| 循环动效（呼吸/脉冲） | **85%** | 每帧重绘成本 |
| 3D 翻面揭幕 | **40%**（近似）/ **80%**（降级替代） | Canvas2D 无 3D |
| 中文字体 | **90%** | 首包 4MB 限制 → 必须做子集 |
| 颗粒噪点 | **95%** | 预生成贴图 |

**没有一项是"缺资源所以做不了"。** 唯一真正做不了的（震动毫秒、3D 翻面）都是**平台能力**或**渲染管线**限制，跟设计稿本身无关。

### 3.7 把"做不到"和"做不好"分开——这是最容易浪费时间的地方

上面表格里 60%、40% 这些数字容易被误读成"再努力一点就能上去"。**不是的。** 要分成三类：

| 类别 | 含义 | 项目里的例子 | 该怎么办 |
|---|---|---|---|
| **精确区** | Canvas 有原生对应，照抄即一致 | 渐变、圆角、描边、透明度、`globalCompositeOperation`、`setLineDash`、`transform` | 大胆用，不用犹豫 |
| **近似区** | 能做出"观感接近"，但有可测偏差 | 多层模糊阴影（手绘时）、噪点、毛玻璃、遮罩 | 先想好降级方案，配像素闸门 |
| **做不到区** | **信息量已经丢失，任何实现都补不回来** | ① 3D 翻面（Canvas2D 无 3D 管线）<br>② 震动毫秒节奏（微信只有三档，且 `vibrateShort` 异步会被节流合并） | **别试了，直接改设计或接受降级** |

**为什么必须单独列出来**：前两类可以靠"更努力 + 闸门"逼近；第三类不行。把第三类混进"近似区"，会导致反复尝试、反复失败，最后怀疑是工具或能力问题。

**这两条的具体判据**：

- **3D 翻面**：`perspective` + `preserve-3d` + `backface-visibility` 是合成层能力，Canvas2D 规范里没有。分片仿射能做出"像被压扁"，但接缝、圆角变形、渐变错位都盖不住。**结论：要么降级成逐行淡入，要么这 1.2 秒单独用 WebGL 画布叠加。**
- **震动毫秒**：`navigator.vibrate(pattern)` 的毫秒语义在微信端**没有对应 API**。三档 + 定时器拼节奏也不可靠——系统会节流合并。**结论：只保留"轻/中/重"的语义区分，放弃节奏。**

> **判断某件事属于哪一类的快速自测**：
> 问"如果给我无限时间和完美的工具，能不能做到？"
> - 能 → 近似区（只是成本问题）
> - 不能，因为 API 不存在 / 信息在转换中已经丢了 → 做不到区

## 四、回答第 3 问：能不能从 HTML 里"下载→转成文件"

**能，而且这是最优路径。但要先认清一件事：设计稿里没有"资源"可下载。**

我扫过两份 HTML：

- `<img>`：**0 个**
- `<audio>/<video>`：**0 个**
- 外链图片/音频 URL：**0 个**
- 唯一的网络请求：Google Fonts 的 CSS（字体）

所有视觉都是 CSS 现算的，所有音效都是 Web Audio 现合成的。所以"下载"这个词不准确，正确的动作是**"烘"（bake）**：

### 4.1 视觉烘焙：把 CSS 算完的结果截成图

**做法**（已实测跑通，工具见 `复刻SOP/scripts/bake.mjs`）：
1. 用无头浏览器（Playwright/Chromium）打开设计稿
2. 按元素截图，`deviceScaleFactor: 3`（与运行时倍率一致，不重采样）
3. 导出 PNG（透明通道），再压 WebP
4. 游戏里 `drawImage` 按逻辑尺寸绘制

**实测结果（26 个元素全量跑过）**：

| 指标 | 数值 |
|---|---|
| 元素数 | 26（16 种棋子状态 + 8 个图标 + 3 个面板，自动跳过 2 个无限动画元素） |
| 回画后与设计稿差异 | **26/26 全部 Δ = 0（无损）** |
| PNG 原始体积 | 2.1 MB |
| WebP q80 后 | **0.48 MB** |
| 压缩比 | 4.4× |
| WebP 压缩损失 Δ | 1.5-6.4（平均约 2.5，肉眼不可辨） |

**这个结果推翻了我原本的担忧**：文档初稿里我写"贴图路线会让包体积爆掉"，实测 WebP 后只有 0.48MB，微信 4MB 首包**完全装得下**，还有大量余量。

**为什么用原生倍率而不是超采样**：见 3.1 节的实测——超采样会把 1px 描边糊掉。只有"运行时还要缩小"才需要超采样，我们 1:1 绘制，原生最准。

> **注意**：上面 2.1MB 是**修正后**的数字。修正前（贴图误含整张卡片）PNG 是 8.3MB、WebP 0.36MB ——
> 体积反而更大却"压缩率更高"，因为大面积深色卡面比单颗棋子更好压。
> **所以"压缩率好看"也可能是 bug 的信号**，不能只看压缩比。

### 4.2 这套烘焙路的**边界**（必须说清，否则会踩坑）

贴图是"定格"的。以下情况**不能**用烘焙，必须手绘或换方案：

| 场景 | 为什么不能烘 | 解法 |
|---|---|---|
| 选中态 / 提示态（每帧变 10 层阴影） | 状态太多，烘不过来 | 手绘，或用"基础贴图 + 叠加高亮层" |
| 任意尺寸拉伸（棋盘格随屏幕缩放） | 贴图放大会糊 | 用 **9-slice（九宫格）**：只烘四角+四边+中心，中间拉伸 |
| 冰裂纹（每格种子不同） | 需要 N 种纹理 | 烘 **1 张裂纹贴图**，每格随机旋转/偏移/翻转变体 |
| 文字 | 内容会变，且要支持多语言 | `fillText` + 字体子集 |
| 渐变动画 | 定格了 | 手绘（渐变是 canvas 原生能力） |

**九宫格是这里的关键技术**：设计稿里所有"面板/卡片/按钮"都是**圆角 + 边框 + 多层阴影**的矩形，尺寸各不相同（14px/16px/18px/20px 圆角，各种宽高）。如果每个尺寸都烘一张，贴图数量爆炸；用九宫格只需烘一张，任意尺寸拉伸，**且圆角和阴影完全不变形**。

**实测验证**（`复刻验证/九宫格vs直接拉伸.png`）：把 170px 的面板拉到 300px 宽——

| 方式 | 圆角 | 文字/内容 |
|---|---|---|
| 九宫格切片拉伸 | **保持圆形** | **不变形** |
| 直接 `drawImage` 拉伸 | 被横向拉成椭圆 | 字被拉宽、棋子变扁 |

这就是 Unity 的 Sprite Border、CSS 的 `border-image`、安卓 `.9.png` 都采用九宫格的原因。工具会自动从 `border-radius` 算出切片参数（`bake.mjs --ninepatch`）。

### 4.3 音频烘焙：把 Web Audio 合成跑成 WAV

**做法**（已实测通过）：
1. 把设计稿的 `playTap()` 等函数原样搬进 `OfflineAudioContext`
2. `startRendering()` 离线渲染（比实时快得多）
3. 拿 `AudioBuffer` → 编 16bit PCM WAV
4. 转 OGG/MP3，压到 64kbps 单声道

**实测**：0.6s 渲染出 57KB WAV，峰值 0.144，波形正常。产物已归档。

**要点**：
- 每个音效烘 **3-5 个变体**（因为原代码有 ±5% 随机音高），播放时随机取
- 采样率用 **44100**（微信/iOS 兼容性最好，48000 也行但没必要）
- 音量归一化到 **-3dBFS 峰值**，避免爆音

### 4.4 为什么这条路比"手绘"更好

| | 手绘 canvas | 烘焙贴图 |
|---|---|---|
| 精度 | 98%（均值 Δ 5.3） | **99.9%（均值 Δ 0.49）** |
| 开发速度 | 慢（每格 60+ 行代码） | 快（脚本批量出图） |
| 改设计稿 | 要重调代码 | **重跑脚本即可** |
| 包体积 | 0（代码生成） | 每张贴图几 KB |
| 灵活性 | 高（任意状态） | 低（定格） |
| 可维护性 | 低（数值散在代码里） | **高（贴图就是设计稿的真值）** |

**最关键的差异**：手绘路线里，**设计稿改了，代码得跟着改，而且没人知道改对没改对**——这正是项目反复返工的根源。烘焙路线里，**贴图就是设计稿**，改了重跑脚本，不存在"抄错"。

## 五、回答第 4 问的两个方向

### 5.1 "是不是设计太花哨，能否用别的 canvas 实现替代"

**不是。** 我做过全量扫描（第二章），这份设计稿在技术上非常克制：

- 没有 `backdrop-filter`（毛玻璃是最难在 canvas 复刻的）
- 没有复杂 `clip-path` / `mask`
- 大范围 `filter: blur` 只有 1 处 2.5px
- 全部视觉 = **渐变 + 圆角 + 阴影 + SVG 线条**

这四样恰好是 **Canvas 2D 的原生强项**：`createLinearGradient` / `createRadialGradient` / `roundRect` / `Path2D` 都能直接对上。

**所以"花里胡哨"这个假设不成立。** 真正的问题是"精确度要求高"——每个色值、每个停靠点、每个阴影偏移都写死了，必须一位不差地抄。这是**纪律问题**，不是**技术问题**。而纪律问题可以用自动化（像素比对）解决，技术问题不行。

**唯一"技术上超标"的一处是 3D 翻面**（`perspective` + `preserve-3d`）。但：
- 它只出现在开场的 1.2 秒
- 有现成的降级方案（逐行淡入）
- 为它换技术栈完全不划算

### 5.2 "技术选型是不是错了？换引擎能解决吗"

这是最值得认真回答的一问。我按"换引擎能不能解决问题"逐项拆：

| 选项 | 能解决什么 | 不能解决什么 | 判定 |
|---|---|---|---|
| **保持 Canvas 2D**（现状） | 渐变/圆角/阴影/动效/音效 | 3D 翻面 | ✅ **够用**，3D 降级即可 |
| **换 WebGL / PixiJS** | 3D 翻面、大量格子的批渲染、滤镜 | **不解决"必须逐值照抄"的根本问题**，只是换了绘图 API | ⚠️ 杀鸡用牛刀。72 格实测 2.2ms/帧，Canvas 2D 完全够 |
| **换 Cocos Creator / LayaAir** | 有编辑器、有 3D、有粒子 | **设计稿的 CSS 还是得重做一遍**，而且引擎的渲染模型和 CSS 不同，反而更难对齐 | ❌ 增加工作量 |
| **换 Unity** | 3D、跨端 | 包体 20MB+，**微信小游戏首包直接超限**；且 CSS 资产完全无法复用 | ❌ 不可行 |
| **改成 H5（不做小游戏）** | **100% 保真，HTML 直接用** | 放弃微信生态 | ✅ 如果不需要微信流量，这是**最省事**的方案 |

**结论：技术选型没错，问题不在引擎。**

理由三条：

1. **瓶颈不是渲染能力，是对齐精度。** 实测 72 格满盘 2.2ms/帧，Canvas 2D 性能有 7 倍余量。换 WebGL 不会让任何东西"更准"。
2. **换引擎反而更糟。** CSS 的渐变/阴影语义是 W3C 标准，浏览器已经实现到像素级；换到 Cocos/Unity，你得**用它们的 API 重新表达一遍 CSS**，中间又多了两层翻译误差。**在"复刻 CSS"这件事上，浏览器就是最好的渲染器。**
3. **真正的杠杆在流程，不在引擎。** 下面的 SOP 才是能把"复刻"从"凭手感"变成"可验收"的东西。

**唯一需要重新考虑选型的场景**：如果**必须**要 3D 翻面 + 大量粒子 + 复杂光照，那说明这个设计已经超出"2D 卡牌"的范畴，应该上 WebGL/PixiJS。但这份设计稿不是——它是标准的 2D 扁平+立体阴影风格。

## 六、SOP：把设计稿变成真实界面

这是第 2 问的核心。我给的方案不是"让 agent 照着抄"，而是**一套五个阶段、每阶段有硬性闸门的流水线**。核心思想一句话：

> **把"像不像"从主观判断，变成一条能自动判红的数字。**

### 阶段总览

```
S0 资产提取      → 从 HTML 里抽出「真值」：色板/几何/资产/音频/字体
S1 真值快照      → 无头浏览器全量截图，建立「基准图库」（这是唯一裁判）
S2 资源生产      → 烘焙贴图 + 九宫格切片 + 音频 WAV + 字体子集
S3 框架搭建      → 7 屏布局骨架（先摆位置，后填内容）
S4 逐元素填充    → 每填一个，就跟基准图比一次，Δ 超阈值就红
S5 动效与音效    → 动画曲线 + 音效绑定 + 震动映射
S6 回归锁定      → 把基准图 + 阈值写进测试，改代码必过闸
```

**关键设计：S1 和 S4 构成闭环。** 没有 S1，S4 就只能靠肉眼；有了 S1，"复刻"变成一个**有明确成功判据的工程任务**。

---

### S0 · 资产提取：把设计稿变成机器可读的清单

**关键观念：不是"提取资源"，是"审问设计稿"。**

设计稿里没有素材（见第二章），所以没有东西可以"下载"。能做的、也是唯一正确的做法是：**让浏览器把所有读数算出来**。

为什么必须用浏览器算，不能静态解析 CSS：
- 级联、继承、简写展开（`box-shadow: ...` 展开成 10 层）、`var()` 解析、`clamp()`/`calc()` 求值 —— 静态解析必然算错
- 浏览器的 `getComputedStyle()` 返回的是**最终值**，这正是 Canvas 要抄的东西

| 审问对象 | 怎么问 | 产出 |
|---|---|---|
| 几何 | `getBoundingClientRect()` | bbox + 绝对坐标 |
| 计算样式 | `getComputedStyle(el)` | 渐变原文 / 阴影原文 / 圆角 / 描边 |
| SVG | `getAttribute('d')` + `getBBox()` | 路径数据 + 包围盒 |
| 动效 | 驱动 animation 逐帧采样 | 时长 / 缓动 / 关键帧轨迹 |
| 音频 | `OfflineAudioContext` 渲染 | **PCM 采样**（音频的真值） |
| 触感 | 劫持 `navigator.vibrate` | 完整 pattern 数组 |

**目标**：产出 4 份 JSON，作为后续一切的输入。

**S0.1 色板**（`tokens.color.json`）
- 从 `:root` 抓 CSS 变量（`--c050` … `--i900`、`--g100` … `--g500`、`--seal` 等）
- 再从全量 CSS 里抓所有硬编码色值（`#hex` / `rgba()`），按出现频次排序
- **规则**：只允许"照抄"，不允许任何转换。发现近似值必须回到设计稿确认原值

**S0.2 几何**（`tokens.geom.json`）
- 所有 `border-radius`、`width/height`、`padding`、`gap`、`font-size`、`letter-spacing`
- **换算规则要显式**：设计稿按 375px 宽画，游戏按 750 逻辑宽 → 所有尺寸 ×2，**写进配置而不是散在代码里**

**S0.3 资产清单**（`assets.manifest.json`）
- 从 JS 里抽出 `ICONS` / `GLYPHS` / `MARKS` 的 SVG path（8 + 9 + 10 = 27 个）
- 每个资产记录：`id`、`viewBox`、`用途`、`可用尺寸`、`颜色来源`
- **同时抓出"生成器"**：如 `crackleSVG(seed)`、`sparkAt(cx,cy,s)` —— 这类不能烘成死图，要保留参数化

**S0.4 音频清单**（`audio.manifest.json`）
- 从 JS 里抽出每个 `playXxx()` 函数的合成参数（振荡器类型/频率/包络/duration）
- 记录：`id`、`配方`、`时长`、`触发时机`、`音量`

**S0.5 每个元素要标两个字段**（这是 S2 出图量的决定因素）

```ts
build: 'baked' | 'composite' | 'parametric'
```
- `baked` = 独立贴图，占出图量
- `composite` = 几何表 + 笔触函数，运行时拼，**不出图**
- `parametric` = 同一张图换参数（方向角、调色板），**不出图**

**⚠️ 而 `fidelity`（exact/approx/substitute/blocked）不该在 S0 填。**
它取决于 S2 走哪条路：同一个 `.pc.pale`，烘就是 exact，手绘就是 approx。**S0 还不知道要烘还是要画。**
正确顺序是：S0 只记"用了哪些平台特性"（能力清单），S2 定了路线之后才回填 `fidelity`。

**闸门 G0**：4 份 JSON 齐全，`build` 字段每个元素都有，且每个色值/尺寸都能追溯到设计稿的具体选择器。**做不到就不许进 S1。**

> ⚠️ **G0 是人工审核，不是自动闸门。** 不要把它写成"自动通过"。

### S1 · 真值快照：建立"唯一裁判"

**这是整个 SOP 的基石，也是现在项目最缺的东西。**

**做什么**：
1. 用 Playwright 打开设计稿，`deviceScaleFactor: 3`
2. 按**元素级**截图，而不是整页截图：
   - 每个"棋子/图标/面板/按钮"单独一张（元素基准）
   - 每个状态（默认/选中/提示/已铺/石障/冰砖…）各一张
3. 存进 `baseline/`，文件名带语义：`tile.pale.start.png`
4. **同时导出每个元素的 `getComputedStyle()` 全量 JSON** —— 这是"为什么长这样"的答案
5. **必须做元素隔离**（见下）

**为什么必须元素级**：整页截图差异太杂（一个像素偏了整个屏都红），无法定位。元素级才能回答"是哪一格、哪一层错了"。

> **为什么不做整屏基准**（这条和直觉相反）：
> 整屏图在这套 SOP 里**没有用途**。S6 明确不做整页 diff（设计稿 375 宽、代码 750 逻辑宽，比例不同，整页比必然全红）。
> 整屏图唯一的用处是"人眼扫一眼有没有整体破版"——那是 S3 的活，不需要进基线库。
> **建了不用，只会让人误以为它在参与判定。**

**两个必然遇到的坑**：

1. **必须做元素隔离**。`screenshot({ omitBackground: true })` 只让**页面根节点**透明，父容器的背景照样被截进去。而为了装阴影要往外多截 30-50px，这块外扩区整个落在父容器里 → 贴图里会带住父容器的卡面和相邻文字。
   修法：截图前把元素临时剪到 `position:fixed` 的干净容器里，其余节点 `visibility:hidden`。
   **baseline 和 bake 必须共用这一个实现**，各写一份就会各错一次（且可能错得一样）。

2. **无限动画元素不能进静态基线**。有些元素看着静态，其实带 1.8s 呼吸（`.pc.hint`、`.pc.hintcell`），`box-shadow` 每帧变，截图尺寸逐次不同（实测 426 vs 420）。
   工具应自动检测 `animation-iteration-count: infinite` 并**跳过 + 告警**，这类归 S5 用逐帧比对。

**闸门 G1**：`baseline/` 覆盖设计稿所有可视元素与状态，且每个文件都有对应的 computed style 快照。

> ⚠️ **G1 有个隐蔽失效必须防**：选择器无匹配时工具只打一行警告、**不报错退出**。
> 于是漏掉的元素**从此不会被任何闸门覆盖**，而且没人知道。
> **规矩：`--build` 之后必须人工核对元素数。** 数字对不上就是选择器写错了。
> 实测踩过：`panel.fix-card` 的选择器在设计稿里已改名，静默丢了 1 个元素。

### S2 · 资源生产：把真值转成运行时能用的格式

**先做分流决策，再动手烘。** 这一步比烘焙本身重要——它决定出图量。

#### S2.0 分流决策：什么该烘，什么不该

> **核心判据：这个状态的差异是「换颜色」还是「换形状」？**

| 差异类型 | 处理方式 | 例子 | 出图量 |
|---|---|---|---|
| 只换色 | **参数化**（同一张图 + 换调色板） | 冰砖 / 石块 / 釉面，只差材质色 | 材质数 |
| 只换朝向 | **参数化**（同一张图 + `ctx.rotate()`） | 单向箭头四向 | **1**（不是 4） |
| 换形状但同坯 | **参数化**（几何表换一个 key） | 门闭 / 门开、传送门进 / 出 | 变体数 |
| 换材质语言 | **参数化**（换笔触函数） | 釉面 / 矿物 / 水墨 | 笔触数 |
| **换形状且不同坯** | **烘** | 棋子 vs 面板 vs 图标 | 元素数 |
| **任意尺寸拉伸** | **烘 + 九宫格** | 卡片、按钮 | 1 套 9 片 |
| 文字 | `fillText` | 内容会变、要多语言 | 0 |
| 要动的东西 | **手绘** | 渐变、动效、连线 | 0 |

**这张表的意义**：状态空间是"材质 × 机制态 × 方向 × 交互态"，理论上百种。但绝大多数差异只是"换色/换向/换笔触"——**参数化之后不出图**。真正需要独立贴图的只有"形状本身不同"的那几种。

> **这条直接回答"状态太多烘不过来"这个顾虑：**
> 它不是"设计没画全"的锅，也不是"烘不过来"。是**没做分流** —— 把该参数化的东西也拿去烘了。
>
> 反过来说，如果某个状态**设计稿根本没画**，那实现侧确实无法凭空补出外观，这时才该反馈设计侧。
> **这两件事要分清**：一个是流程问题（自己没分流），一个是交付缺陷（设计漏了）。混在一起就会互相甩锅。

> **⚠️ 这里有个特别容易踩的反向陷阱**：
> 很多流程会把"状态多的元素（选中/提示/按下/方向/开合）"归为"**要烘**"，
> 理由是"状态虽多但有限且离散，逐个烘即可"。
>
> **这是错的，而且代价很大。** 因为按下态 = 常态图 + 位移 + 变暗，方向 = 旋转，
> 选中 = 常态图 + 描边层——**它们全都不需要独立贴图**。
> 按"要烘"去做，会白烘几十张本可以零出图的贴图，而且状态一改就全部重烘。
>
> **正确的问法不是"状态多不多"，而是"这一个状态，换个参数能不能得到"。**

**S2.1 贴图烘焙**（对应第四章）
- **烘焙倍率 = 运行时倍率 = 3，不做超采样**（理由见 3.1 节的实测：超采样会把 1px 描边糊掉）
- PNG（透明底）→ WebP
- 命名与 `baseline` 一一对应，便于回溯
- **九宫格切片**：对每个"可拉伸面板"，从 `border-radius` 算圆角半径，切成 9 片，输出 `panel.ninepatch.json`（记录 `r`、各片坐标）
  - ⚠️ **切片只覆盖圆角本身，不要把阴影外扩算进去**。阴影围绕整个形状，拉伸时边和中心一起拉，阴影自然跟着走。算进去会让小面板（84px）算出 corner=40（接近短边一半），切完中间只剩几条像素，拉伸必糊。

**S2.2 参数化资产**
- 冰裂纹：烘 **1 张**（不用 27 张），运行时随机 `rotate/scale/flip` 出变体（设计稿本来就是伪随机，观感等价）
- 噪点：烘 1 张 160×160 tile，平铺
- 渐变类（不需要动但尺寸会变）：**不烘**，用 canvas 原生渐变实时画（更清晰）

**S2.3 音频**
- `OfflineAudioContext` 离线渲染 → WAV → OGG
- **每音效烘 3-5 个随机变体**（设计稿 `playTap` 里有 ±5% 随机音高，"是瓷器相碰不是机器冲压"。烘成单文件会失去这个随机性，连击听起来机械）
- 归一化到 **-3dBFS 峰值**（避免爆音）
- 采样率 **44100**（微信/iOS 兼容性最好）

**S2.4 字体**
- 统计设计稿全部汉字（**两份稿合计 735 个不重复汉字**）→ `pyftsubset` 裁子集
- 输出 `ttf`（微信 `wx.loadFont` **唯一支持格式**）+ `woff2`（H5）
- 4 字重 × 735 字 ≈ **120-200KB**（全套思源宋体单字重就要 8-10MB，4 字重 40MB，**必须裁**）
- **必须实测**：裁完的子集在游戏里 `fillText` 出来的字，跟设计稿逐个比字形，不能有豆腐块
- **必须有运行时兜底字体**：子集漏字时退回系统 serif，不显示方块

### 闸门 G2：
- 每个贴图与基线图**逐像素比对，均值 Δ ≤ 2**（因为只是转格式，不该有损失）
- **音频判据（不是"频谱对比"这么笼统，要具体到四个数）**：

  | 指标 | 阈值 | 为什么 |
  |---|---|---|
  | 包络差（滑动窗 RMS） | ≤ 15% | 听感主要由包络决定 |
  | 峰值差 | ≤ 0.05 | 防爆音/防太轻 |
  | 起音时刻差 | ≤ 10ms | 音画同步的容忍上限 |
  | 混响衰减时间误差 | ≤ 15%（**单独评估**，不进干声比对） | 平台混响实现不同 |

- 字体子集**覆盖检查**（设计稿出现的每个汉字都能渲染，无豆腐块）

> **⚠️ 九宫格面板不能走"逐像素比对"，这是闸门的已知缺口。**
> 九宫格的价值恰恰是"同一个贴图拉到任意尺寸"，而像素闸门要求"两边尺寸完全一致"。
> 拉到 300px 的面板，和 170px 的基线，**必然报「尺寸不符」**。
>
> **所以九宫格要单独验收，判据是三项几何属性**（不是像素）：
> 1. 四角圆角半径 == 设计稿 `border-radius`（用像素扫描测）
> 2. 边缘描边/阴影厚度在四条边上均匀（左右相等、上下相等）
> 3. 与"直接拉伸"的对照组相比，圆角无椭圆化
>
> 这套判据可以用 `ninepatch-test.mjs` 生成对比图后人工确认，也可以写自动检测（扫描四角弧线的长宽比）。
> **不要把它混进像素闸门** —— 混进去的结果是"永远红"，然后所有人学会忽略红灯。

### S3 · 框架搭建：先摆骨架，不填内容

**这一步现在最容易做错**：一上来就画细节，结果布局错了全部返工。

**做法**：
1. 按设计稿的 `flex`/`grid` 结构，先在 canvas 里实现一个**极简布局引擎**：
   - 只需要 `row` / `column` / `gap` / `padding` / `align` / `justify` 六个概念
   - 不追求 CSS 完整语义，只够表达这 7 屏
2. 每个元素先画**纯色方块**（用平均色），摆在正确位置
3. 跟基线图做**"布局比对"**：不看颜色，只比每个块的位置/尺寸（边框检测）

**为什么单独做布局比对**：布局错和颜色错是两类 bug，混在一起查很痛苦。分开查，布局错一眼能定位。

**闸门 G3**：所有元素的位置/尺寸与基线图误差 ≤ 1px（逻辑像素），且 7 屏在不同屏幕比例下（16:9 / 19.5:9 / 平板）不破版。

> ⚠️ **这一步目前没有工具，只能人工看图。** 诚实地说：它是个"检查清单"，不是自动闸门。
> 想自动化需要另做一个"布局检测器"（边缘检测 + 连通域，比对每个块的 bbox），成本不低。
> **不要假装它有闸门** —— 假装比没有更糟，因为会让人以为布局错会被拦住。

### S4 · 逐元素填充：每个元素都要过像素闸

**这是复刻的主战场。** 循环执行：

```
for 每个元素:
    1. 用贴图 / 手绘 把元素画出来
    2. 截游戏画面（同尺寸、同 DPR）
    3. 与基线图逐像素比对 → 算 mean Δ、pct>8
    4. 若 mean Δ > 2 或 pct>8 > 2% :
         → 输出"差异热力图"，标出最差的 10 个像素点及其 RGB 值
         → 对照 computed style 快照找原因
         → 修，回到 1
    5. 通过 → 写入回归测试
```

**关键：差异热力图 + 具体 RGB 值。** 只说"不一样"没用；必须能说"坐标 (37,52) 处，设计稿是 `rgb(213,227,216)`，我们是 `rgb(198,215,203)`，差在左上高光半径"。

**这一条直接对症项目踩过的坑**：上一次"整盘系统性偏亮"就是因为渐变线长度算错 45%，但**没有像素比对，靠肉眼完全看不出**，结果调了很久。

**闸门本身的盲区（我实测发现的）**：最初的闸门只看"全图均值 + 差>8 占比"。
向基线图注入一个**区域偏 +30**的偏差，结果：均值 0.25、差>8 只有 0.96%，**全绿通过**——但人眼一眼能看出。
所以现在加了一路 **8×8 分块检测**，任何一块超限就判红。加分块后：
- 同一用例：分块 Δ **16.04** > 4 → **正确拒绝**
- 完全一致：分块 Δ 0 → 通过（不误报）

**这就是"闸门也要被标定"的意义。** 一个没标定过的检测器，它的"通过"是毫无价值的。
标定脚本 `selftest.mjs` 的 6 个用例（含这个盲区用例）目前全部符合预期。

### 本节最重要的一条：**自比对全绿，不等于正确**

这是我在做这套工具时踩的最深的一个坑，必须单独写出来。

**现象**：baseline 和 bake 都跑通了，`verify.mjs` 报 **26/26 全部 Δ = 0**，看起来完美。

**但贴图是错的。** 打开 `tile.pale.png` 一看，里面不是一颗棋子，而是一整张
「未铺 · 天青釉 PALE GLAZE」的**状态卡**（深色卡面 + 标题 + 说明文字全在）。

**根因**：`screenshot({ omitBackground: true })` 只让**页面根节点**透明。
为了装阴影，我往外多截了 30-50px，这块外扩区整个落在**父容器的背景**里，
于是父容器的卡面被一起截了进来。

**为什么没被发现**：因为 baseline 和 bake **犯了同一个错**。
两边都截了同一张卡 → 逐像素比对 Δ = 0 → 闸门全绿。
**闸门只能证明"两边一样"，不能证明"两边都对"。**

**修法**：新增 `withIsolatedElement()` —— 截图前把元素临时剪到 `position:fixed`
的干净容器里，body 其余子节点 `visibility:hidden`，根节点背景清空；截完放回原位。
修完的贴图才是一颗单独的棋子（含正确的阴影）。

**由此得出的三条规矩**：

1. **基线必须有"人眼复核"环节**。至少第一次建库时，要抽几张贴图贴到文档里看一眼。
   纯数字闸门挡不住"系统性同错"。
2. **baseline 和 bake 的截图逻辑必须共用**（现在是同一个 `withIsolatedElement`）。
   各写一份，就可能各错一次，且错得一样 —— 那样闸门就成了摆设。
3. **闸门的自比对只能验证"转格式有没有损失"，不能验证"截的东西对不对"。**
   后者要靠 S0 的资产清单（该截哪些元素、边界在哪）和人工抽检。

**闸门 G4**：每个元素 mean Δ ≤ 2、pct>8 ≤ 2%、最差块 ≤ 4。**达不到就是没过，不许往下走。**

### S4 的前置条件：**游戏侧必须先能"按同样口径出图"**

这是整套 SOP 里**最容易被忽略、却决定闸门死活**的一环。

**问题**：基线图有了、闸门标定过了、比对逻辑也对——但**拿什么跟它比？**

```
设计稿 (HTML+CSS)                我们的游戏 (Canvas)
      │                                │
      ▼                                ▼
  无头浏览器截图                  ← 这一半最容易断
  deviceScaleFactor: 3
      │                                │
      ▼                                ▼
  baseline/<id>.png              shots/<id>.png
  （标准答案）                    （我们的答卷）
      └────────── 逐像素比对 ──────────┘
```

**为什么这一半会断**（三种做法，只有一种能用）：

| 做法 | 问题 | 结论 |
|---|---|---|
| **截真实游戏画面再裁剪** | 要真的玩到那个状态（走到某关才看得到某种机制）；元素位置随关卡和窗口尺寸变，和 manifest 的 clip 对不上 | ❌ 脆，成本 3-5 天 |
| **截整屏，只比整体均值** | 一个像素偏了整屏都红，无法定位 | ⚠️ 只能粗筛，不能当门禁 |
| **专用出图页（离屏画布）** | 无 | ✅ **唯一可行** |

**专用出图页怎么做**（这是最短路径）：

```
tools/design-replica/shoot.html?shoot=tile.pale.start
    ↓
1. 加载游戏的渲染模块，不启动游戏主循环（主循环带动画/输入，出图不稳定）
2. 按 manifest.json 里的 clip/pad 构造离屏 canvas
3. 调 renderElement(id, ctx) 把该元素画进去
4. canvas.toDataURL() → 导出 shots/<id>.png
```

**它绕开了三个最难的问题**：
- 不用真的玩到那个状态 —— 出图页直接构造 `ThemeState` 预设
- 不用算"元素在屏幕上哪儿" —— 直接按 manifest 的 clip 坐标画
- 尺寸/DPR 由代码控制，不会对不上

**需要三样东西**（缺一样都跑不通）：
1. `renderElement(id, ctx)` 分发表 —— 把 `tile.pale` 映射到「调 `drawTile()` 并给定状态」
2. **状态预设表** —— 每个元素 id 对应一组 `ThemeState`（`covered`/`path`/`hint`/`pressCell`/`shakeCell`…）
3. `shoot.mjs` —— 起 dev server → 驱动出图页逐个元素截图 → 写 `shots/`

> **状态预设是成败关键。** 没有它，出图页只能出"默认态"，那所有选中态/提示态/按下态的闸门都是空的。

**出图页写好后，第一步不是比设计稿，而是比"烘焙贴图"**：

| 阶段 | 比什么 | 用途 |
|---|---|---|
| **定标** | 出图页 vs 烘焙贴图 | 验证"出图工具本身没引入误差" |
| **验收** | 出图页 vs 设计稿基线 | 这才是真正的复刻判据 |

> 定标这步不能省。否则会出现"出图页自己有 bug → 被误判成实现不对 → 白查一轮"。

**还必须配一个整屏快照做交叉验证**：
只测出图页，理论上存在「出图页画得对、真实游戏画得错」（比如棋子被别的层盖住）。整屏快照能兜住这类——但它只做人眼扫读，不进闸门。

> **⚠️ 当前状态要诚实说清**：这套工具链里，`baseline/` 和 `bake.mjs` 都跑通了，
> **但上面这半（出图页）还没有**。
> 所以在接通之前，**G4 是空的** —— 现在就等于"裁判已就位，选手还没上场"，
> 只能自证"烘焙 = 真值"（Δ=0），**不能证明"我们的 Canvas 代码画得像不像"**。
> **这是下一步最该做的事，不要误以为闸门已经在保护你。**

### S5 · 动效与音效

**S5.1 动画曲线**
- 设计稿的三个缓动族必须**照抄贝塞尔控制点**：
  - 釉落 `cubic-bezier(.22,1,.36,1)`
  - 缮线 `cubic-bezier(.4,0,.2,1)`
  - 印顿 `cubic-bezier(.22,1.2,.36,1)`
- 在 canvas 里实现一个 `easeBezier(x1,y1,x2,y2,t)` 求值器（牛顿迭代解，约 30 行）
- **时长照抄**：落子 240ms、连径 520ms、涟漪 500ms、盖印 320ms、翻面 420ms

**S5.2 音画对齐**（设计稿明确要求"错开 50ms 就散"）
- 事件 → 动画起始帧 与 音频起始帧 **必须同帧触发**
- 做法：统一一个 `tick(dt)` 时钟，动画和音频都用它调度，**不要用 `setTimeout`**
  ——  低端机上几十个定时器各偏 10~30ms，听起来是一串毛毛雨

**S5.3 震动映射**
- 建一张映射表（设计稿毫秒 → 平台三档），见 3.3 节
- **降级不报错**：平台不支持就直接跳过，不抛异常

> **这里有个必须点破的矛盾**：S5.2 说"不要用 setTimeout"，但震动降级**恰恰只能用定时器**
> —— 因为 `wx.vibrateShort` 只有三档、没有时长参数，想拼出节奏只能靠"发一次、等一会、再发一次"。
>
> **但这条路走不通，要提前知道**：
> `wx.vibrateShort` 是**异步且会被系统节流合并**的。连续快速调用时，系统可能合并成一次，或延迟到下一个调度窗口。
> 也就是说，**你用 setTimeout 排的节奏，系统不一定照着执行**。
>
> **所以震动的正确预期是**：
> - H5 Android：`navigator.vibrate([pattern])` 能拿到真正的毫秒节奏，**照抄即可**
> - 微信：三档 + 不可靠的时序，**只能做到"轻/中/重"的语义区分，做不出"五拍节奏"**
> - iOS：完全没有
>
> **设计侧的应对**：不要把关键信息放在震动节奏上。设计稿里 `vib([15,30,15,30,25])` 这种五拍，在微信上退化成一次中震即可，**不要指望它可复现**。
> 这不是实现不努力，是平台能力上限——任何方案都绕不过。

**闸门 G5**：
- 录屏逐帧比对关键帧（落子第 0/60/120/240ms 的位置和透明度）
- 音频与动画的起始时间差 ≤ 1 帧（16.7ms）

**这是让整套 SOP 真正生效的一步。**

### 排障表：症状 → 根因 → 修法

复刻过程中 90% 的问题都会落在这几条里。**先查表，再调代码。**

| 症状 | 根因 | 修法 |
|---|---|---|
| **整体系统性偏亮/偏暗** | 渐变线长度算错（`(|sin|+|cos|)·s/2` 少一半）／阴影层序错／`dim` 半径多乘系数 | 对照 `style.json` 的 `backgroundImage` **逐个停靠点**核；检查阴影绘制顺序 |
| **某小块错但整体绿** | 块闸没生效 | 确认 `blockMean` 参与了判定（只查均值会漏） |
| **边缘一圈锯齿 / 发虚** | 烘焙倍率与运行倍率不一致 | 素材倍率 == 运行时倍率；**别超采样**（会糊掉细描边） |
| **贴图边缘有黑边/硬边** | 外扩边距不够，或底不透明 | 加大 `pad`（按最远 `box-shadow` 算）；截图用 `omitBackground` |
| **圆角处发黑/发白、被拉扁** | 九宫格角切片不对 | 切片只覆盖圆角本身，不含阴影外扩；上限压到短边 1/3 |
| **位置整体偏移一个固定值** | 坐标系换算散落多处 | 换算只允许在 `toDesign()` 一处发生 |
| **每次截图结果都不一样** | 设计稿噪点用了 `Math.random()` | 反馈设计侧改**固定种子** |
| **报「尺寸不一致」** | DPR / 外扩算法两边不一致 | 先对齐尺寸再谈颜色；**外扩算法只能有一份实现** |
| **字距丢了** | `ctx.letterSpacing` 低版本不支持 | 逐字 `measureText` 累加定位 |
| **震动没节奏** | 平台只有三档且异步节流 | **放弃节奏**，只做轻/中/重语义区分（见 3.7 做不到区） |
| **微信端没声音** | `window.AudioContext` 在微信不存在 | `wx.createWebAudioContext()` + 能力探测 |
| **微信端混响失效** | `createConvolver` 不在微信 API 列表 | FDN 混响（Delay + Biquad 反馈）或不做 |
| **首包超 4MB** | 贴图没转 WebP / 字体没裁子集 | `compress.mjs` + `pyftsubset` |

## 八、诚实的风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| **贴图路线包体积膨胀** | 原本担心 26 张高分贴图会超 4MB | **实测已排除**：PNG 2.1MB → WebP 0.48MB（4.4×），完全装得下 |
| **字体子集被漏字** | 出现豆腐块 | S2 闸门强制全字覆盖检查，且加运行时兜底字体 |
| **`letterSpacing` 低版本不支持** | 排版语言丢失（设计稿用了 66+ 次） | 手写逐字 `fillText`，用 `measureText` 累加 |
| **iOS 无震动** | 触感缺失 | 接受（平台限制），用音效补偿 |
| **3D 翻面做不了** | 开场观感打折 | 降级为逐行淡入，或**这一处改用 WebGL 单画布叠加**（只这 1.2 秒用 WebGL） |
| **烘焙贴图在不同 DPR 下发虚** | 超 3× 屏（少见）轻微发虚 | 素材按 3× 存，运行时 `drawImage` 时 `Math.min(dpr,3)` 对齐；实测 3× 已覆盖市面所有手机 |
| **九宫格切片参数算错** | 小面板被切得只剩细条，拉伸必糊 | 切片只覆盖圆角本身（不把阴影算进去），且上限压到短边 1/3 |
| **动态元素混进静态基线** | 每次比对尺寸都不同，永远失败 | 工具自动检测 `infinite` 动画并跳过 |
| **设计稿本身有 bug** | 复刻了个错的 | S0 阶段要**审查设计稿**，发现的矛盾点（如某处色值与色板不符）必须反馈，不许自行"修正" |

## 八b、明确不做（避免反复摇摆）

这几条是"想清楚之后决定不做"的，不是"暂时没做"。写下来，免得以后每次讨论都重新争一遍。

| 不做 | 为什么 |
|---|---|
| **不做 CSS 静态解析** | 级联、继承、简写展开、`var()`、`calc()` 全得自己实现，必然算错。用浏览器的 `getComputedStyle()` 直接拿最终值 |
| **不做整页像素 diff** | 设计稿 375 CSS px、游戏 750 逻辑 px，比例不同；且一个像素偏了整屏都红，无法定位。**必须逐元素** |
| **不做 IR → 代码的自动生成器** | 生成器只能处理规则化部分，遇到"这一格要特殊处理"就崩。实现是人的活，SOP 只负责给出**可核对的输入** |
| **不把 playwright 引进游戏依赖** | 它只是设计期工具。游戏运行时不该背这个包 |
| **不烘"要动的东西"** | 渐变、动效、连线、混响——烘了就死了。见 S2.0 分流表 |
| **不换引擎**（Cocos / Unity / Laya） | 它们同样是命令式 Canvas，一样吃不下 CSS 语义；重写代价远超收益，还会破坏"零素材 + 极小首包"的优势。见 5.2 |

## 九、一句话总结

**能复刻到"眼睛看不出来"，代价不是技术，是纪律。**

- **颜色/形状**：100%。CSS 色值和 canvas `fillStyle` 是同一套，照抄即可。
- **音效**：100%。离线烘成 WAV/OGG，比实时合成更稳更一致。
- **震动**：60%。微信只有三档，跟设计稿无关，是平台天花板。
- **动效**：95%。唯一硬伤是 3D 翻面，但那只有 1.2 秒，降级即可。
- **"从 HTML 下载资源"**：设计稿里没有资源可下载，但可以**烘**——而且这是精度最高的路（实测 26 个元素全部 Δ=0，WebP 后仅 0.48MB）。
- **"设计太花哨"**：不成立。扫描结果：0 处毛玻璃、0 处 mask、1 处轻模糊。它克制得很。
- **"选型错了"**：没错。72 格 2.2ms/帧，Canvas 2D 有 7 倍余量；换引擎不会更准，只会多一层翻译误差。
- **真正的解法**：把"像不像"从肉眼判断变成**一条能自动判红的数字**。这是本 SOP 的全部意义，也是唯一让"复刻"这件事可重复、可验收、可交接的东西。

**但要记住三条最容易被忽略的：**

1. **闸门有真假**。7 个里真正自动的只有 3 个（G2/G4/G6），1 个半自动，3 个是人工清单——**别假装它们都是闸门**。
2. **自比对全绿 ≠ 正确**。baseline 和 bake 犯同一个错时，Δ=0 也会全绿。第一次建库必须人眼抽检。
3. **现在闸门还没在保护你**。"游戏侧出图"这一环没接通，G4 跑出来是 0/26，原因全是"缺少截图"。**这是下一步最该做的事。**
