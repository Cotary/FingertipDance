## 2. users

```sql
CREATE TABLE users (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  openid        VARCHAR(512) NOT NULL DEFAULT '',
  openid_hash   CHAR(64)     NOT NULL,
  nickname      VARCHAR(64)  NOT NULL DEFAULT '',
  avatar        VARCHAR(512) NOT NULL DEFAULT '',
  max_level     INT          NOT NULL DEFAULT 0,
  total_time_ms BIGINT       NOT NULL DEFAULT 0,
  total_steps   INT          NOT NULL DEFAULT 0,
  unlocked_skins JSON        NOT NULL,
  ad_watch_cnt  INT          NOT NULL DEFAULT 0,
  created_at    DATETIME     NOT NULL,
  last_login_at DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_openid_hash (openid_hash),
  KEY idx_max_level (max_level)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 字段说明

| 字段 | 说明 |
|---|---|
| `openid` | **AES-GCM 密文**（密钥 = SHA256(appid+secret)），不存明文 |
| `openid_hash` | SHA256(openid) 的 base64url，唯一索引。查用户靠它，不用解密 |
| `max_level` | 最高**已通关**关卡（`0` = 一关都没通）。**跳过的关卡也推进**（否则玩家卡死）。<br>**注意**：这是「已通关的最高关号」，**不是**「下一个该打的关号」—— 后者是 `max_level + 1`。客户端凡是要判断「当前关 / 继续 / 解锁」的，一律用 `max_level + 1`，直接拿 `max_level` 当当前关会整体错一格 |
| `total_time_ms` | 累计用时。**仅首次通关累加**（防重复提交刷数值） |
| `total_steps` | 累计步数，同上 |
| `unlocked_skins` | JSON 数组，如 `["wood","mint","marble"]` |
| `ad_watch_cnt` | 累计完整看完的广告次数（用于风控与收益核算） |

### 索引
- `uk_openid_hash`：登录查用户的唯一路径
- `idx_max_level`：总榜重建时按关卡数排序（可选，量大后再加）

## 3. level_records

> **实际方言是 PostgreSQL**（见 `server/migrations/001_init.sql`），
> 下面这份 MySQL 风格的建表语句是早期稿，**字段含义以迁移文件为准**。

```sql
-- PostgreSQL（实际）
CREATE TABLE level_records (
  uid        BIGINT    NOT NULL,
  mode       SMALLINT  NOT NULL DEFAULT 0,   -- 0=经典 1=cover
  level_idx  INTEGER   NOT NULL,
  steps      INTEGER   NOT NULL,
  time_ms    INTEGER   NOT NULL,
  undos      INTEGER   NOT NULL DEFAULT 0,   -- cover 模式的悔棋次数
  path       JSONB     NOT NULL,
  skipped    SMALLINT  NOT NULL DEFAULT 0,
  created_at TIMESTAMP NOT NULL,
  PRIMARY KEY (uid, mode, level_idx)
);
CREATE INDEX idx_level ON level_records (level_idx);
```

### 设计要点

- **主键 `(uid, mode, level_idx)`** → 一人一关一条，天然幂等。重复提交走 upsert，保留更优记录
- **`mode` 列（2026-11-06 新增，迁移 `003_cover_mode.sql`）**：
  经典模式与 cover 模式**共用同一套关号空间**（都是 1..1000）。
  没有 `mode` 的话，同一个 `(uid, level_idx)` 会被两种模式互相覆写，
  而且星级会按错误的 `shortest` 算（cover 的 `shortest` 恒为 `required − 1`）。
  - `mode = 0` 经典模式（起终点连线）
  - `mode = 1` cover 模式（铺满全盘）
- **`undos` 列（2026-11-06 前新增，迁移 `002_cover_undos.sql`）**：
  cover 模式的步数恒为 `required − 1`，没有区分度，
  真正的成绩指标是**悔棋次数**（0 次 = 一次想通全程 = 3 星）。
  经典模式恒为 0。
- **`path` 存完整路径** → 用途：
  1. 防作弊复核（管理员可回放验证）
  2. 事后分析「玩家在哪些格子最常卡住」
  3. 未来做"回放"功能
- **`skipped=1`** → 该关是看广告跳过的，**不发放该关皮肤、不给星**
- **`idx_level`** → 统计每关的通过人数（"全区已有 X 人玩过第 N 关"）

### 保留策略
- 路径 JSON 平均约 200 字节/行。1000 万用户 × 1000 关 = 100 亿行 → **必须分区或冷热分离**
- **建议**：`created_at` 按月分区，或超过 90 天的记录只留 `(uid, level_idx, steps, time_ms)`，把 `path` 移到归档表

## 4. friends

```sql
CREATE TABLE friends (
  uid        BIGINT UNSIGNED NOT NULL,
  friend_uid BIGINT UNSIGNED NOT NULL,
  status     TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (uid, friend_uid),
  KEY idx_uid_status (uid, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### status
| 值 | 含义 |
|---|---|
| 0 | pending（已申请，待同意） |
| 1 | accepted（互为好友） |
| 2 | blocked（已拉黑） |

### 双向存两行
- A 申请 B → 写入 `(A,B,pending)` 和 `(B,A,pending)`
- B 同意 → 两行都改 `accepted`
- 好处：查询「我的好友」和「谁加了我」都是单表索引扫描，不用 UNION

### 与开放数据域的关系
- **开放数据域**（微信）：拿得到真正的微信好友关系，零成本，用于**好友榜**
- **服务端 friends 表**：自维护，用于**申请/同意/拉黑/助力记录**，Steam 版可复用
- 两者**好友列表不一定一致** → 好友页同时展示：开放数据域画榜，服务端算统计

## 5. scores

```sql
-- PostgreSQL（实际）
CREATE TABLE scores (
  id         BIGSERIAL PRIMARY KEY,
  uid        BIGINT    NOT NULL,
  mode       SMALLINT  NOT NULL DEFAULT 0,  -- 0=经典 1=cover（2026-11-07 新增）
  level_idx  INTEGER   NOT NULL,
  steps      INTEGER   NOT NULL,
  time_ms    INTEGER   NOT NULL,
  undos      INTEGER   NOT NULL DEFAULT 0,  -- cover 的重来次数（2026-11-07 新增）
  created_at TIMESTAMP NOT NULL
);
CREATE INDEX idx_uid ON scores (uid);
CREATE INDEX idx_created ON scores (created_at);
CREATE INDEX idx_scores_level_mode ON scores (level_idx, mode);
```

### 用途
- **只增不改** → 每次通关/挑战写一条流水
- 与 `level_records` 的区别：`level_records` 是「每关最优」，`scores` 是「历史流水」
- `idx_scores_level_mode` → 查某关的历史最佳（挑战结算用）
- 用途：流失热力图、难度回归验证、玩家行为分析

### 为什么 `scores` 也要有 `mode` 和 `undos`（2026-11-07）

`scores` 是**成绩流水表**，挑战接口要拿它算「历史最佳」：

| 模式 | 接口 | 最佳排序维度 |
|---|---|---|
| 经典 | `/api/challenge` | `steps` 最小 |
| cover | `/api/cover/challenge` | `undos` 最小（步数恒为 `required−1`，没有区分度） |

两个后果：

1. **漏了 `undos` 列 → `/api/cover/challenge` 100% 报 500**
   （`SQLSTATE 42703: column "undos" does not exist`）。
   2026-11-06 加迁移时只给 `level_records` 加了 `undos` 和 `mode`，
   **漏了 `scores`** —— 表建出来时只有 `(uid, level_idx, steps, time_ms)`。
2. **漏了 `mode` 过滤 → 两种模式的流水互相污染**。
   经典与 cover **共用关号空间**（1..1000）：
   cover 的 `steps` 恒为 `required−1`，混进来会把经典的 steps 最佳值拉低。

> **「历史最佳」必须是「自己的」** —— 查询要带 `uid`。
> 不带的话查的是**全服**最佳，第一个清关的人把纪录定死，
> 「刷新纪录」这个功能对所有人**永久失效**。
>
> **查历史必须早于写流水** —— 先写再查的话本次这一行也在「最佳」里，
> `isNewBest` 恒为 false。

## 6. skips

```sql
-- PostgreSQL（实际）
CREATE TABLE skips (
  uid        BIGINT      NOT NULL,
  mode       SMALLINT    NOT NULL DEFAULT 0,  -- 0=经典 1=cover（2026-11-06 新增）
  level_idx  INTEGER     NOT NULL,
  day        VARCHAR(10) NOT NULL,
  PRIMARY KEY (uid, mode, level_idx, day)
);
```

> **`mode` 列（迁移 `003_cover_mode.sql`）**：跳过次数是按「关」限的，
> 经典第 5 关跳过了不该把 cover 第 5 关的跳过机会也吃掉。

- 主键含 `day` → 每天每关只能有一条
- 服务端用 `INSERT IGNORE` 幂等写入，RowsAffected=0 即"今日已跳过"
- 客户端也存一份本地标记做快速预检（服务端仍会校验）

## 7. events（埋点）

```sql
CREATE TABLE events (
  id     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  uid    BIGINT UNSIGNED NOT NULL DEFAULT 0,
  name   VARCHAR(64) NOT NULL,
  params JSON NOT NULL,
  ts     DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY idx_name_ts (name, ts),
  KEY idx_uid (uid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 事件清单
见 `05-商业化与埋点.md` 第 6.1 节（22 个事件）。

### 清理策略
```sql
-- 保留 90 天
DELETE FROM events WHERE ts < DATE_SUB(NOW(), INTERVAL 90 DAY) LIMIT 10000;
```
加到每日 cron。

## 8. 关卡表（只读，不在 MySQL）

```
server/data/levels.json      公开，会下发给客户端
server/data/solutions.json   私密，仅服务端
```

**为什么不进 MySQL**
- 1000 关 × 95 字节 ≈ 95KB → 一次读进内存即可
- 只读、版本化、随代码发布 → 走 `go:embed` 或磁盘加载
- **不进数据库** → 避免每次查询都解码 base64

**版本一致性**
- `levels.json` 与 `solutions.json` 带同一个 `version`（内容哈希前 12 位）
- 服务端启动时校验两者版本一致 + 抽检 50 关 → 不一致**拒绝启动**

## 10. 容量估算（1 万用户）

| 表 | 行数 | 单行 | 总量 |
|---|---|---|---|
| users | 10,000 | ~300B | 3 MB |
| level_records | 10,000 × 30 关 = 300,000 | ~250B | 75 MB |
| scores | 10,000 × 30 = 300,000 | ~60B | 18 MB |
| events | 10,000 × 300 = 3,000,000 | ~120B | 360 MB |
| friends | 10,000 × 10 = 100,000 | ~50B | 5 MB |

**结论**：1 万用户约 460MB，2C4G 完全够。**events 表增长最快** → 必须有清理策略。

## 11. 迁移注意事项

- **DSN 必须带 `multiStatements=true`** → 否则 `db.Exec` 执行多语句 SQL 会失败
- **字符集 `utf8mb4`** → 昵称可能有 emoji
- **`loc=Local`** → 否则时区错乱
- **`parseTime=true`** → 否则 `DATETIME` 扫不进 `time.Time`
- 迁移按文件名顺序执行，**不重复执行**（用 `CREATE TABLE IF NOT EXISTS`）
