# 17 — 数据模型

## 1. 全表概览

```
users          玩家主表（含进度与皮肤）
level_records  玩家每关成绩（好友统计 / 防作弊 / 流失热力图的数据源）
```

## 2. users

```sql
CREATE TABLE users (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  openid        VARCHAR(512) NOT NULL DEFAULT '',
  openid_hash   CHAR(64)     NOT NULL,
  nickname      VARCHAR(64)  NOT NULL DEFAULT '',
  avatar        VARCHAR(512) NOT NULL DEFAULT '',
  max_level     INT          NOT NULL DEFAULT 0,
  total_time_ms BIGINT       NOT NULL DEFAULT 0,
  total_steps   INT          NOT NULL DEFAULT 0,
  unlocked_skins JSON        NOT NULL,
  ad_watch_cnt  INT          NOT NULL DEFAULT 0,
  created_at    DATETIME     NOT NULL,
  last_login_at DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_openid_hash (openid_hash),
  KEY idx_max_level (max_level)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 字段说明

| 字段 | 说明 |
|---|---|
| `openid` | **AES-GCM 密文**（密钥 = SHA256(appid+secret)），不存明文 |
| `openid_hash` | SHA256(openid) 的 base64url，唯一索引。查用户靠它，不用解密 |
| `max_level` | 最高通关关卡。**跳过的关卡也推进**（否则玩家卡死） |
| `total_time_ms` | 累计用时。**仅首次通关累加**（防重复提交刷数值） |
| `total_steps` | 累计步数，同上 |
| `unlocked_skins` | JSON 数组，如 `["wood","mint","marble"]` |
| `ad_watch_cnt` | 累计完整看完的广告次数（用于风控与收益核算） |

### 索引
- `uk_openid_hash`：登录查用户的唯一路径
- `idx_max_level`：总榜重建时按关卡数排序（可选，量大后再加）

## 3. level_records

```sql
CREATE TABLE level_records (
  uid        BIGINT UNSIGNED NOT NULL,
  level_idx  INT          NOT NULL,
  steps      INT          NOT NULL,
  time_ms    INT          NOT NULL,
  path       JSON         NOT NULL,
  skipped    TINYINT(1)   NOT NULL DEFAULT 0,
  created_at DATETIME     NOT NULL,
  PRIMARY KEY (uid, level_idx),
  KEY idx_level (level_idx),
  KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 设计要点

- **主键 `(uid, level_idx)`** → 一人一关一条，天然幂等。重复提交走 upsert，保留更优记录
- **`path` 存完整路径** → 用途：
  1. 防作弊复核（管理员可回放验证）
  2. 事后分析「玩家在哪些格子最常卡住」
  3. 未来做"回放"功能
- **`skipped=1`** → 该关是看广告跳过的，**不发放该关皮肤**
- **`idx_level`** → 统计每关的通过人数（"全区已有 X 人玩过第 N 关"）

### 保留策略
- 路径 JSON 平均约 200 字节/行。1000 万用户 × 1000 关 = 100 亿行 → **必须分区或冷热分离**
- **建议**：`created_at` 按月分区，或超过 90 天的记录只留 `(uid, level_idx, steps, time_ms)`，把 `path` 移到归档表

## 4. friends

```sql
CREATE TABLE friends (
  uid        BIGINT UNSIGNED NOT NULL,
  friend_uid BIGINT UNSIGNED NOT NULL,
  status     TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (uid, friend_uid),
  KEY idx_uid_status (uid, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### status
| 值 | 含义 |
|---|---|
| 0 | pending（已申请，待同意） |
| 1 | accepted（互为好友） |
| 2 | blocked（已拉黑） |

### 双向存两行
- A 申请 B → 写入 `(A,B,pending)` 和 `(B,A,pending)`
- B 同意 → 两行都改 `accepted`
- 好处：查询「我的好友」和「谁加了我」都是单表索引扫描，不用 UNION

### 与开放数据域的关系
- **开放数据域**（微信）：拿得到真正的微信好友关系，零成本，用于**好友榜**
- **服务端 friends 表**：自维护，用于**申请/同意/拉黑/助力记录**，Steam 版可复用
- 两者**好友列表不一定一致** → 好友页同时展示：开放数据域画榜，服务端算统计

## 5. scores

```sql
CREATE TABLE scores (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  uid        BIGINT UNSIGNED NOT NULL,
  level_idx  INT    NOT NULL,
  steps      INT    NOT NULL,
  time_ms    INT    NOT NULL,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY idx_uid (uid),
  KEY idx_created (created_at),
  KEY idx_level_steps (level_idx, steps)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 用途
- **只增不改** → 每次通关/挑战写一条流水
- 与 `level_records` 的区别：`level_records` 是「每关最优」，`scores` 是「历史流水」
- `idx_level_steps` → 查某关的历史最佳（挑战结算用）
- 用途：流失热力图、难度回归验证、玩家行为分析

## 6. skips

```sql
CREATE TABLE skips (
  uid        BIGINT UNSIGNED NOT NULL,
  level_idx  INT          NOT NULL,
  day        VARCHAR(10)  NOT NULL,
  PRIMARY KEY (uid, level_idx, day)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- 主键含 `day` → 每天每关只能有一条
- 服务端用 `INSERT IGNORE` 幂等写入，RowsAffected=0 即"今日已跳过"
- 客户端也存一份本地标记做快速预检（服务端仍会校验）

## 7. events（埋点）

```sql
CREATE TABLE events (
  id     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  uid    BIGINT UNSIGNED NOT NULL DEFAULT 0,
  name   VARCHAR(64) NOT NULL,
  params JSON NOT NULL,
  ts     DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY idx_name_ts (name, ts),
  KEY idx_uid (uid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 事件清单
见 `05-商业化与埋点.md` 第 6.1 节（22 个事件）。

### 清理策略
```sql
-- 保留 90 天
DELETE FROM events WHERE ts < DATE_SUB(NOW(), INTERVAL 90 DAY) LIMIT 10000;
```
加到每日 cron。

## 8. 关卡表（只读，不在 MySQL）

```
server/data/levels.json      公开，会下发给客户端
server/data/solutions.json   私密，仅服务端
```

**为什么不进 MySQL**
- 1000 关 × 95 字节 ≈ 95KB → 一次读进内存即可
- 只读、版本化、随代码发布 → 走 `go:embed` 或磁盘加载
- **不进数据库** → 避免每次查询都解码 base64

**版本一致性**
- `levels.json` 与 `solutions.json` 带同一个 `version`（内容哈希前 12 位）
- 服务端启动时校验两者版本一致 + 抽检 50 关 → 不一致**拒绝启动**

## 9. 关系图

```
users (1) ──┬── (N) level_records   [uid, level_idx]
             ├── (N) scores           [uid]
             ├── (N) skips            [uid, level_idx, day]
             ├── (N) events           [uid]
             └── (N) friends          [uid] ── (N) friends [friend_uid] ── (1) users
```

## 10. 容量估算（1 万用户）

| 表 | 行数 | 单行 | 总量 |
|---|---|---|---|
| users | 10,000 | ~300B | 3 MB |
| level_records | 10,000 × 30 关 = 300,000 | ~250B | 75 MB |
| scores | 10,000 × 30 = 300,000 | ~60B | 18 MB |
| events | 10,000 × 300 = 3,000,000 | ~120B | 360 MB |
| friends | 10,000 × 10 = 100,000 | ~50B | 5 MB |

**结论**：1 万用户约 460MB，2C4G 完全够。**events 表增长最快** → 必须有清理策略。

## 11. 迁移注意事项

- **DSN 必须带 `multiStatements=true`** → 否则 `db.Exec` 执行多语句 SQL 会失败
- **字符集 `utf8mb4`** → 昵称可能有 emoji
- **`loc=Local`** → 否则时区错乱
- **`parseTime=true`** → 否则 `DATETIME` 扫不进 `time.Time`
- 迁移按文件名顺序执行，**不重复执行**（用 `CREATE TABLE IF NOT EXISTS`）
