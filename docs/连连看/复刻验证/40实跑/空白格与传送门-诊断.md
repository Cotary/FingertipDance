# 空白格与传送门：诊断结论

> 2026-11-19 · 针对「空白格 vs 石障」「传送门没生效」两个问题的排查结果

---

## 一、空白格和石障：数据里确实是两种，不是 bug

### 结论

**服务器下发的数据里，`VOID` 和 `BLOCK` 是两种真实存在的类型。**

| 类型 | 含义 | 全表数量 |
|---|---|---|
| `VOID`（0） | **缺口** —— 不可走，且**与盘外连通**（露出底板） | 2676 |
| `BLOCK`（2） | **石头** —— 不可走，但**被可走格完全包围**（盘内障碍） | 2128 |

- 含 VOID 的关：755
- 含 BLOCK 的关：728
- **两者都有的关：483**

### 判定规则（`generate.ts` 的 `classifyObstacles`）

```
不可走格 → 从它出发，在"被挖掉的格"内部泛洪
  ├─ 能碰到盘边界 → VOID（缺口，盘外连着）
  └─ 碰不到边界   → BLOCK（石头，盘内孤岛）
```

这是 v3 相对 v2 的修正：v2 用「四邻全是可走格才判 BLOCK」，导致 2×2 及以上的洞永远被判成 VOID
（实测全表只有 38 个 BLOCK、27766 个 VOID，盘内可见障碍根本没落地）。

### 渲染现状

- `BLOCK` → 画石头（`drawStone` / `drawRock`），**有明确外观**
- `VOID` → `kit.ts` 里 `if (type === VOID) continue`，**什么都不画，露出底板**

所以看到的大片空白就是 VOID —— **这个行为符合设计**（缺口本来就该露出底板，让盘外轮廓不规则）。

> 用户确认：**不用改，现在就是对的。**

### 诊断工具

```bash
node tools/diag-cells.mjs
```

直接统计服务端表里各类型格的数量、含 VOID/BLOCK 的关卡数、样例布局。

## 二、传送门没生效：规则层实现了，但被"拖动采样"吃掉了

### 现象

> 「通过传送门没有生效，而是当成一般的格子直接通过了，应该从 a 进、从 b 出」

### 排查过程（逐层排除）

| 层 | 状态 |
|---|---|
| 数据层 | ✅ 252 关全部配对正确（每关正好 2 格、同 group、`portalOf` 互指） |
| 规则层 | ✅ `candidateMoves` 里有 `viaPortal` 的边；`test/cover-portal.test.ts` 7 个用例全过 |
| 状态层 | ✅ `tryCoverMove` 里有「站上传送门 → 拖到搭档 → 传送」的分支，且**优先于相邻判断** |
| 输入层 | ❌ **问题在这里** |

### 根因：拖动时指针会先"吃掉"中间格

以关卡 153 为例（5×6）：

```
(2,0) 传送门 A    (3,0) 普通格    (4,0) 传送门 B
```

玩家从 A 往右拖到 B：

1. 指针采样**先进入 (3,0)** → `pointerMove` 调 `tryCoverMove(state, mid)`；
   这一步是合法的普通移动，**路径立刻变成 A → (3,0)**；
2. 指针再落到 B → 此时线头是 (3,0) 而**不是**传送门，
   `if (r.typeOf[last] === PORTAL)` 不成立 → 走相邻分支。

**结果：看起来"从传送门旁边走过去了"，传送边一次都没用上。**

### 但改成"强制传送"会撞上一个数学矛盾

用户选择了「进 A 立即出 B」（强制）。实现后发现：

**cover 模式是哈密顿路径 —— 解必须铺满全盘。**

实测关卡 153：`可走格 = 26`，`解步数 = 26`，**严格铺满**。
所以：

- 盘上**没有空闲格**可以放"路外的传送门"（试过：`offPathCells` 恒为 0，1000 关一个都没生成）
- 只能取"解路径上相邻的两格"做传送门
- 但哈密顿路径**每一步都是四邻移动**，所以相邻两格**必然几何相邻**（实测 5030 步全部如此）
- 几何相邻的传送门 = 传送和普通走一步没区别，**玩家看不出来**（实测 252 关全是这种退化情况）

**结论：铺满全盘（哈密顿）与"传送跳得远"（需要留空格）在数学上互斥。**

### 三条可选路线

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 保持可选边，修好拖拽**（推荐） | 不改数据。让"指针最终落在搭档上"能触发传送：站上传送门后，指针划过中间格不生效，直到落在搭档或离开传送门 | 小。252 关参考解全部保持有效 |
| **B. 允许不铺满** | 把 cover 的"铺满全盘"改成"覆盖 N 格"，留出空格放远距离传送门 | 大。1000 关的难度曲线、验收门禁、求解器都要重做 |
| **C. 强制传送 + 退化传送门** | 传送门只能相邻（看不出效果），但规则成立、回放通过 | 中。实测可行（0 关失败），但玩家感知不到"传送" |

### 诊断工具

```bash
node tools/diag-portal.mjs
```

统计：含传送门的关卡数、每组传送门格数、配对是否成立、以及几何距离分布。

## 四、建议

如果目标是「传送门要能看见效果」，推荐**路线 A**：

只改 `coverState.ts` 一处 —— 站上传送门时，若指针还没落到搭档，
**忽略中间格的移动**（返回 `same`），直到指针落到搭档或离开。

这样：
- 不改关卡数据，252 关全部保持有效
- 玩家从 A 拖向 B 时，中间格不会被吃掉
- 传送门可以隔着整片盘（数据里本来就有远距离配对）

要真正做"强制传送 + 远距离"，必须先改 cover 的核心玩法（允许不铺满），
那是另一个量级的改动。
