# 40 文档流程实跑报告（2026-11-19）

> 按 40 文档的 S0→S4 流程，把两套设计稿（秘色天青 / 鸣沙丹青）真跑了一遍。
> 结论：**流程可行，闸门有效，并且立刻抓出了 6 个真实 bug。**

---

## 一、跑通了什么

### 补齐了 40 文档指出的最大缺口：游戏侧出图

40 文档 §S4 说「裁判就位、选手没上场」。这次把选手接上了：

| 新增 | 作用 |
|---|---|
| `games/line/tools/design-replica/core.ts` | 按 manifest 口径画单格（跳过展柜底板） |
| `shoot.html` | 出图页，URL 参数驱动，不启动游戏主循环 |
| `shoot.mjs` | 批量出图，两套主题 × 16 种状态 |
| `side.mjs` / `measure.mjs` | 并排图与包围盒测量（定位偏差用） |

### 基线扩展到两套主题

`baseline.mjs` 改成多稿模式：每套主题用自己的选择器，文件名带主题前缀。

```
baseline/
  mise__tile.pale.png          mise__tile.deep.png       …
  mingsha__tile.pale.png       mingsha__tile.deep.png    …
```

**两套主题的 id 一致**（`tile.pale` 都指"未铺普通格"），这样出图台和闸门可以复用同一套逻辑。

## 二、闸门抓出的 6 个真实 bug

**全部是靠数据发现的，没有一个能靠肉眼立刻看出。**

| # | Bug | 发现方式 | 修法 |
|---|---|---|---|
| 1 | `theme.board()` 会画整块展柜底板，而设计稿的单格元素**没有底板** | 出图后看到深色卡面 | 加 `cellsOnly` 开关 |
| 2 | 出图**没按 manifest 尺寸**，全按 62px 硬编码 | 第一道就报「尺寸不一致」 | 从 manifest 读 `box` 与 `pad` |
| 3 | 截图 DPR 用 1，基线用 3 → 差 3 倍 | 尺寸 188 vs 564 | shoot.mjs 改 DPR 3 |
| 4 | 锚点按"左上角对齐"，棋子偏右下 **44px** | 包围盒对比 | 改成"棋子中心对画布中心" |
| 5 | 裁切半径按槽位算，**切掉了投影** | 包围盒 232 vs 260 | 按「棋子 + shadowPad」算 |
| 6 | 格内纹样由 `motifOf(gx,gy)` 轮换，(3,3) 拿到第 6 品而非 moon | 并排图看到字形完全不同 | 用 (0,0) 拿 moon |

### 最有价值的一条：位置偏 44px

修好尺寸后，**均值 Δ 只从 55 降到 35**。看起来像"画法不对"，但测量包围盒发现：

```
设计稿本体：从 (186,186) 开始，192×201
我们  本体：从 (230,230) 开始，191×191    ← 偏了 44px
```

**根因是锚点**：槽位比棋子大 14px，按"左上角对齐"会让棋子在框内偏右下。
改成"棋子中心对画布中心"后，两图都从 (186,186) 起 —— **均值 Δ 从 35 降到 11.9**。

> 这条说明：**只看均值找不到病因，必须看包围盒**。
> 40 文档的闸门输出「坐标 + RGB」，但那是"哪一点差"，
> 还需要一个「整体偏了多少」的测量 —— 这次补上了 `measure.mjs`。

## 三、当前真实偏差

### 天青（mise）：11.2 ~ 91.9，平均 24.1

| 元素 | 均值 Δ | 判定 |
|---|---|---|
| tile.stone | 11.23 | 位置尺寸全对，差在阴影层次 |
| tile.pale | 11.24 | 同上 |
| tile.pale.key / oneway / portal | 11.3-13.1 | 机制标颜色微差 |
| tile.deep | 13.28 | 金边偏粗 |
| tile.pale.start / end | 18.7 / 24.3 | 端点标记画法不同 |
| tile.pale.trail | 32.99 | 路径高亮层 |
| tile.pale.pressed | 36.63 | 按下态（缩放 + 描边） |
| tile.frost | 44.09 | **偏白、偏实**（设计稿是半透明淡蓝） |
| tile.pale.arrive | 91.86 | 爆闪态，出图未传 `wonAt` |

**关键进展**：基础格从 Δ 55-76 降到 **11-13**。

**剩余 11 的来源**（测量确认）：
- 位置、宽度完全一致（都是 (186,186) 起、192 宽）
- **高度差 9px**：设计稿 201，我们 192 —— 底部投影少一层

### 丹青（mingsha）：48.8 ~ 104.2，平均 73.7

**这是真正的问题区。** 颜色系统性错误：

| 元素 | 设计稿 | 我们（修前） |
|---|---|---|
| tile.pale | 石绿 `#6E9580` | **米黄** |
| tile.deep | 朱砂 `#B5472E` | 偏亮橙红 |
| tile.frost | 石青 `#6E93AE` | 偏艳蓝 |
| tile.stone | 赭石 | 偏橙，且**多画了纹理** |

**根因（已定位并修了一部分）**：`mingsha.ts` 的 `PASTES[0]`（未铺）写的是 `#ECDCB8` 淡土黄，
而设计稿裸 `.mp` 明确是 `#6E9580` 石绿。

> 关键发现：`#ECDCB8` 对应的是设计稿 **`.mp.pale`** —— 那个 class 只用于
> **机制格**（起点/终点/按下/线头/钥匙/门），是那些格子底下的"纸面"。
> **这是把两个 class 的色值挂反了。**

## 三b、已修的两处（本轮实际改动）

### 修 1：`PASTES[0]` 与 `PASTES[1]` 对调

```diff
- // 0 · 未铺：淡土块
- { ramp: ['#ECDCB8', '#DAC59A', '#C6AC80'], … }
- // 1 · 石绿
- { ramp: ['#7BA089', '#56786A', '#456055'], … }
+ // 0 · 未铺普通格 = 石绿（设计稿裸 .mp）
+ { ramp: ['#6E9580', '#56786A', '#456055'], … }
+ // 1 · 机制格的"纸面" = 淡土黄（设计稿 .mp.pale）
+ { ramp: ['#E8D6B0', '#D2BC8E', '#BFA176'], … }
```

**效果**：`mingsha__tile.pale` 均值 Δ **104.2 → 49.07**（改善 53%）。

### 修 2：机制格改用 `PASTES[1]`

机制格（START/END/ONEWAY/SHARD/KEY/GATE）在未铺状态下本该是淡土黄"纸面"，
而不是石绿空墙。新增 `MECH_CELLS` 判断。

**效果**：`tile.pale.start` **89.4 → 77.0**，`end` 85.5 → 68.5。

> 但这两项仍偏高。并排图显示：**色相已经对了，尺寸仍偏大 17.5%**
> （设计稿本体 160 物理像素，我们 188）。
> 这是下一个要查的点，见「剩余问题」。

### 剩余问题：丹青格子偏大

| | 设计稿 | 我们 |
|---|---|---|
| 起点坐标 | (46,46) | (47,47) ✓ 对上了 |
| 本体宽度 | **160** | **188** |
| 换算逻辑 | 53.3 | 62.7 |

天青本体实测 192（= 64×3），是对的。
丹青同样 `s = cell - 14 = 62`，但设计稿的丹青格实际渲染是 **53.3**。

> 设计稿 `.mp` 的 CSS 是 `width:64px`，但多处覆盖（54/56/64）叠加后
> 实际渲染出了 53.3 —— 这说明 `.mp` 在真实上下文里被另一条规则压到了 54。
> **需要进一步找出是哪条规则**，或者接受"丹青的格子本来就比天青小一档"，
> 在引擎里给 mingsha 单独的 `cell` 比例。

## 四、流程本身的验证结论

### 有效的地方

1. **闸门能拦住"看起来差不多"**。修锚点前后，肉眼几乎看不出差别（都是"一颗青瓷棋子"），但均值 Δ 从 35 → 11.9 精确反映了改进。
2. **包围盒测量补齐了闸门的盲区**。均值只告诉"差多少"，包围盒告诉"偏哪儿"。
3. **尺寸/DPR/pad 必须单点定义**。这次 3 个 bug（#2 #3 #5）全是"两边各算各的"。

### 不够的地方（40 文档已预警，这次被证实）

1. **G3 布局闸门确实没有工具**。位置偏 44px 这种错，40 文档说"没有工具只能人眼看" —— 实际靠 `measure.mjs` 临时补的。
   **应该把包围盒测量固化进 baseline.mjs**，作为独立的「几何闸门」。
2. **`verify.mjs`（自比对）依然只能证明"烘焙=真值"**，证明不了"我们的画对不对"。这次是 `shots vs baseline` 才暴露问题。

## 七、一句话结论

**40 文档的流程是对的，而且第一次真跑就抓出 6 个 bug。**

天青从"对不上"推进到 **Δ 11-13（基础格）**，靠的是三件事：
按 manifest 出图、中心对齐、正确裁切。

丹青仍差得远（Δ 48-104），但**病因已经明确**：
`mingsha.ts` 把 `.mp` 和 `.mp.pale` 的色值搞混了 —— 这是改一个常量就能解决的事，
不是"复刻能力不够"。

> **这正是 40 文档想证明的**：复刻的难点不在"画得像"，在"说清楚差在哪"。
> 闸门给出的不是分数，是待修清单。
