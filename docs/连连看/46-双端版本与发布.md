# 46 · 双端版本与发布：一套代码，两个包

> 2026-11-23。回答一个问题：**微信和抖音都要上，代码该怎么分配？要不要开分支？**
>
> 结论先给：**不要按平台开分支。单主干 + 构建目标分离 + 按端打 tag。**

---

## 一、为什么不能按平台开分支

「微信一个分支、抖音一个分支」看起来最直观，但它把**平台差异**和**业务演进**放进了同一个维度。
这个项目的实际形态是：95% 的代码是共用的（关卡、渲染、会话、服务端协议），
差异只有三处 —— 平台能力实现、构建期常量、工程脚手架。

按平台拉分支之后，会依次出现这四件事：

1. **每个 bug 都要修两遍。** 棋盘手感、埋点、结算逻辑改一次，另一个分支没有。
   漏一次就是「微信修好了、抖音还是旧 bug」，而线上没人会主动去核对另一端。
2. **平台差异会漂移。** 微信分支的 `platform/wechat.ts` 改了接口签名，抖音分支
   的 `douyin.ts` 还按老的写 —— 两边都编译通过（各自只 import 自己那一半），
   合并时才发现对不上。
3. **服务端和关卡表没法原子发布。** 关卡表、`platform_config`、`users` 表结构
   是两端共用的。代码分两个分支，数据只有一套，改表那天必然一端先坏。
4. **合并成本随天数指数上升。** 两个分支都在动 `main.ts`（这是全仓最长的文件），
   三天不合并，diff 就是几千行。

> 这不是理论。这个项目已经踩过一次同类问题：`main.ts` 里只读 `wx.onTouchStart`，
> 抖音端**整个触摸是断的**，而微信端一切正常 —— 单分支都已经这么容易漏，
> 双分支只会把这个概率乘以二。

## 二、那什么放哪里：一张分配表

| 东西 | 放哪 | 是否按平台分叉 |
|---|---|---|
| 业务逻辑（关卡/会话/渲染/结算/埋点） | `games/line/src/**` | ❌ 一份 |
| 平台能力（登录/请求/广告/分享/触摸/存储/音频/画布） | `games/line/src/platform/{wechat,douyin,web}.ts` | ✅ 各自实现同一接口 |
| 平台选择 | `platform/index.ts` 的 `__TARGET__` 三元 | 构建期决定，**不手动改** |
| 构建目标 | `vite build --mode wx` / `--mode douyin` | ✅ 两条 npm script |
| 工程脚手架（appid、game.json、入口） | `games/line-wx/`、`games/line-dy/` | ✅ 两个目录 |
| 服务端 | `server/`（单套） | ❌ 一份，`users.platform` 区分 |
| 平台配置（广告位/分享前缀/频控） | `platform_config` 表，按 `platform` 行 | ✅ 数据行，不是代码分支 |
| 资质与素材（图标/截图/宣传图） | `assets/release/{wx,dy}/`（建议） | ✅ 目录分开 |
| 版本标记 | git tag `wx-vX.Y.Z` / `dy-vX.Y.Z` | ✅ 互相独立 |

**判断标准只有一条**：这段代码如果两端都跑，就必须只有一份；
只有「调用的平台 API 不同」时才允许分叉，而分叉必须发生在 `src/platform/` 里。

### 差异矩阵（现有能力，代码里怎么表达）

| 能力 | 微信 | 抖音 | 表达方式 |
|---|---|---|---|
| 分享通道 | 好友 + 朋友圈 | 好友 + 抖音 | `platform.shareChannels`，UI 只画报上来的 |
| 好友榜 | 开放数据域 | 无 | `platform.openDataAvailable` |
| 隐私授权 | 强制 | 无 | `platform.privacy?` 可选，缺失即放行 |
| 启动参数 | `wx.getLaunchOptionsSync` | `tt.getLaunchOptionsSync` | `platform.launchQuery()` |
| 触摸 | `wx.onTouch*` | `tt.onTouch*` | `platform.onTouch()` |
| 录屏 | 有 | 有（强推） | 未接（见 44 · D2） |

## 三、发布流程：tag 是版本，不是分支

两端**审核节奏天然不同**（微信 1~7 天，抖音 1~3 天，驳回要重来）。
所以不要追求「同时上线」，要追求**同一个 commit 出两个包**。

```bash
# 1. 门禁（一个命令跑完 typecheck + 631 条测试 + 双端产物断言）
cd games/line
npm run release:check

# 2. 用生产地址重新构建两端，并检查产物
API_BASE=https://api.your-domain.com npm run verify:targets:build

# 3. 打 tag：指向同一个 commit，先发哪个就先打哪个
git tag wx-v1.0.0
git tag dy-v1.0.0

# 4. 上传
#    微信开发者工具打开 games/line-wx → 上传 → 后台提审
#    抖音开发者工具打开 games/line-dy → 上传 → 提审
```

**tag 命名**：`wx-v1.2.0` / `dy-v1.2.0`。不要用 `release/wx-1.2`（带斜杠容易和分支混淆）。

**两端版本号可以不同步**：微信驳回两次、抖音已经过了 1.2.0 是常态，
`dy-v1.2.1` 早于 `wx-v1.2.0` 完全正常 —— tag 本来就是独立的。
代码里不需要写死版本号，小游戏后台的版本号才是提审看到的那个。

**回滚**：重新上传旧 tag 的产物（不是 `git revert`）。所以**每次上传的包要从
干净 tag 构建**，不要从工作区直接传 —— 工作区里可能带着下一版的半成品。

## 四、什么时候该开分支

只有一种情况：**某一端被驳回，且修法会让另一端也跟着重新提审**。

```bash
git checkout -b hotfix/wx-1.0.1 wx-v1.0.0
# 改文案 / 改类目相关的表述
git commit -m "fix(wx): 提审文案去掉'无限'字样"
# 上传微信包，提审通过后
git checkout main && git cherry-pick <sha>
```

规矩：

- 分支名带平台与版本（`hotfix/wx-1.0.1`），**不叫 `wechat`**；
- 生命周期按天算，合回 `main` 后立刻删除；
- 合回后给抖音也打一个新 tag（同一个修复，抖音下一版自动带上）；
- 如果修法只影响微信（比如 `game.json` 字段），**连分支都不用开** ——
  直接在 `main` 上改，因为 `games/line-wx/` 本来就只属于微信。

## 五、机械门禁：别靠人记

`games/line/scripts/verify-targets.mjs` 做的是「人眼看不见的那部分」：

| 断言 | 为什么 |
|---|---|
| 微信包 `tt.` = 0、抖音包 `wx.` = 0 | 平台代码漏进对面包，构建照样成功、开发者工具照样跑 |
| 两端无 `127.0.0.1` | 构建期地址漏注入，线上登录静默失败 |
| 微信 `game.json` 有 `openDataContext` / `__usePrivacyCheck__` | 少一行，好友榜全黑 / 隐私从不弹窗，都不报错 |
| 两端都有 `onTouchStart` | 触摸缺失时「点了没反应」，零日志 |
| 主包 < 4MB | 微信主包上限，超了上传直接失败 |
| appid 非占位 | 占位能预览，**不能上传**（WARN，不拦本地开发） |

CI 至少要跑 `npm run release:check`，tag 上再加 `verify:targets:build`。
现在仓库还没有 CI（`.github/workflows` 不存在），这是**下一个该补的东西**。

## 六、当前仓库的两处小债 ✅ 已处理（2026-11-23）

1. **构建会弄脏工作区**：`copy-wx-assets.mjs` / `copy-dy-assets.mjs` 每次都重写
   `game.json`、`openDataContext/index.js`、`game.js`，内容没变也让 `git status` 变脏，
   发布 commit 容易夹带无关改动。
   → 已改成「内容相同就不写盘」。实测双端构建前后，6 个脚手架文件 md5 全部一致。
2. **发布前没有 CI**：门禁脚本能跑，但没人强制跑。
   → 已加 `.github/workflows/ci.yml`：前端 `typecheck` + 631 条单测、
   双端构建 + 产物断言、服务端 `build` + `vet`。
   （服务端全量测试要连库，CI 里没起 Postgres，所以只做编译与静态检查。）
