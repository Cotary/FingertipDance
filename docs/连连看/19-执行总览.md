## 三个核心设计决策（记住这三条就不会跑偏）

### 1. 生成器只有一份，在 TypeScript 侧

```
core/generator.ts + core/solver.ts  ← 唯一真相源
      ├─> Node CLI 批量生成 1000 关 → levels.json + solutions.json
      ├─> Go embed 进二进制 → /api/levels 分批下发
      └─> 客户端复用 solver 做「提示」
```

**Go 侧不实现求解器**。服务端校验成绩只查预存的 `shortest` + 朴素路径校验（约 50 行）。零重复实现、零漂移风险。

### 2. 关卡表版本化

`levels.json` 带内容哈希 → `/api/config` 下发 → 客户端缓存不一致就重拉 → **改表后全端自动对齐**。服务端启动时校验完整性，不一致**拒绝启动**。

### 3. UI 全 Canvas 绘制，零 DOM 零 CSS 零图片

为了微信移植零成本。美术全程序化（纹理用确定性噪声）。包体只有几十 KB。

## 数字速查

| 项 | 值 |
|---|---|
| 关卡数 | 1000 |
| 单关体积 | ~95 字节（base64 紧凑编码） |
| 关卡表总体积 | ~95KB，gzip ~28KB |

| 纯通关时长 | 1000 × 60 秒 ≈ 16 小时 |

| 后端接口数 | 9（T23 新增 `/api/progress/stars`） |
| PostgreSQL 表数 | 6（不变） |
| 棋盘尺寸 | 6×6 → 11×11 |
| 最大求解器状态数 | 121 格 × 4 方向 = 484 |
