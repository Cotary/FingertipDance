# 41 · 设计稿规范（面向 Canvas 运行时的设计）

> **这份文档是给设计侧的。**
> 目的：让设计稿从第一天起就**长成代码能落地、且能被自动验收的样子**，
> 从而把「设计稿 → 代码」这件事从「反复手工翻译 + 肉眼判断」变成「有闸门的工程」。
>
> 配套文档：**《42 · 设计稿到代码落地 SOP》**（给实现侧的完整流程）。
>
> 适用范围：微信小游戏 / 抖音小游戏等**无 DOM、仅 Canvas** 的运行时。

---

## 〇、为什么需要这份规范

### 0.1 问题的本质：两边不是同一种语言

设计稿用 **DOM + CSS**（声明式，浏览器算级联），代码用 **Canvas 2D**（命令式，每层手写）。
两边"表达一个视觉效果"的成本差一个数量级：

| | 写设计稿 | 写代码 |
|---|---|---|
| 一层阴影 | `box-shadow: 0 2px 8px #0003` （**1 行**） | 分层渐变 + 阴影色推导 + 层级管理（**若干行**） |
| 圆角 + 描边 | `border-radius` + `border` （**2 行**） | `roundRect` + `stroke` （**2 行**，等价 ✅） |
| 噪点纹理 | `filter: url(#noise)` （**1 行**） | 程序化噪点贴图（**几十行**） |

**结论：设计稿写得越"CSS 味"，翻译成本越高，且越高越难自动验收。**

### 0.2 三条铁律

> **铁律一：能 Canvas 表达的，绝不用 CSS 独占特性。**
> 优先用渐变 / 圆角 / 描边 / `opacity` / `globalCompositeOperation` —— 这些在 Canvas 里有**一一对应**的原生 API，翻译是"改名"而不是"重做"。
>
> **铁律二：一切数值必须是"可被机器读出"的。**
> 色值写成 `#hex` / `rgb()`（不要用颜色名、不要用 `color-mix`）；尺寸写成 `px`；
> 动效写成 `@keyframes`（不要只描述"弹一下"）。
>
> **铁律三：设计稿必须自带"状态清单"。**
> 每一个可视元素，都要能回答："它有哪些状态？每个状态长什么样？"
> ——这是后面能自动比对的前提。

### 0.3 这份规范不能做什么

**它不会让你设计得更好看。** 它只保证你设计出来的东西**能被落地、能被验收**。
视觉审美仍然是设计侧的事。

## 一、目标运行时的能力边界（写设计稿前必须知道）

### 1.1 微信小游戏 / 抖音小游戏

| 能力 | 支持 | 替代方案 | 保真度 |
|---|---|---|---|
| `linear-gradient` / `radial-gradient` | ✅ | — | **精确** |
| `border-radius` / `roundRect` | ✅ | — | **精确** |
| `border` / `stroke` / `line-width` | ✅ | — | **精确** |
| `opacity` / `rgba()` | ✅ | — | **精确** |
| `globalCompositeOperation: lighter` | ✅ 官方支持 | — | **精确** |
| `setLineDash` | ✅ | — | **精确** |
| `transform`（平移/缩放/旋转） | ✅ | — | **精确** |
| `box-shadow`（外/内/多层） | ⚠️ 文档支持，真机曾反馈失效 | **分层描边 + 渐变** | 近似 |
| `filter: blur()` | ❌ 真机未实现 | 多层径向渐变 | 近似 |
| `backdrop-filter`（毛玻璃） | ❌ | 用半透明色块 + 渐变模拟 | 近似 |
| `mix-blend-mode` | ❌ 未文档化 | `globalCompositeOperation` | 近似 |
| `clip-path` / `mask-image` | ❌ | `ctx.clip()` + 路径 | 近似 |
| CSS 3D（`perspective` / `rotateX`） | ❌ 无 3D 管线 | 分片仿射 / 降级 | 低 |
| SVG 直接渲染 | ❌ 官方明确不支持 | `Path2D` 重绘 / 光栅化 | 精确 |
| `feTurbulence` 噪点滤镜 | ❌ | 程序化噪点贴图 | 近似 |
| `@font-face` | ❌ | `wx.loadFont`（需打包 ttf） | 近似 |
| `letter-spacing` | ❌ | 逐字 `measureText` 定位 | 精确 |
| `position: sticky` / `vh` 单位 | ⚠️ | 固定尺寸 + 运行时计算 | 近似 |
| Web Audio 振荡器/滤波/包络/FM | ✅ `wx.createWebAudioContext` | — | 精确 |
| `PeriodicWave` / `WaveShaper` / `Delay` | ✅ | — | 精确 |
| **`ConvolverNode`（卷积混响）** | ❌ **不在官方 API 列表** | **FDN 混响（Delay+Biquad 反馈）** | 近似 |
| `navigator.vibrate(pattern)` | ❌ 只有 light/medium/heavy | 连续 `vibrateShort` + 定时器 | 近似 |
| 首包体积 | ❌ 主包 ≤ 4MB，总包 ≤ 30MB | 分包 / CDN | — |

### 1.2 一句话记法

> **"渐变 + 圆角 + 描边 + 透明度 + 混合模式" = 精确复刻区，可以大胆用。**
> **"滤镜 + 阴影 + 3D + 遮罩 + 毛玻璃" = 近似区，用之前先想清楚降级方案。**

### 1.3 首包预算（4MB 是硬墙）

| 项目 | 建议预算 | 说明 |
|---|---|---|
| 字体子集（4 字重） | 200–400 KB | 按设计稿实际汉字裁剪 |
| 贴图（烘焙 + WebP） | 1.5–2.5 MB | 用九宫格，别按尺寸各烘一张 |
| 代码 | 300–800 KB | Canvas 2D 程序化绘制很省 |
| 音频 | 50–150 KB | 若烘焙；用合成则近 0 |
| **合计** | **< 4 MB** | 留 10% 余量 |

> ⚠️ **实测教训**：`bake.mjs` 产出 27 张 PNG 共 **27MB**。
> 直接打包会撑爆首包。**必须过 `compress.mjs` 转 WebP**（实测 q0.8 保真可接受）。

## 二、设计稿写作规范

### 2.1 文件与结构

```
docs/<项目>/风格样片/
  YYYY-MM-DD-<主题名>-设计稿.html      ← 完整设计稿（唯一真相源）
  YYYY-MM-DD-<主题名>-音频稿.html       ← 动效 + 音效稿（可选，拆分便于审问）
  YYYY-MM-DD-<主题名>-基准图/           ← 基线图（由工具生成，不要手放）
```

**命名规则**：日期 + 中文主题名。日期用**设计定稿日**，不是创建日。
文件名会被工具链写进 `manifest.json`，改名等于换基线。

### 2.2 画布与坐标

| 项 | 规定 | 理由 |
|---|---|---|
| 设计基准宽 | **375 CSS px**（= 750 逻辑 px ÷ 2） | 与主流手机 1:1，截图即 1:1 |
| 设计基准高 | 812 px（iPhone X）或 **不限** | 长页面设计稿不设固定高 |
| 手机框外框 | 宽 375，高 812 | 用于在浏览器里预览 |
| 文档坐标系 | **文档左上角 = 页面原点**，不随手机框偏移 | 避免"两套坐标" |
| 手机框内边距 | 上下各留出状态栏区（44px） | 避开刘海/胶囊 |

> **关键**：**一个文档只有一个坐标系。** 手机框只是视觉容器，
> 任何元素的 `getBoundingClientRect()` 都以文档坐标为准。

### 2.3 命名与类名（**机器可读性是硬要求**）

设计稿里的类名就是**工具链的抓取锚点**。命名不规范 = 工具抓不到 = 无法自动比对。

```html
<!-- ✅ 好的：可预测、可枚举 -->
<div class="pc pale start"></div>        <!-- 棋子：材质 pale，状态 start -->
<div class="pc deep star"></div>          <!-- 棋子：材质 deep，状态 star -->
<div class="icon-card stone"></div>       <!-- 图标卡：stone -->
<div class="icon-stage"></div>            <!-- 图标舞台（截图区域）</div>

<!-- ❌ 坏的：抓不到，或抓错 -->
<div class="box-1"></div>
<div class="redTile"></div>               <!-- 材质名用颜色，违反"抽掉颜色也要成立" -->
```

**规则**：

1. **棋子统一用 `.pc`**（piece），后接材质类和状态类：`pc <material> [<state>]`。
2. **状态类必须是固定词表**：`default / start / end / trail / pressed / hint /
   oneway / key / door / door-open / portalA / portalB / arrive / star / frost / stone`。
   **新增状态必须同时更新工具的 `TARGETS` 清单。**
   **词表里的每个状态，设计稿里都要有对应的一行元素** —— 见 §3.1 的棋子矩阵。
3. **截图区必须有独立容器**（`.icon-stage`），因为截图是按容器 `clip` 的。
4. **禁止用颜色命名**（`.redTile`）。命名要表达**语义/材质/状态**，
   颜色写在 CSS 里 —— 这样"把颜色抽掉只看灰度"仍能认出是哪一套。

### 2.3b 图标要「几何 + 笔触」分离，不要画成死图

> **这一条决定了状态会不会爆炸。**
> 若每个图标状态都画成一张成品图，9 类机制 × N 套主题 × 几个状态 = 几百张图。
> 若拆成「几何 + 笔触」，就是 `9 + N` 个零件，组合在运行时拼。

**设计稿里应该怎么组织**（这是设计侧能控制的部分）：

```html
<!-- ✅ 好的：几何用内联 SVG path 定义一次，笔触（材质）用 CSS 类切换 -->

<!-- ① 几何：一份 SVG，形状是「符号」不是「成品」 -->
<svg class="glyph-defs" width="0" height="0" aria-hidden="true">
  <defs>
    <symbol id="g-arrow" viewBox="0 0 24 24">
      <path d="M5 12 H15" />              <!-- 一根杆 -->
      <path d="M11 7 L17 12 L11 17" />   <!-- 一个折角 -->
    </symbol>
    <symbol id="g-gate" viewBox="0 0 24 24">
      <rect x="6" y="4" width="12" height="16" rx="2" />
    </symbol>
  </defs>
</svg>

<!-- ② 笔触：材质语言，用 class 切换；四个方向靠 transform 复用同一份 -->
<div class="glyph-stage glaze">
  <svg class="glyph" data-shape="g-arrow"><use href="#g-arrow" /></svg>
</div>
<div class="glyph-stage glaze" style="--rot:90deg">
  <svg class="glyph" data-shape="g-arrow"><use href="#g-arrow" /></svg>
</div>
```

**三条硬规则**：

| 规则 | 理由 | 引擎侧的对应 |
|---|---|---|
| **符号必须画成「符号」而不是「成品」** | 成品图无法换材质 | 几何表（`GLYPHS`） |
| **四向必须用 `transform` 复用同一份 path** | 设计稿自己用 `<g transform="rotate(90)">` 时，引擎侧也不该展开成四份 | `ctx.rotate(dir * π/2)` |
| **材质差异用 class，不用复制元素** | 复制元素 = 复制状态 | 笔触函数（`PAINTERS`） |

> **本项目的现成先例**：`glyphs.ts` 里有
> `GLYPHS`（9 类几何）+ `PAINTERS`（每套主题一个笔触函数），
> 组合数是 `9 + N` 而不是 `9 × N`。
> 注释原话：「改一条规则（比如『所有图标统一线宽』）要改 27 处」——
> 拆开之后只改 1 处。

**给设计侧的操作建议**：

1. **先画"符号层"**（每个机制一套 path），再画"材质层"（每套主题一组 class）。
2. **能用 class 切换的，绝不复制元素。**
3. **四向、缩放、旋转，一律用 `transform`。**
4. **同一形状的多个状态（如门闭/门开），用不同 `symbol` id 或不同 path，
   但放在同一张"几何清单"表里** —— 引擎侧会把它读成"变体"而不是"另一类机制"。

### 2.4 色值规范

```css
/* ✅ 全部可被机器读出、可直接抄进 Canvas fillStyle */
--c050: #96B4CC;
--ink:  rgba(14, 24, 21, 0.75);
--gold: #D4AF6A;

/* ❌ 这些都没法直接抄 */
--c050: color-mix(in srgb, #96B4CC 80%, black);
--c050: oklch(0.72 0.05 240);
--c050: #96b4cc;   /* 小写 hex 也能用，但全项目统一大写 */
```

**规则**：

| 规则 | 说明 |
|---|---|
| 只用 `#hex` / `rgb()` / `rgba()` | 这三者与 Canvas `fillStyle` **同一色彩空间**，照抄即一致 |
| 统一大写 hex | 便于字符串比对去重 |
| 色板放 `:root` 的 CSS 变量 | 工具从 `:root` 抽色板，也便于人工审阅 |
| **每个色值只允许一个定义处** | 禁止"看起来一样"的两处各写一遍 |
| 颜色要能被抽掉 | 主题判据：**灰度图下仍能认出是哪一套** |

> **常见坑**：`#96B4CC` 与 `#6E93AE` 肉眼极像但差 40+。
> **禁止"凭印象取色"**，一律从设计稿 CSS 变量里抄。

### 2.5 阴影规范（最容易翻车的地方）

CSS 阴影 = 浏览器合成器算的模糊；Canvas 要自己一层层叠。**叠的顺序错一步就系统性偏亮/偏暗。**

```css
/* ✅ 推荐：用「多层同向描边」代替模糊阴影 —— Canvas 能 1:1 复刻 */
box-shadow:
  0 2px 0 rgba(0,0,0,.28),      /* 底边：实体厚度 */
  0 4px 10px rgba(0,0,0,.18);   /* 近处投影：可接受的模糊 */

/* ⚠️ 谨慎：多层模糊阴影 */
box-shadow:
  0 1px 2px rgba(0,0,0,.3),
  0 2px 4px rgba(0,0,0,.25),
  0 4px 8px rgba(0,0,0,.2),
  0 8px 24px rgba(0,0,0,.15);
```

**规则**：

1. **阴影层数 ≤ 3 层。** 超过 3 层，Canvas 侧几乎必然叠错。
2. **优先"实体厚度"（0 偏移 + 不透明色）**，其次"柔光"（大半径 + 低 alpha）。
3. **`inset` 阴影要单独标注**（内阴影在 Canvas 需反转绘制方向）。
4. 每处阴影必须能回答：**方向 / 偏移 / 模糊 / 颜色**。回答不了就是设计侧没说清。

> 项目实测过的坑：整盘"系统性偏亮"= 渐变线长度算短 45% + `dim` 半径多乘 0.5。
> 这类 bug **肉眼完全看不出**，只有像素比对能抓。

### 2.6 噪点 / 颗粒规范

```css
/* ✅ 推荐：用一个可复用的 SVG 噪点定义 + data URI 引用 */
background-image: url("data:image/svg+xml,%3Csvg ...%3Cfilter id='n'%3E...%3C/filter%3E...");
```

**规则**：

1. 噪点必须是**固定种子的确定性伪随机**（`feTurbulence` 带 `baseFrequency` + `numOctaves`，
   或手写 LCG）。**不能是 `Math.random()`** —— 否则每次截图都不一样，
   基线图失去意义，工具链直接失效。
2. **一个设计稿只定义 1 个噪点**，多处复用（尺寸不同用 `background-size` 缩放）。
3. 记录 `baseFrequency` / `numOctaves` / `opacity` —— 这三个数就是 Canvas 侧
   程序化噪点的**标定目标**。

### 2.6b 分辨率：要不要出「超级大图」？

> **这一条回答一个很自然的问题**：
> 「手绘复刻的误差是不是因为图不够大/不够细？
>  让设计出 6 倍大的图，烘下来是不是就没锯齿了？」

**实测结论：部分成立，但不是你以为的那一半。**

用真值基线图做「降采样 k 倍再升回」，可以制造出**纯分辨率误差**，
再把误差分解成两个成分：

| 成分 | 含义 | 怎么来的 |
|---|---|---|
| **DC** | 系统性偏移（整体偏亮/偏暗/偏色） | 阴影层序错、渐变停靠点算错 |
| **HF** | 高频残差（锯齿、边缘毛刺、细节错） | 分辨率不足、模糊近似 |

**实测数据**（6 个元素平均）：

| 降采样 | mean | **DC** | **HF** |
|---|---|---|---|
| 1/3 | 3.07 | **0.47** | 3.03 |
| 1/2 | 2.11 | **0.21** | 2.09 |
| 1/4 | 3.47 | **0.39** | 3.44 |

**对照 doc 40 实测的手绘路线总误差：mean 5.29 / pct8 17.4%。**

**判读**：

1. **降采样的 DC 极小（0.21~0.47）** —— 说明重采样**只制造了锯齿/模糊**，
   没有制造系统性偏色。这符合预期，也证明这个分解方法是对的。
2. **HF 与 mean 几乎相等**（3.03 vs 3.07）—— 纯分辨率误差**几乎全是高频**。
3. **手绘的 5.29 明显高于同等分辨率下的重采样误差（1/3 时才 3.07）** ——
   说明**手绘的误差里有一块是重采样解释不了的**，那部分是**结构翻译错误**
   （阴影层序、模糊近似、停靠点算错），**大图救不了**。

**所以「大图」的真正价值是**：

| 目的 | 大图有用吗 | 说明 |
|---|---|---|
| 消除锯齿、毛边 | ✅ **有用** | 6× 烘 → 3× 输出的 2:1 下采样，边缘最干净 |
| 消除"手绘画得不像" | ❌ **没用** | 那是结构问题，要改画法或直接烘 |
| 支撑任意尺寸拉伸 | ✅ **有用** | 配合九宫格 |
| 支撑 3D 翻面等近似 | ⚠️ **有限** | 大图能让分片接缝更难察觉，但不解决形变 |

**给设计侧的三条结论**：

> **① 设计稿的"清晰度"已经够了 —— 不必为了清晰度去出超大图。**
> 浏览器渲染 CSS 本身就是抗锯齿的。**清晰度问题在烘焙倍率上解决，不在设计上解决。**
>
> **② 如果设计稿用了 `filter: blur()` / `feTurbulence` 这类"靠滤镜造质感"的手法，
> 那才是真正需要大图的场景** —— 因为滤镜效果与渲染分辨率相关。
> 这种情况：**大图 + 烘焙是唯一能保住质感的路**（并把噪点做成可平铺 tile）。
>
> **③ 但真正决定成败的是"状态画全了没有"（见 §2.3 与《42》§4.1.1），
> 不是"图够不够大"。** 一个只画了默认态的 6 倍大图，
> 复刻出来依然只有默认态 —— 而那正是"状态太多烘不过来"的真正原因。

### 2.7 动效规范

```css
/* ✅ 每个动效都必须有：时长 + 缓动函数 + 关键帧 */
@keyframes dropIn {
  0%   { transform: translateY(-18px) scale(.92); opacity: 0; }
  60%  { transform: translateY(2px)   scale(1.03); opacity: 1; }
  100% { transform: translateY(0)     scale(1);    opacity: 1; }
}
.dropIn { animation: dropIn 240ms cubic-bezier(.22,1,.36,1) both; }
```

**规则**：

1. **必须用 `@keyframes` 写死关键帧**，不能只描述"弹一下"。
2. **必须显式写 `cubic-bezier(...)`**。禁止 `ease` / `linear` 等关键字
   —— 关键字在不同浏览器实现不同，Canvas 侧无法反解。
3. **时长必须显式写**，且**音画同帧触发**的动效要在旁边注明音频事件名。
4. 一次性动效用 `both`（保留终态），避免首帧闪烁。
5. **循环动效**（呼吸、脉冲）单独标注 —— 它在 Canvas 侧每帧重画，成本不同。

> **每个动效都要在设计稿里写一行人话注释**，说明它在玩法里对应哪件事：
> ```html
> <!-- 落子：新砖从上方落入并回弹，对应 sfx('tap') -->
> ```

### 2.8 音频规范

**设计稿里的音效必须是 Web Audio 合成代码**（不是音频文件），
因为它是**可执行规格**——工具可以离线渲染出 PCM 当真值。

```javascript
/* 瓷轻叩 · Porcelain Tap
   配方：tri 2350/3170/4260 三重泛音 90ms + 4.2kHz 高通噪点
   时机：落子（与 dropIn 动效同帧）
   随机：频率微抖 ±5%（是瓷器相碰，不是机器冲压） */
function playTap(vol = 1) { ... }
```

**规则**：

| 项 | 要求 |
|---|---|
| **必须有配方注释** | 频率 / 波形 / 包络 / 时长，写在人能读懂的地方 |
| **必须声明触发时机** | 与哪个动效 / 哪个玩法事件同帧 |
| **随机性必须显式** | 用了 `Math.random()` 就写明范围；否则复刻方会漏掉 |
| **不要写 `ConvolverNode`** | 目标平台不支持（见 §1.1），需要空间感就用多谐波 + 延迟暗示 |
| **必须给"无混响"版本** | 设计稿的混响在 Canvas 侧要单独实现，先保证干声对齐 |

> **音频的复刻判据**（来自项目实测）：设计稿与实现**各自离线渲染**，
> 对齐起音点，比对**包络**（滑动窗 RMS）与峰值。
> 混响层不参与比对（平台近似不同），混响保真度单独用「衰减时间误差 ≤ 15%」评估。

### 2.9 震动规范

```javascript
/* 落子 · 瓷叩 —— 8ms */
vib([8]);
/* 铺满 · 玉磬 —— [15,30,15,30,25] 五拍节奏 */
vib([15, 30, 15, 30, 25]);
```

**规则**：

1. **震动必须是「事件 × pattern 数组」的表**，不要散落在代码里。
2. **pattern 数组是节奏**，不是"震一下"。**不许把多拍简化成单拍。**
3. 设计侧要知道：**微信端只有 light/medium/heavy 三档**，
   实现侧会降级成「连续短震 + 定时器拼节奏」。降级是实现侧的事，
   但**设计侧必须给每个事件一个明确的毫秒数**，否则无法降级。

### 2.10 字体规范

```css
@import url('https://fonts.googleapis.com/css2?family=Noto+Serif+SC:wght@400;600;700;900&display=swap');
:root { --serif: 'Noto Serif SC', serif; --sans: 'Noto Sans SC', sans-serif; }
```

**规则**：

1. **只用开源字体**（Noto Serif SC / Noto Sans SC）。
   商用字体在微信有授权风险。
2. **字重 ≤ 4 个**。每个字重都要进字体子集，4 字重 ≈ 400KB。
3. **必须用 `letter-spacing`** 表达排版语言（这是中文字体的气质来源），
   且**必须写具体数值**（`0.18em` 这种要能解析成 px）。
4. 工具会统计设计稿里**所有不重复汉字** → 那是字体子集的裁剪范围。
   **设计稿里不要出现生僻字**，否则子集会变大。

```markdown
## 4. 棋子矩阵（**必须画全，但可以「组合」着画**）

> ⚠️ **这一节打叉 = 整套主题无法通过 S0。**
> 「状态太多烘不过来」不是实现侧的困难，**是设计侧的交付缺陷**。
> 状态空间是**有限且可枚举**的：材质 × 机制态 × 方向 × 交互态。
>
> **但"画全"不等于"逐张画"。** 每个格子可以是：
> - **一张独立成品图**（外观与别的状态毫无关系）
> - **一个组合件**（几何 + 笔触 + class，运行时拼出来）—— 见 §2.3b
>
> **组合件不占出图量。** 这就是状态爆炸的解法。

### 4.1 机制态 × 材质（必填，**每格标明是「成品图」还是「组合件」**）

| 材质 \ 状态 | 默认 | 起点 | 终点 | 路径 | 按下 | 提示 | 单向 | 钥匙 | 门 | 门开 | 传送A | 传送B | 抵达 | 星屑 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 釉面 | 图 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 |
| 矿物 | 图 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 | 组 |

> **图** = 独立成品图（单独出一张）
> **组** = 组合件（几何 + 笔触 class 复用，**不出图**）
>
> 每格都要有对应的 CSS 类（如 `.pc.pale.door-open`）。
> **不适用**的格子写 `-` 并在备注说明原因，**不许留空**。

### 4.2 方向维度（**只对有朝向的元素**）

| 元素 | 有方向吗 | 上 | 右 | 下 | 左 | 处理方式 |
|---|---|---|---|---|---|---|
| 单向块箭头 | ✅ | 组 | 组 | 组 | 组 | **画一张 + 声明旋转**（`transform: rotate(90deg)`） |
| 起点 | ❌ | - | - | - | - | — |
| 终点 | ❌ | - | - | - | - | — |
| 路径块 | ❌ | - | - | - | - | — |

**处理方式三选一**（在设计说明里写明）：
1. **画四张** —— 外观本身随方向改变（非对称装饰）
2. **画一张 + 声明旋转** —— 外观旋转对称，实现侧 `ctx.rotate()`（**推荐**，省 3 倍图）
3. **画一张 + 声明无方向** —— 该元素无方向语义

> ⚠️ **注意**：只有当元素**旋转对称**时才能用方案 2。
> 若外观有方向性装饰（如箭羽），必须方案 1 —— 或者**把装饰拆成独立层**，
> 装饰层再单独做四向（见 §2.3b 的「装饰层」）。

### 4.3 交互态（**每个可点元素**）

| 元素 | 常态 | 按下 | 选中 | 禁用 |
|---|---|---|---|---|
| 按钮 | 图 | 图 | - | 图 |
| 棋子 | 图 | 组 | 组 | - |
| 皮肤卡 | 图 | 组 | 组 | 组 |

> **"按下"必须有** —— 项目实测踩过的坑：
> 设计稿的按压反馈是**三件事同帧**（棋子下沉到 0.94 / 金环扩散 / 瓷轻叩），
> 三者错开 50ms 就散。只画了常态，这三件事一个都实现不出来。
>
> **按下的实现方式**：多数情况下"按下"是**位移 + 变暗**，
> 不需要单独出图 —— 引擎侧在常态图上叠一层即可。
> **只有当按下态换了形状或换了材质**（如从"釉面"变成"生釉"）才需要单独出图。

## 5. 机制件六件套
每类机制件写：几何规则 + 配色 + 状态表 + 一句话语义

## 6. 动效表
| 事件 | 时长 | 缓动 | 关键帧描述 | 同帧音效 |
|---|---|---|---|---|

## 7. 音效表
| 事件 | 名称 | 配方 | 时长 | 随机性 |
|---|---|---|---|---|

## 8. 触感表
| 事件 | pattern | 手感描述 |
|---|---|---|

## 9. 平台降级声明
<哪些效果在微信端做不到？打算怎么降级？>

## 10. 已知取舍
<主动放弃了什么？为什么？>
```

| 维度 | 取值数 | 其中成品图 | 其中组合件 |

## 五、常见问题（设计侧自查）

| 症状 | 根因 | 修法 |
|---|---|---|
| 实现方说"看不清这个阴影怎么叠的" | 阴影层数多且没标 `inset` | 减到 ≤3 层，或改用实体厚度 |
| 实现方说"这个噪点每次都不一样" | 用了 `Math.random()` | 改固定种子 |
| 实现方"照抄了但颜色不对" | 色值用了 `color-mix` / `oklch` | 改 `#hex` / `rgb()` |
| 实现方"动画手感不对" | 用了 `ease` 等关键字缓动 | 改显式 `cubic-bezier` |
| 实现方"首包超了" | 字体没裁子集 / 贴图没转 WebP | 按 §1.3 预算 |
| 实现方"震动做不出节奏" | pattern 被简化 / 没给毫秒 | 按 §2.9 补齐 |
| 抽色后认不出是哪一套 | 颜色承担了过多区分职责 | 强化形态/材质差异 |
| 抠图对比全红但看不出差在哪 | 没有元素级基线 | 按 §3.2 登记状态清单 |
