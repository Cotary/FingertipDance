## 〇、五分钟理解全局

### 0.1 核心思想

> **不要让 agent「看着设计稿写代码」。**
> 要让 agent **对着一台可执行的规格工作，并且每一步都有机器判定的闸门。**

设计稿（HTML + CSS + WebAudio）**本身就是一台可执行的规格**：
它的每个属性都能被程序化读出，不需要人眼转述、不需要 agent 猜。

```
              ┌─────────────── 设计稿（可执行规格）───────────────┐
              │  DOM/CSS  → 几何/样式/渐变/阴影                   │
              │  @keyframes → 动效曲线                             │
              │  WebAudio   → 音效（可离线渲染成 PCM）             │
              │  vibrate()  → 触感 pattern                        │
              └───────────────────┬───────────────────────────────┘
                                  │  S1 审问
                                  ▼
                         ┌────────────────┐
                         │   Design IR    │  机器可读中间表示
                         └────────┬───────┘
                                  │  S3 实现
                                  ▼
                         ┌────────────────┐
                         │   Canvas 代码   │
                         └────────┬───────┘
                                  │  S5 比对
                                  ▼
              闸门：像素 Δ ≤ 2 / 差>8 ≤ 2% / 最差块 ≤ 4
              （设计稿截图）  ←──逐像素──→  （代码截图）
```

**闸门是全部意义所在。** 没有闸门，这套流程和「让 agent 照着抄」没区别。

### 0.2 为什么"提取资源"这条路走不通

全量扫描设计稿的结果（`2026-11-15` / `2026-11-16` 两份稿）：

| 资源类型 | 实际数量 |
|---|---|
| `<img>` 标签 | **0** |
| 音频文件（mp3/wav/ogg） | **0** |
| 外链图片/音频 | **0** |
| `url()` 引用 | 5× `data:image/svg+xml`（噪点）+ 4× SVG 渐变 + 1× Google Fonts |
| 设计稿自述 | "Web Audio 合成 / **零音频文件**" |

**所以正确动作不是"下载"，是"审问 + 烘"。**
设计稿没有素材可下载，但它的**计算结果**可以被提取出来。

### 0.3 复刻路线：手绘 vs 烘焙（实测决策）

| 路线 | 精度（实测） | 成本 | 适用 |
|---|---|---|---|
| **A. 手绘 Canvas**（CSS 逐条译成绘图调用） | 均值 Δ **5.29**/255，17.4% 像素超阈 | 高（每元素 60+ 行，改一版要重调） | **需要动起来的**元素 |
| **B. 浏览器烘焙贴图**（截图 → PNG/WebP → drawImage） | 均值 Δ **0.49**/255，**0.1%** 超阈 | 低（脚本自动生成） | **静态外观**：棋子、图标、面板、底板 |
| C. HTML 直出（保留 DOM/CSS 运行时） | 100% | 最低 | **仅 H5/APP**；小游戏无 DOM，走不通 |

**推荐组合：B 打底 + A 补动态 + 像素闸门。**

> **B 的边界（必须记住，否则会踩坑）**：贴图是"定格"的。
> 状态多 / 尺寸要拉伸 / 内容会变 / 要动画 → **不能烘**，必须手绘。
> 详见 §S2.2 的分流表。

## 一、七阶段总览

```
S0 审问规格   → 把设计稿读成 IR（几何/样式/动效/音频 PCM/触感）
   ↓ 闸门 G0：IR 完整，每个值可溯源
S1 真值快照   → 建元素级基线图 + computed style 快照（唯一裁判）
   ↓ 闸门 G1：基线覆盖全部元素与状态
S2 资源生产   → 烘贴图 / 九宫格 / 音频 WAV / 字体子集 / 分流决策
   ↓ 闸门 G2：贴图与基线 Δ ≤ 2；字体全覆盖；音频非静音
S3 骨架搭建   → 只摆位置与尺寸，不填内容
   ↓ 闸门 G3：元素位置/尺寸误差 ≤ 1px，且多比例不破版
S4 逐元素填充 → 每个元素单独过像素闸
   ↓ 闸门 G4：mean Δ ≤ 2 且 pct8 ≤ 2% 且 最差块 ≤ 4
   ↑ 前置：游戏侧能按 manifest 口径出图（见 §6.3.1）—— 缺它则 G4 是空的
S5 动效音效   → 曲线还原 + 音画同帧 + 触感映射
   ↓ 闸门 G5：关键帧位置/透明度一致；音画延迟 ≤ 1 帧
S6 回归锁定   → 阈值写进测试，改代码必过闸
```

## 二、S0 · 审问规格

### 2.1 做什么

**不是"提取资源"，是"把设计稿当 oracle 盘问"。**
所有读数都由浏览器算出来 —— 级联、继承、简写展开全部正确，不做 CSS 静态解析。

| 审问对象 | 怎么问 | 产出 |
|---|---|---|
| 几何 | `getBoundingClientRect()` | `bbox` + 绝对坐标 |
| 计算样式 | `getComputedStyle(el)` | 背景/阴影/圆角/描边/透明度/混合模式 |
| SVG | `getAttribute('d')` + `getBBox()` | 路径数据 + 包围盒 |
| 动效 | 驱动 animation，逐帧采样 `getComputedStyle` | 时长/缓动/关键帧轨迹 |
| 音频 | `OfflineAudioContext` 渲染 | **PCM 采样**（音频的真值） |
| 触感 | 劫持 `navigator.vibrate` | 完整 pattern 数组 |
| 噪点 | SVG filter 栅格化 | PNG（用于标定程序化噪点） |

### 2.2 IR 骨架

```ts
interface DesignIR {
  meta: { source: string; canvas: { w: number; h: number }; hash: string };
  tokens: {
    colors: Record<string, string>;      // 色板
    easings: Record<string, string>;      // cubic-bezier
    durations: Record<string, number>;    // ms
    sizes: Record<string, number>;        // px
  };
  elements: ElementIR[];                  // 每个可截图元素
  motions: MotionIR[];                    // 时长/缓动/关键帧
  sounds: SoundIR[];                      // 配方 + PCM 指纹
  haptics: HapticIR[];                    // 事件 → pattern
  capabilities: CapabilityRequirement[];  // 用到的平台特性 + 保真度
}

interface ElementIR {
  id: string;                             // 'tile.pale.start'
  selector: string;                       // '.pc.pale.start'
  kind: 'tile' | 'icon' | 'panel' | 'bg' | 'text';
  bbox: { x: number; y: number; w: number; h: number };
  /**
   * 这个元素是「成品图」还是「组合件」。
   *
   * `composite` = 几何 + 笔触 + class，运行时拼出来，**不出图**。
   * 这一栏决定了 S2 要烘多少张 —— 组合件不占出图量。
   */
  build: 'baked' | 'composite' | 'parametric';
  /** composite 时：几何来自哪个图元表，笔触来自哪个函数 */
  composite?: { shape: string; painter?: string; variant?: string };
  /** parametric 时：参数是什么（如方向角、palette key） */
  params?: Record<string, string | number>;
  style: {
    backgroundImage?: string;             // 渐变原文
    backgroundColor?: string;
    boxShadow?: string;                   // 原文，供逐条翻译
    borderRadius?: string;
    border?: string;
    opacity?: number;
    mixBlendMode?: string;
  };
  fidelity: 'exact' | 'approx' | 'substitute' | 'blocked';  // 本次落地保真度
  substitute?: string;                    // 被替代时写清方案
}

interface MotionIR {
  id: string;                             // 'dropIn'
  selector: string;
  durationMs: number;
  easing: string;                         // 'cubic-bezier(.22,1,.36,1)'
  keyframes: Array<{ at: number; transform?: string; opacity?: number }>;
  soundEvent?: string;                    // 同帧音效
}

interface SoundIR {
  id: string;                             // 'tap'
  recipe: string;                         // 配方原文
  durationMs: number;
  randomRange?: number;                   // 随机范围（如 ±5%）
  pcm: { sampleRate: number; peak: number; rms: number; envelope: number[] };
}

interface HapticIR {
  event: string;                          // 'step' / 'trail' / 'settle' / 'seal' / 'tap'
  pattern: number[];                      // [15,30,15,30,25]
}
```

### 2.4 ⚠️ S0 必须审查设计稿本身的 bug

**设计稿可能自己就有错。** 发现的矛盾点**必须反馈给设计侧，不许自行"修正"**。

常见矛盾：

| 症状 | 检查方法 |
|---|---|
| 某处色值与色板不符 | 全量扫描色值，与 `:root` 变量交叉比对 |
| 元素重叠 / 压字 | 元素级截图目视 + bbox 交叉检测 |
| 状态样式没生效 | `getComputedStyle` 取到的值与预期不符 |
| 噪点每次都变 | 检查是否用了 `Math.random()` |

## 三、S1 · 真值快照（建立唯一裁判）

### 3.1 为什么这是基石

没有基线图，"像不像"只能靠肉眼 —— 而**肉眼查不出渐变线短 45% 这类 bug**
（项目实测：整盘系统性偏亮，靠肉眼查了很久）。

有了基线图，"复刻"变成一个**有明确成功判据的工程任务**。

### 3.2 做什么

1. 用无头浏览器打开设计稿，`deviceScaleFactor: 3`
2. **按元素级截图**（不是整页）：
   - 每个棋子材质 × 每个状态
   - 每个图标
   - 每个面板/卡片
   - 每屏一张整屏基准
3. 存进 `baseline/`，文件名带语义：`tile.pale.start.png`
4. **同时导出每个元素的 `getComputedStyle()` 快照** —— 这是"为什么长这样"的答案

**为什么必须元素级**：整页截图差异太杂（一个像素偏了整屏都红），无法定位。
元素级才能回答"是哪一格、哪一层错了"。

### 3.3 执行

```bash
cd docs/连连看/复刻SOP/scripts
node baseline.mjs --build --design "../../风格样片/2026-11-16-秘色天青-图标动效音效.html"
```

产出：

```
baseline/
  tile.pale.start.png            ← 元素截图
  tile.pale.start.style.json     ← computed style 快照（为什么长这样）
  manifest.json                  ← 元素清单 + clip 区域 + DPR
```

### 3.4 新增元素怎么加

编辑 `baseline.mjs` 里的 `TARGETS` 数组：

```js
export const TARGETS = [
  { id: 'tile.pale', selector: '.pc.pale' },
  { id: 'tile.pale.start', selector: '.pc.pale.start' },
  // ... 新增一行即可
];
```

> ⚠️ **选择器口径要统一**：同一材质在不同章节尺寸不同（62/54/44px）时，
> `.first()` 命中的是**文档里第一个出现的位置**。要固定口径就写精确选择器
> （如 `.glyph-grid .pc.pale`）。

> ⚠️ **选择器无匹配会被静默跳过**（只打一行 `! 选择器无匹配：xxx`，不报错退出）。
> 所以 `--build` 之后**一定要核对元素数**：
> 预期 27 个就必须是 27 个。少了就是选择器写错了，
> 漏掉的元素**从此不会被自动比对** —— 这是最隐蔽的一种失效。
>
> 实测：`panel.fix-card`（`.fix-card`）在当前设计稿里已改名，导致静默丢失 1 个元素。
> **每次 `--build` 后比对元素数，是必须做的检查。**

### 闸门 G1

- [ ] `baseline/` 覆盖设计稿**全部可视元素与状态**
- [ ] 每个 PNG 都有对应的 `.style.json`
- [ ] `manifest.json` 里每个 target 都有 `clip` 和 `pad`
- [ ] 重跑 `--build` 后文件数一致（幂等）

## 四、S2 · 资源生产

### 4.0 先做「分层决策」—— 决定哪些该烘、哪些该参数化

> **这是 S2 的第一步，比烘焙更重要。**
> 状态空间的总量是**固定的**（材质 × 机制态 × 方向 × 交互态）。
> 问题不是"状态多不多"，而是**每个状态要不要单独出图**。
>
> **判据：这个状态的差异是「换颜色」还是「换形状」？**

| 差异类型 | 处理方式 | 例子 | 出图量 |
|---|---|---|---|
| **只换色** | **参数化** —— 同一张图/同一段代码 + 换 palette | 冰砖 vs 石块 vs 釉面，只差材质色与笔触 | 材质数（4） |
| **只换朝向** | **参数化** —— 同一张图 + `ctx.rotate(dir * π/2)` | 单向箭头四向 | **1**（不是 4） |
| **换形状但同坯** | **参数化** —— 几何表里换一个 key | 门闭 / 门开、传送门进 / 出 | 变体数（2） |
| **换材质语言** | **参数化** —— 换笔触函数 | 釉面 / 矿物 / 水墨 / 赛博 | 笔触数 |
| **换形状且不同坯** | **烘** —— 独立贴图 | 面板 vs 棋子 vs 图标（形状本身不同） | 元素数 |
| **任意尺寸拉伸** | **烘 + 九宫格** | 卡片、按钮 | 1 套 9 片 |

**这张表就是「组合式落地」的判据。** 本项目的现成先例见 §4.0.1。

### 4.0.1 本项目的现成范式：**几何 + 笔触分离**

`src/render/themes/glyphs.ts` 已经实现了这套组合架构，**可以直接抄**：

```
GLYPHS:  9 类机制的几何（单位空间 [-1,1]²）     ← 只写 9 次
PAINTERS: 每套主题的笔触语言                  ← 只写 N 次
MARKS:   端点/路径的记号                        ← 只写一次
                    ↓ 组合
        9 × N 种图标 = 运行时拼出来
```

> 原文注释说得很清楚：
> 「9 类机制 × 3 种图标族 = 27 种组合。逐对硬写要 27 段绘制代码，
> 而且改一条规则（比如「所有图标统一线宽」）要改 27 处。
> 拆开之后：几何只写 9 次（`GLYPHS`），笔触只写 3 次（`PAINTERS`），
> 组合是 `9 + 3` 而不是 `9 × 3`。」

**关键的三层**（设计侧只需产出第 1、2 层）：

| 层 | 是什么 | 谁定 | 出图量 |
|---|---|---|---|
| **几何层** | 形状：多边形/圆/矩形/线/弧，单位空间坐标 | **设计侧给**（SVG path → 图元表） | 9 类 × 变体数 |
| **笔触层** | 材质语言：面怎么填、线多粗、要不要颗粒/亮边 | **设计侧给**（每套主题一个函数） | 每套 1 个 |
| **装配层** | 几何 × 笔触 × 调色板 → 运行时绘制 | 实现侧 | **0 出图** |

**这套架构直接消掉了状态爆炸**：

| 状态维度 | 在这套架构下 | 出图量 |
|---|---|---|
| 机制类型（9 种） | 几何表 9 条 | 9 |
| 材质/主题（每套 1 个） | 笔触函数 1 个 | 1 |
| 方向（4 向） | `ctx.rotate()` | **0** |
| 开/闭、进/出（变体） | 几何表换个 key | 变体数（2~3） |
| 装饰细节（每套特有） | `decor` 回调 | 0 |

> **实测依据**：本项目设计稿有 `arrow/arrowR/arrowD/arrowL` 四个键，
> 引擎侧**只保留一个 `arrow`**，用 `DIR` 转 —— 注释明写
> 「四向是**同坯旋转**（设计稿自己也是 `<g transform="rotate(90)">`），
> 四个键会变成四份要同步维护的路径」。
>
> **这就是「组合式」在设计侧的对应写法**：
> 设计稿如果自己就是旋转复用（`<g transform="rotate(90)">`），
> 引擎侧就不该展开成四份。

### 4.0.2 什么时候**必须**烘（不能参数化）

| 情形 | 为什么不能参数化 |
|---|---|
| 元素形状本身不同（棋子 vs 面板 vs 图标） | 没有共同的几何底座 |
| 面板要任意尺寸拉伸 | 参数化画不出任意尺寸 |
| 材质是**贴图级**的（木纹/石纹/指纹） | 参数化画不出真实纹理 |
| 用了 `filter: blur()` / `feTurbulence` 造质感 | 滤镜效果与分辨率绑定（见《41》§2.6b） |
| 形状是**位图**（照片、手绘笔触） | 没有矢量描述 |

### 4.1 分流决策表（**先做这个判断，再动手**）

> ⚠️ **先纠正一个常见误判**：
> 「状态太多，烘不过来」**不是实现侧的困难，是设计侧的交付缺陷。**
> 状态空间是**有限且可枚举**的（材质 × 状态 × 方向 × 交互 ≈ 几十到一两百种），
> 它的**总量由设计稿决定，不由烘焙器决定**。
> 设计稿若只画了默认态没画按压态，实现侧就**无从凭空补出按压态**。
>
> **正确做法**：设计侧在《41》§3.1 的「状态清单」里把状态矩阵**列全**，
> 实现侧只是把它拍成贴图。**状态穷举是设计的责任。**

| 场景 | 烘 / 手绘 | 理由 |
|---|---|---|
| 棋子静态外观、图标、面板、底板 | ✅ **烘** | 状态有限、尺寸固定 |
| **状态多的元素（选中/提示/按下/方向/开合）** | ✅ **烘 —— 但前提是设计稿画全了** | 状态虽多但是**有限且离散**的，逐个烘即可（见 §4.1.1） |
| 任意尺寸拉伸的圆角面板 | ✅ **烘 + 九宫格** | 否则贴图数量爆炸 |
| 冰裂纹 / 随机纹理 | ✅ 烘 **1 张** + 运行时随机变体 | 设计稿本就是伪随机 |
| 噪点底 | ⚠️ **建议手绘（程序化）** | 已有确定性噪点实现，跨设备一致、零资产；烘 PNG 反而有 DPR 差异 |
| 文字 | ❌ `fillText` | 内容会变、需多语言 |
| 渐变（要动或尺寸会变） | ❌ **手绘（原生 API）** | Canvas 原生渐变更清晰、无损 |
| 动效 | ❌ 手绘 | 贴图是定格的 |

> **决策原则：能参数化的就参数化，贴图只用于"静态且需要位级一致"的。**
> 混响尤其不能烘 —— 设计稿本身也没有混响，烘了会把游戏的空间感设计（各主题的
> `space.decay` 0.18s~2.6s）拆掉。

#### 4.1.1 九宫格：让「一个面板」变成「任意尺寸的一个面板」

| 场景 | 烘 / 手绘 | 理由 |
|---|---|---|
| **任意尺寸的圆角面板**（卡片、按钮、弹窗） | ✅ **烘 + 九宫格** | 见下 |
| 尺寸固定的面板 | ✅ 烘 1 张 | 不必切片 |

**为什么必须切片**：设计稿里所有面板都是「圆角 + 边框 + 多层阴影」的矩形，
尺寸各不相同（14/16/18/20px 圆角，各种宽高）。
**每个尺寸烘一张 → 贴图数量爆炸，且圆角会被拉变形。**

**九宫格（9-slice）** 切成 9 片（四角 + 四边 + 中心），只拉伸中间和边：

```
┌───┬─────┬───┐
│角 │ 边  │角 │   角：不动（保圆角 + 阴影）
├───┼─────┼───┤
│边 │中心 │边 │   边：只沿一个方向拉
├───┼─────┼───┤
│角 │ 边  │角 │   中心：自由拉伸
└───┴─────┴───┘
```

> **这是业内标准做法**：Unity Sprite Border、CSS `border-image`、
> 安卓 `.9.png` 都是这个。

**实测**（`ninepatch-test.mjs` 已跑通，产物 `ninepatch-compare.png`）：
170px 面板切九宫格后拉伸到 300px，**圆角与阴影完全不变形**。

**给设计侧的要求**：

| 要求 | 原因 |
|---|---|
| 面板的**圆角半径和阴影外扩必须固定** | 变了就切不出通用九宫格 |
| 面板的**边框/阴影不能画在内容区** | 中间会被拉伸变形 |
| 面板内**不要放居中文字** | 居中元素要单独画，不能靠拉伸 |
| 内容区（中心）用**可平铺**的底纹 | 拉伸才不出重复感 |

#### 4.1.2 状态空间是有限的 —— 设计侧必须把它列全

**这是本节最重要的一条。** 状态 = 几个**离散维度**的笛卡尔积：

| 维度 | 取值 | 数量 |
|---|---|---|
| 材质 | 釉面 / 矿物 / 石 / 冰 … | 4 |
| 机制态 | 默认 / 起点 / 终点 / 路径 / 按下 / 提示 / 单向 / 钥匙 / 门 / 门开 / 传送A / 传送B / 抵达 / 星屑 | 14 |
| 方向 | 上 / 右 / 下 / 左 | 4 |
| 交互态 | 常态 / 按下 / 选中 / 禁用 | 4 |

**理论上限 ≈ 4 × 14 × 4 × 4 = 896**，但**不是全组合都要画**——
只有"该维度对这个材质有意义"时才需要。所以实际要画的是**几十到一两百张**。

> ⚠️ **关键约束**：**方向维度只对"有朝向"的元素有意义**
> （单向箭头朝四个方向；起点/终点/路径无方向）。
> **状态清单里必须标明每个元素的"有效维度"**，否则实现侧会去做无意义的组合。

**但更要紧的是：这几十到一两百张，是"成品图"还是"组合件"？**

> **「状态太多烘不过来」的真正解法不是让设计多画，
> 而是让设计把它们标成「组合件」—— 组合件不出图。**

| 标成 | 出图量 | 实现侧的做法 |
|---|---|---|
| **成品图**（`baked`） | 1 张/个 | 烘贴图，`drawImage` |
| **组合件**（`composite`） | **0 张** | 几何表 + 笔触函数，运行时拼 |
| **参数化**（`parametric`） | **0 张** | 同一张 + 换参数（方向角、palette key） |

**判据（回到 §4.0 的那张表）**：差异是「换颜色」→ 参数化；
「换朝向」→ 参数化；「换材质语言」→ 组合件；「换形状但同坯」→ 组合件（换 variant）；
**只有「换形状且不同坯」才是成品图。**

**实现侧的责任边界**（很重要，避免互相甩锅）：

| 情况 | 谁负责 |
|---|---|
| 设计稿画了 N 个状态 → 实现侧要还原这 N 个 | 实现侧 |
| 设计稿没画某个状态，但玩法需要它 | **设计侧补**（反馈给设计，不许自行编造外观） |
| 方向类状态只画了"向上" | **设计侧补齐四个方向**（或明确声明"运行时旋转 90°"） |
| 运行时用旋转/缩放代替独立贴图 | 实现侧（**但必须在 S0 记录**：`build: parametric`） |
| 设计稿标了"组合件"但没给几何 path | **设计侧补**（引擎侧要靠它拼） |

> **方向维度的三种处理方式**（设计侧选一个，并写进设计说明）：
> 1. **画四张** —— 外观本身随方向改变（如单向箭的箭羽）。
> 2. **画一张 + 声明旋转** —— 外观是旋转对称的，实现侧 `ctx.rotate(dir * π/2)`。
> 3. **画一张 + 声明不做方向** —— 该元素无方向语义。
>
> **本项目的现成先例**：单向箭的箭头是**旋转**实现的
> （`glyphs.ts` 的 `DIR_ROT`），只有"箭羽"这类非对称装饰才需要独立变体。
> 设计稿自己也是 `<g transform="rotate(90)">` —— **两边本来就不该展开成四份。**

## 五、S3 · 骨架搭建

### 5.1 为什么单独一步

**这一步最容易做错**：一上来就画细节，结果布局错了全部返工。

### 5.2 做法

1. 按设计稿的 `flex`/`grid` 结构，先摆**纯色方块**（用平均色），位置尺寸要准
2. 与基线图做**「布局比对」**：不看颜色，只比每个块的位置/尺寸（边框检测）

**为什么单独做布局比对**：布局错和颜色错是两类 bug，混在一起查很痛苦。
分开查，布局错一眼能定位。

### 5.3 设计坐标系约定

```
设计基准   750 × 1334（逻辑 px）    ← 代码内部一律用它
运行时     ctx.scale(dpr * (canvasW / 750))
```

> **关键**：设计稿画在 375 CSS px，代码用 750 逻辑 px，**比例精确 2×**。
> 转换只在 `toDesign()` 一处发生，其余代码只认 750 坐标系。
> 设计稿与代码的坐标系比例差异，是"整页像素 diff 不可达"的原因 ——
> 所以比对必须**逐元素**做，不能整页比。

### 闸门 G3

- [ ] 所有元素的位置/尺寸与基线图误差 ≤ 1px（逻辑像素）
- [ ] 在 16:9 / 19.5:9 / 平板比例下不破版
- [ ] 坐标转换只在 `toDesign()` 一处（无散落的换算）

## 六、S4 · 逐元素填充（主战场）

### 6.1 循环

```
for 每个元素:
    1. 用贴图 / 手绘 把元素画出来
    2. 截游戏画面（同尺寸、同 DPR）
    3. 与基线图逐像素比对 → 算 mean / pct8 / blockMean
    4. 若任一超阈:
         → 看报告里的「最差像素坐标 + 两边 RGB」
         → 对照 baseline/<id>.style.json 找原因
         → 修，回到 1
    5. 通过
```

### 6.2 判据

| 指标 | 阈值 | 为什么 |
|---|---|---|
| `mean` | **≤ 2** | 浏览器自身重渲染的固有差异约 0.5~1，留一倍余量。实测手绘 5.29 → 判红；烘焙 0.49 → 通过 |
| `pct8` | **≤ 2%** | 允许抗锯齿边缘，但整片区域不许偏 |
| `blockMean` | **≤ 4** | **堵住全局均值的盲区** |
| `max` | 不参与判定 | 抗锯齿边缘天然有单点大差异，用它判会永远失败 |

> **`blockMean` 为什么必须单独有**：全局均值有致命盲区 —— 角落 1% 区域偏 +30，
> 均值只有 0.25、差>8 只有 0.96%，**全绿通过但人眼一眼能看出**。
> 标定脚本里这条是独立用例（`corner`），必须过。

### 6.3 执行

```bash
# ① 游戏侧出图（按 manifest 的 clip 口径）
node tools/shot-cdp.mjs http://127.0.0.1:50002/ out/shots/tile.pale.png 4000 750 1334 2

# ② 比对
cd docs/连连看/复刻SOP/scripts
node baseline.mjs --check --shots ./shots
node baseline.mjs --check --shots ./shots --only tile.pale    # 调试单个
```

> ⚠️ **DPR 必须与基线一致，否则第一道就判红。**
> 基线是 `deviceScaleFactor: 3` 截的（64×64 的元素 → 基线 564×564 含 24px 外扩 ×3）。
> 游戏侧截图的 scale 也必须能对上，否则报「尺寸不一致：设计稿 564,564 vs 我们 336,336」。
> **先对齐尺寸，再谈颜色。**
>
> ⚠️ **`shots/` 目录里的旧图会被误用。** 换设计稿或改渲染后，
> 必须清空重建，否则会拿旧截图对新基线比，报出一堆假差异。

#### 6.3.1 ⭐ 怎么让游戏侧出图（**当前最该做的一件事**）

> **现状：像素闸门是 0/27 通过。**
> 这**不是"复刻质量差"，是"考试卷还没交"** ——
> 裁判已经就位（27 份基线 + 27 份 computed style），
> 选手（游戏侧截图）还没上场。`shots/` 目录当前**根本不存在**。
>
> **没有这一步，S4 就是"做完靠肉眼看看像不像"** ——
> 那正是这套 SOP 要消灭的东西。

**两张图的关系**：

```
设计稿 (HTML+CSS)                我们 (Canvas 代码)
      │                                │
      ▼                                ▼
  无头浏览器截图                  无头浏览器截图
  deviceScaleFactor: 3           ← 这一半还没接上
      │                                │
      ▼                                ▼
  baseline/<id>.png              shots/<id>.png
  （裁判的"标准答案"）            （我们的"答卷"）
      └────────── 逐像素比对 ──────────┘
                     ↓
              mean Δ ≤ 2 且 pct8 ≤ 2%？
                   通过 / 判红
```

> **实测发现**：今天 `baked/` 与 `baseline/` 是**同一批字节**（MD5 相同）——
> 因为烘焙器就是用同一个设计稿、同一套 clip 口径截的。
> 所以目前能自证的只有「**烘焙 = 真值**」（已成立，Δ=0），
> 而「**我们的 Canvas 代码画得像不像**」这一环**完全没被验证过**。

##### 方案 A · 专用出图页（**推荐**）

新建一个「复刻展示台」页面（如 `tools/design-replica/shoot.html`）：

| 步骤 | 做法 |
|---|---|
| 1 | 页面加载游戏的渲染模块，**不启动游戏循环** |
| 2 | URL query 指定要出图的元素：`?shoot=tile.pale.start` |
| 3 | 把该元素**按 manifest 的 clip 区域**画进一张**离屏 canvas** |
| 4 | `canvas.toDataURL()` 导出 PNG → `shots/<id>.png` |

**为什么这是最短路径**：

- ✅ **绕开了"元素在屏幕上哪儿"这个本来最难的问题** ——
  不截整屏，直接按 manifest 的 clip 坐标画离屏画布
- ✅ **不用真的玩到那个状态**（选中了？铺满了？）—— 出图页直接构造状态
- ✅ **尺寸/DPR 完全由代码控制** —— 不会对不上
- ✅ **clip 口径与基线共用** —— `manifest.json` 已有 `clip` 与 `pad`，直接用

**要做的三件事**：

| # | 内容 | 说明 |
|---|---|---|
| 1 | **`renderElement(id, ctx)` 分发表** | 把 `tile.pale` 映射到「调 `drawTile()` 并给定状态」 |
| 2 | **状态预设** | 每个元素 id 对应一组 `ThemeState` 预设（`covered`/`path`/`hint`/`pressCell`…） |
| 3 | **出图脚本** `shoot.mjs` | 起 dev server → 驱动出图页逐个元素截图 → 写 `shots/` |

> **状态预设是这套方案的关键**：
> `ThemeState` 里已有 20 个字段（`covered`/`path`/`keysHeld`/`shardsGot`/
> `hint`/`enter`/`paused`/`shakeCell`/`pressCell`/`drops`/`settle`/`wonAt`/`trailAt`…），
> **每个元素 id 对应一组预设**，才能出"选中态""提示态""按下态"的图。

##### 方案 B · 真机游玩 + 逐帧截屏（**补充，不做主路径**）

用 `shot-cdp.mjs` 截真实游戏画面再裁剪。

**问题**：
- 要**真的玩到那个状态**（走到第 37 关才看得到某种机制组合）
- 元素在屏幕上的位置**随关卡、随窗口尺寸变**，与 manifest 的 clip 对不上
- 要额外做"元素位置 → 屏幕坐标"的映射

**成本** 3~5 天且脆。**不推荐做主路径，但可作为方案 A 的交叉验证。**

##### 方案 C · 只截整屏，人工判读（**辅助粗筛**）

`shot-cdp.mjs` 截 7 屏整图，比对只做整体均值。

**问题**：回到 doc 40 说过的问题 —— 整页差异太杂，**一个像素偏了整屏都红**，无法定位。

**成本**半天。**只能做粗筛，不能当门禁。**

##### 推荐组合

```
方案 A（出图页，精确出图）        ← 主路径，做门禁
   +
方案 C（整屏截，作为回归快照）    ← 辅助，防止"出图页能骗过闸门"
```

> **方案 C 作为补充很重要**：只测出图页，理论上存在
> 「出图页画得对、真实游戏画得错」的情况（如真实游戏里棋子被别的层盖住）。
> 整屏快照能兜住这类。

##### 闸门定标（**必须先做这一步**）

出图页写好后，**第一步不是比对设计稿，而是比对"出图页自己"**：

| 阶段 | 比什么 | 判据 | 为什么 |
|---|---|---|---|
| **定标** | 出图页 vs 烘焙贴图 | Δ ≤ 2 | 验证"出图页的渲染路径没引入额外误差" |
| **验收** | 出图页 vs 设计稿基线 | Δ ≤ 2 | 这才是真正的复刻判据 |

> **定标这步不能省** —— 否则会出现"出图页自己有 bug 导致偏差"，
> 然后被误判成"我们的实现不对"，白查一轮。
> 定标能**把"出图工具的错"和"实现的错"分开**。

##### 门禁接入

> 否则"改设计稿"和"改代码"混在一起，就失去回归意义了。

##### 出图页的注意事项

| 事项 | 说明 |
|---|---|
| **别截整屏** | 整屏截图的差异无法定位到元素级 |
| **状态必须可枚举** | 出图页要能复现每一种状态，否则某些态永远测不到 |
| **离屏画布的 DPR 要显式设 3** | 与基线口径一致，否则第一道就判红 |
| **透明底** | 用 `omitBackground` 等价的方式（`clearRect` 后不填背景） |
| **出图页不要复用游戏主循环** | 主循环带动画/输入，会让出图不稳定 |

## 七、S5 · 动效与音效

### 7.1 动画曲线

**缓动控制点必须照抄**。不要用 `ease` / `linear` 关键字（各浏览器实现不同，Canvas 无法反解）。

```ts
/** cubic-bezier 求值器（牛顿迭代 + 二分兜底）。项目已有，勿重写。 */
export function easeBezier(x1: number, y1: number, x2: number, y2: number) {
  return (t: number): number => { /* ... */ };
}
```

### 7.2 音画对齐

**事件 → 动画起始帧 与 音频起始帧必须同帧触发。**

**做法**：统一一个 `tick(dt)` 时钟，动画和音频都用它调度，
**不要用 `setTimeout`** —— 低端机上 40 个定时器各偏 10~30ms，听起来是一串毛毛雨。

### 7.3 触感映射

| 平台 | API | 能做到 |
|---|---|---|
| H5 (Android) | `navigator.vibrate([pattern])` | 毫秒级节奏，**可完全照抄** |
| H5 (iOS) | ❌ | **没有震动** |
| 微信小游戏 | `wx.vibrateShort({type})` | 只有 light/medium/heavy **三档** |
| 抖音小游戏 | `wx.vibrateShort` 同构 | 同上 |

**微信端降级方案**（能把节奏拼回来）：

```ts
/**
 * 把 design pattern 还原成节奏：
 * 数组 = 振/停交替（奇数位是振动时长，偶数位是停顿时长）。
 * 微信只有三档，所以用「连续 vibrateShort + 定时器」拼出节拍。
 */
function vibratePattern(pattern: number[]): void {
  for (let i = 0; i < pattern.length; i += 2) {
    const ms = pattern[i];
    const gap = pattern[i + 1] ?? 0;
    setTimeout(() => {
      wx.vibrateShort({ type: ms >= 30 ? 'heavy' : ms >= 12 ? 'medium' : 'light' });
      if (gap) setTimeout(() => {}, gap);   // 停顿由下一次 setTimeout 的间隔天然形成
    }, i === 0 ? 0 : acc);
    acc += ms + gap;
  }
}
```

> ⚠️ **不许把多拍简化成单拍。** 手感是**节奏** ——
> 五件事用同一个时长，等于告诉手指"这五件事没有区别"。

### 7.4 音频复刻判据（G-AUDIO）

**设计稿与实现各自离线渲染**同一组事件 → 两段 PCM → 对齐起音点 → 比对：

| 指标 | 阈值 |
|---|---|
| 包络（滑动窗 RMS）差 | ≤ 15% |
| 峰值差 | ≤ 0.05 |
| 起音时刻差 | ≤ 10ms |
| 混响衰减时间误差 | ≤ 15%（**单独评估**） |

**混响层不参与干声比对** —— 平台近似方式不同（卷积 vs FDN），卷积特性本就不同。

### 闸门 G5

- [ ] 关键帧（落子 0/60/120/240ms）的位置与透明度与设计稿一致
- [ ] 动画与音频起始时间差 ≤ 1 帧（16.7ms）
- [ ] 触感 pattern 与设计稿逐槽相等（或已声明降级）
- [ ] G-AUDIO 四项达标

## 十、失败处理

| 症状 | 根因 | 修法 |
|---|---|---|
| 闸门全红但看不出差在哪 | 没做元素级基线 | 回 S1，改元素级 |

| 字距丢了 | `ctx.letterSpacing` 低版本不支持 | 逐字 `measureText` 定位（`trackedText` 已有） |

| 微信端混响失效 | `createConvolver` 不在微信 API 列表 | FDN 混响（Delay + Biquad 反馈网络） |

## 十二、明确不做

- **不做 CSS 静态解析** —— 用浏览器计算样式，级联正确且省事
- **不做 IR → 代码的自动生成器** —— 实现是 agent 的活，SOP 只保证它有可核对的输入
- **不做整页像素 diff** —— 设计稿 375 宽 vs 代码 750 逻辑宽，比例不同；
  比对必须逐元素（ROI）
- **不引入 npm 依赖到游戏** —— playwright 只用于设计期工具
- **不烘焙参数化的东西** —— 渐变、动效、混响、状态多的一切，手绘
- **不换引擎** —— Cocos/Unity/Laya 都是命令式 Canvas，同样吃不下 CSS 语义；
  重写代码的代价远超收益，且会破坏「零素材 + 极小首包」的优势

#### A.1 「大图能不能解决手绘误差」的实测结论

用真值基线图做「降采样 k 倍再升回」制造**纯分辨率误差**，再分解为
DC（系统性偏移）与 HF（高频残差），6 个元素平均：

| 降采样 | mean | DC | HF |
|---|---|---|---|
| 1/3 | 3.07 | **0.47** | 3.03 |
| 1/2 | 2.11 | **0.21** | 2.09 |
| 1/4 | 3.47 | **0.39** | 3.44 |

**对照 doc 40 实测的手绘路线总误差：mean 5.29 / pct8 17.4%。**

**结论**：

1. **降采样的 DC 极小（0.21~0.47）** —— 重采样只制造锯齿/模糊，
   几乎不产生系统性偏色。证明这个分解方法有效。
2. **HF ≈ mean** —— 纯分辨率误差几乎全是高频，**这正是"齿感"的来源**。
3. **手绘 5.29 > 同等分辨率下的重采样误差（1/3 时 3.07）** ——
   手绘误差里有一块**重采样解释不了**，那部分是**结构翻译错误**
   （阴影层序、模糊近似、渐变停靠点算错）。

**所以**：
- ✅ **大图能消除"齿感"**（HF 部分）—— 6× 烘 → 3× 输出的 2:1 下采样。
- ❌ **大图消除不了"画得不像"**（结构部分）—— 那是画法问题。
- 🎯 **真正决定成败的是"状态画全了没有"**，不是"图够不够大"。

#### A.2 当前最该补的缺口

> **像素闸门是 0/27 通过**，因为**游戏侧出图这一半从未接通**
> （`shots/` 目录当前不存在）。
> 裁判已标定可用，选手还没上场。
> **这是下一步最该做的事**：让游戏按 `manifest.json` 的 clip 口径自动出图，
> 接通闭环。在此之前，**G4 门禁是空的**，SOP 只走通了 S0–S3。
>
> **完整方案见 §6.3.1**（三个方案的取舍 + 闸门定标 + 门禁接入）。

**实测补充**：`baked/` 与 `baseline/` 当前是**同一批字节**（MD5 相同）——
烘焙器用的就是同一个设计稿、同一套 clip 口径。
所以目前能自证的只有「**烘焙 = 真值**」（Δ=0，已成立），
而「**我们的 Canvas 代码画得像不像**」这一环**完全没被验证过**。
