# 28 · 移动端适配体检

> 2026-11-11 · 结论先说：**能玩，但不是「满屏」**。
> 功能（触摸拖动、DPR、旋转重建）是通的；版式是「固定 750×1334 等比缩小 + 居中」，
> 在 19.5:9 的手机上上下各留一条空白，横屏基本不可用。

## 1. 实测数据（不是推算，是从运行中的页面量的）

测量方式：`tools/probe-mobile.mjs` 按目标设备尺寸打开页面，
读 `canvas.getImageData` 的 alpha 找「真正被画过的区域」——
没被绘制的地方 alpha=0，所以这个边界是客观的，不依赖截图观感。

| 设备 | 视口 | scale | 内容占屏 | 留白 |
|---|---|---|---|---|
| iPhone SE / 8 | 375×667 | 0.500 | **100%** | 无（设计稿就是 16:9） |
| iPhone 14 | 390×844 | 0.520 | **82%** | 上下各 75px |
| Android 常见 | 412×915 | 0.549 | **80%** | 上下各 91px |
| iPhone 14 Pro Max | 430×932 | 0.573 | **82%** | 上下各 84px |
| iPad 竖屏 | 768×1024 | 0.768 | **100% 高** | 左右各 96px |
| 横屏 | 844×390 | 0.292 | **31.8% 宽** | 左右各 312px |

同一张盘在 iPhone 14 上的实际观感：顶部有一条颜色略深的横带，
那是留白区（body 背景 `#E3C9AE`）与背景渐变（`clayBackdrop`）的接缝。

## 2. 已经做对的

这些不用动：

| 项 | 实现 |
|---|---|
| 视口 | `width=device-width, initial-scale=1` + `maximum-scale=1` + `user-scalable=no` |
| 禁止滚动/回弹 | `html,body{overflow:hidden}` + `canvas{touch-action:none}` |
| 高清屏 | `canvas.width = cssW × min(dpr,3)`，上限 3 档，兼顾清晰度与显存 |
| 尺寸变化 | 监听 `resize` + `orientationchange`，重建 viewport（渲染与输入同一对象） |
| 坐标系 | 设计坐标 ↔ CSS ↔ 设备像素三层显式换算，`applyTo` 与 `toDesign` 严格互逆（有测试锁） |
| 触摸输入 | 走 Pointer Events，`pointercancel` 也接了 |
| 微信小游戏 | `platform/wechat.ts` 走 `wx.onTouchStart/Move/End`、`wx.onWindowResize`、`onShow` 重新测量 |
| 音频解锁 | WebAudio 惰性创建，`state==='suspended'` 时 `resume()`；首个音效在 pointerdown 触发 |
| 布局取值 | 用 `window.innerHeight` 而不是 CSS `100vh`，避开 iOS 地址栏收缩导致的高度错位 |

**触摸拖动实测通过**：在 390×844 下模拟手指按住横向划 4 格，
棋盘正确覆盖 4 格、连线画出、当前格白环跟随（截图 `out/shots/dbg-hold.png`）。

## 3. 真问题（按严重度）

### P0-1 固定 16:9 的画布，在长屏手机上「上下有边」

`render/viewport.ts` 的策略是 `scale = min(w/750, h/1334)` 后居中。
设计稿是 iPhone 8 时代的 16:9，现在主流是 19.5:9~20:9，于是：

- iPhone 14 上 844 − 1334×0.52 = **150px** 高度被浪费，上下各 75px；
- 这 150px 不是留白那么简单——**它是两种不同米色的拼接**，屏幕上下沿各有一条可见接缝；
- 底部导航因此上浮到 769px 处，距屏幕底还有 75px，手势条区域反而空了。

### P0-2 抬手指＝整段作废，且扣一次「重来」

`coverState.releaseCover()`：没铺满就松手 → `undos++`、`resetPath()`。
规则本身合理（一笔画），但触屏的误抬手指概率远高于鼠标，
而星级是 `StarOf(undos)`：**一次误抬手指就丢 3 星**。

实测复现：按住拖 4 格时是 `4 / 21`，松手后立刻回到 `0 / 21`
（截图 `dbg-hold.png` → `dbg-after-release.png`）。

对手机来说这是**最该改的一条**，它直接决定手感是「可控」还是「一碰就炸」。

### P1-3 顶部三个小按钮低于最小触控尺寸

390 宽下换算（scale 0.52）：

| 元素 | 设计尺寸 | 实际 CSS | HIG 要求 |
|---|---|---|---|
| 提示 / 跳过 / 返回 | 90×60 | **46.8 × 31.2** | ≥44×44 |
| 分享 / 皮肤 / 返回大厅 | 高 64 | 高 33.3 | ≥44 |
| 主按钮（下一关） | 高 88 | 高 45.8 | 勉强达标 |
| 底部页签 | 150×120 | 78 × 62.4 | 达标 |

高度 31px 的按钮，成年人指尖接触面约 45–55px，容易点空或点到隔壁。

### P1-4 最小字号只有 11.4px

`22px` 设计字号 → iPhone 14 上 **11.4 CSS px**，320 小屏上 **9.4px**。
出现位置：`皮肤 2/16`、`第 0 关`、`共 1000 关`、`剩 21`、`起点自由 · 任意格都能起手`。
这些恰好是**读数**（进度/剩余/说明），最不该小。

### P1-5 11×11 的格子只有 31px，拖动精度吃紧

| 棋盘 | 设计格宽 | iPhone 14 实际 |
|---|---|---|
| 5×5 | 134 | 69.7px |
| 7×7 | 95 | 49.4px |
| 8×8 | 83 | 43.2px |
| 9×9 | 74 | 38.5px |
| 10×10 | 67 | 34.8px |
| 11×11 | 60 | **31.2px** |

11×11 的世界七是难点：31px 格 + 快拖自动补齐（`autoFill`）在窄道上容易补错格，
一补错就要重来——和 P0-2 叠加后惩罚很重。

### P2-6 没有安全区，只是「碰巧躲开」

`index.html` 没有 `viewport-fit=cover`，代码里也没有 `env(safe-area-inset-*)`。
现在没出事，是因为 P0-1 的上下留白（75px）比刘海（约 47px）大，
**属于「错误叠加出正确结果」**。一旦把画布改成满屏，刘海和手势条会立刻压住内容。

### P2-7 横屏没有处理

横屏时内容只占 31.8% 宽，中间一条细带。既没锁方向、也没有「请竖屏游玩」的提示。
微信小游戏可以 `"pageOrientation": "portrait"` 锁死；Web 端至少要提示。

### P2-8 其他零碎

- `user-scalable=no` 屏蔽了双指缩放（无障碍问题；iOS 10+ 其实会忽略它）。
- 没有 `theme-color`（安卓状态栏会是一条突兀的白/灰）。
- 没有 `apple-mobile-web-app-*`，加桌面后是全屏还是带地址栏不确定。
- `navigator.vibrate` 在 iOS Safari 不存在 → 震感在 iPhone 上是静默的。

## 4. 三条路线

### A. 保持等比，只补「收边」（改动最小，1 天）

- 留白区不再露 body 背景：把 `clayBackdrop` 扩到整块画布（在变换前先铺满），接缝消失；
- 顶部按钮从 60 抬到 88 设计高（CSS 45.8），字号 22→26；
- 误抬手指给 300ms 宽限或「续画」：松手不清路径，再按下接着走，只有超时才作废计入重来。

**收益**：丑的地方没了，误操作代价降下来。**代价**：上下仍各有 75px 白边，本质没变。

### B. 高度可伸缩（推荐，2~3 天）

固定宽度 750，**高度不再固定 1334**，而是按屏幕比例在 `1334~1560` 之间取值，
把多出来的高度分配给「棋盘上下留白」与「底部安全区」：

```
scale = w / 750
designH = clamp(h / scale, 1334, 1620)
```

- 16:9 机型仍是 1334（完全不回归）；
- 19.5:9 机型 designH≈1622，棋盘可多占 ~100px，格子在 11×11 上能到 32.5px；
- 因为棋盘是居中的，多出来的高度自动变成呼吸感，而不是一条接缝；
- 底部导航锚定在 `designH` 上，天然落到底边，手势条用 `env(safe-area-inset-bottom)` 兜住。

需要改的：`layout.ts` 里 `DESIGN_H` 从常量变成「运行时值」，
所有 `DESIGN_H - x` 的硬编码（nav、toast、结算面板）改成从布局对象取。

### C. 完全响应式（不做）

每屏独立排版、棋盘自适应。收益有限（核心是一张方块棋盘），
代价是把已经稳定的渲染与输入坐标体系全部重写。不建议。

---

## 5. 如果只做三件事

1. **P0-2 误抬手指**——松手不清零，超时（1.5s）才作废并计重来。
   这一条不改，手机上再好看也白搭。
2. **路线 B 的高度可伸缩**——一次把「接缝 / 白边 / 手势条」三个问题一起消掉。
3. **顶部小按钮抬到 88 设计高 + 读数 22→26 字**——两个数值，改完最直观。

## 7. 实施记录（2026-11-11 晚）

体检报告出来后先做了**不需要拍板的三件事**（手感 + 可达性 + 接缝），
路线 B 的「高度可伸缩」暂缓 —— 理由见 7.4。

### 7.1 P0-2 误抬手指 → 已修

`CoverSession` 引入 `paused` 阶段，把原来一步完成的三件事拆开：

| 时刻 | 旧行为 | 新行为 |
|---|---|---|
| 松手未通关 | `undos++`、清空路径、回 `idle` | 进 `paused`，**路径/钥匙/星屑全保留**，`undos` 不动 |
| 按回线头 | ——（已清空） | 恢复 `dragging`，接着拖 |
| 按别处 | —— | 立即作废（`undos++`）后从新格起步 |
| 超过 `GRACE_MS` | —— | `tick()` 到点才作废 |

- `GRACE_MS = 1500`。少于 800ms 来不及反应，多于 3s 玩家会以为卡住。
- 用**每帧比对时间戳**而不是 `setTimeout`：切后台时定时器被系统节流，
  回前台会「早该过期了却还要等下一次触发」。
- 宽限期内线画成 0.55 透明度 + 一条 toast（「松手了 · 1.5 秒内按回线上可继续拖」），
  表达「这段还在，但不算数」。
- `level_fail` 埋点从「松手」挪到 `expired` 事件 —— 否则每次宽限都误报一次失败。
- 旧的 `releaseCover` 保留（语义 = 判定 + 未通关立即作废），单测仍按它断言；
  会话层改用 `isCoverSolved` / `failCover` / `resumeCover`。

新增 `test/cover-grace.test.ts`（7 条）：路径保留、续接后仍是零重来、
按别处立刻作废、到期才作废、宽限内移动无副作用、宽限时长边界。

### 7.2 P1-3 按钮尺寸 → 已修

| | 旧 | 新 | 375 屏实际 | 390 屏实际 |
|---|---|---|---|---|
| 顶部按钮高 | 60 | **88** | 44 CSS px | 45.8 |
| 顶部按钮宽 | 90 | 96 / 104 | 48 / 52 | 50 / 54 |
| 提示（盘面下方） | —— | 176×88 | 88×44 | 91×45.8 |

顺带重排了「手会放哪」：

- **提示**是卡住时的高频动作 → 挪到盘面下方右侧（单手持机的拇指区）；
- **跳过**是看广告换通关、点错代价大 → 留在右上角，和「返回」隔着一整个关号胶囊。
  顶部原来三颗按钮间隙只有 12 设计像素（6 CSS），误触概率不低。
- 挑战模式隐藏「跳过」（比的是谁真能走完）。

### 7.3 P1-4 / P2-6 / P2-7 → 已修

- **字号**：关内读数 26/20 → 28/22；关号 34 → 36；盘面下小字 22 → 24；
  结算页「关卡进度」21 → 24、数据块 label 20 → 22。390 屏上最小正文从 11.4 → 12.5 CSS px。
- **接缝**：`clayBackdrop` 新增 `BackdropBox` 参数，由 `visibleDesignBox()`
  把「等比缩放留下的边」反算回设计坐标传给背景。
  原来背景只画 `0..1334`，390×844 上上下各 75px 的留白位于范围之外，
  渐变断在边界上 —— 这才是那道横缝的真正来源。现在一块渐变铺满整屏。
- **横屏**：短边 < 560 且宽>高时全屏提示「请竖屏游玩」。
  **用 CSS 像素画**（临时 `setTransform(dpr,0,0,dpr,0,0)`）——
  横屏时缩放只有 0.29，在设计坐标里写 46 号字落到屏上只有 13px，
  一条抱怨「屏幕不够用」的提示自己先看不清就滑稽了。只提示不拦截。
- **皮肤计数**从盘面上方挪到底部进度条右侧：它和大厅进度是同一类信息，
  挂在「还剩几格」旁边只是噪声。
- `BOARD_TOP` 200 → 216：顶部工具区加高后，读数（28 号字，中心 190）底部到 204，
  再不挪棋盘就顶上了。
- toast 从底部（`DESIGN_H − 320`）挪到 240 —— 底部那条带子被「盘面底缘 + 提示按钮」
  占着，toast 放哪都会压到其中一边。

### 7.4 路线 B 为什么没做

体检报告推荐的是「设计高度可伸缩（750 固定宽、1334~1620 可变）」。
实际量下来它的收益比预估小：

- 棋盘尺寸**受宽度限制**，不是高度。11 格最多 `(750−80)/11 ≈ 60` 设计像素，
  设计稿从 1334 拉到 1620 也不会让格子变大一个像素；
- 真正被解决的是「上下 75px 留白」。但那段留白恰好覆盖刘海（47px）和手势条（34px），
  **当安全区用是对的**。修完接缝后它读作「背景纸」，不再是缺陷；
- 代价是 5 个大厅页 + 地图的几十处硬编码 y 都要改成锚底，`NAV_TOP`、`VIEW_BOTTOM`
  这类模块级常量得改成函数。改动面比「棋盘变大」这点收益大得多。

结论：留白留着当安全区。等真机反馈「上/下空太多」再做不迟。

### 7.5 验证

```bash
npx tsc --noEmit && npx vitest run        # 239 用例
npx vite build                            # 393KB / gzip 80.7KB

# 进关 → 自动按参考解拖完 → 拍结算页
```

新增两个工具：

- `tools/autoplay.ts`：按关卡表里的参考解算出屏幕坐标串，喂给 `shot-cdp.mjs` 的 `DRAG`。
