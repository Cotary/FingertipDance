### 2.3 挖出并修掉 3 个真 bug

#### ① P0 · `/api/cover/challenge` **100% 报 500**

- **现象**：

  ```
  {"code":5000,"msg":"查询最佳成绩失败: ERROR: column \"undos\" does not exist (SQLSTATE 42703)"}
  ```

- **根因**：`scores` 表在 `001_init.sql` 里建出来时只有
  `(uid, level_idx, steps, time_ms)`。
  但 cover 的挑战要按 **undos**（重来次数）排序查历史最佳 ——
  **列根本不存在**，查询直接报错。
  上一轮加了 `002_cover_undos.sql`（给 `level_records` 加 `undos`）和
  `003_cover_mode.sql`（给 `level_records`/`skips` 加 `mode`），
  **唯独漏了 `scores`**。
- **修法**：
  - 新增迁移 `004_cover_scores.sql`：`scores` 加 `undos` + `mode` 两列，
    加 `(level_idx, mode)` 索引；
  - 所有写 `scores` 的地方（`progress.go` / `challenge.go` / `cover_handler.go`）
    改成带 `mode` 与 `undos`；
  - 两种模式的「查历史最佳」都加 `mode` 过滤。

#### ② P0 · `isNewBest` **恒为 false**

- **现象**：连着提交 `undos = 5 / 2 / 4` 三次，三次 `isNewBest` 全是 `false` ——
  而 `undos=2` 那次本该刷新纪录。
- **根因**：handler 里是「**先写流水，再查历史最佳**」。
  查的时候本次提交的这一行**也在**结果里，
  于是 `req.Undos < bestUndos` 永远为 false。
- **修法**：把「查历史最佳」挪到「写流水」**之前**；
  并区分「没有历史成绩」（`sql.ErrNoRows` → 本次就是首个纪录 → `isNewBest=true`）
  与「有历史但不如」。
  经典挑战 `/api/challenge` 有**完全相同**的 bug，一起修了。

#### ③ P0 · 「历史最佳」查的是**全服**最佳，不是自己的

- **现象**：修完 ② 之后，用**同一个账号**测是好的；
  但换一个新账号测第一关，`isNewBest` 又是 `false`。
- **根因**：查 `scores` 时**没有按 `uid` 过滤** ——
  查出来的是这一关**全服**最好的成绩。
  第一个玩家清了这关之后，后面所有人都是 `false`，
  「刷新纪录」这个功能对所有人**永久失效**。
- **修法**：查询加 `uid=$1` 条件。

### 2.4 顺带修的客户端问题：挑战根本没跟好友比

- **现象**：分享链接里带了好友的成绩（`undos=N`），
  但结算页的「最佳 N 次」用的是**服务端返回的 best**（= 自己这关的历史最佳），
  好友的成绩 `challenge.fromUndos` **解析了但从没用过**。
  结果：好友来 2 次、我来 5 次，判我「惜败」——
  但好友根本没参与比较，这个「挑战」是假的。
- **另有一个更隐蔽的问题**：`fromUndos` 用 `0` 当「不知道」的哨兵。
  但 **0 次重来是最好的成绩（三星）**——
  好友 0 次的成绩会被当成缺失，输赢**判反**。
- **修法**：
  - `Challenge.fromUndos` 改成 `number | null`，`null` 才表示「不知道」；
  - 结算页优先跟好友比（`fromUndos !== null`），没有才退回自己的历史最佳；
  - `buildShareQuery` 补上 `uid` / `name`（之前只带关号和分数，
    好友打开链接看到的是「好友的挑战」，没有名字也没有 uid）；
  - `Progress` 加 `uid` 字段并从登录响应写入。

## 三、关键决策与取舍

### 3.1 决策：迁移写成**新增** `004`，不改 `003`

- **否决的方案 A**：直接往 `003_cover_mode.sql` 里加 `scores` 的语句。
  - 否决理由：`003` 已经在测试库上跑过了。改已发布的迁移文件意味着
    「同一个迁移文件在不同环境下产生不同结果」——
    老环境重跑 `003` 会执行新语句，新环境从头跑也会。
    虽然本项目 `migrate.go` 是「每次启动重跑全部迁移」（靠 `IF NOT EXISTS` 保证幂等），
    但依赖这个副作用去改历史迁移是**埋雷**。
- **采纳**：新增 `004_cover_scores.sql`。

### 3.2 决策：契约测试用**读源码文本**的方式锁，而不是连库

- 理由：本仓库的 Go 测试**没有连数据库**（`internal/core` 只有 `DB` 类型，
  没有测试夹具）。新写一套 DB 夹具的成本远超收益。
- 但「读源码文本」这种测试很脆 —— 重构时容易误伤。
  折中：只锁**三条跨文件的不变量**（列清单带 `mode`/`undos`、
  查询带 `mode`/`uid` 过滤、查历史在写流水之前），
  每条都写清楚「为什么」，并在注释里承认这种测试的局限。

### 3.3 决策：客户端挑战的「对手」是**分享链接里的好友**，不是全服最佳

- **否决的方案**：让服务端返回「这一关全服最好的成绩」，客户端跟它比。
  - 否决理由：那不是「挑战好友」，是「挑战榜一」。
    分享的语义是「我卡在这关 / 我用 N 次重来，你来试试」，
    对手必须是**分享链接里的那个人**。
- **代价**：链接丢了分数（老版本分享的链接只有 `l=N`）就没法比 ——
  这种情况退回「跟自己的历史最佳比」，并在文案上说清楚。

### 3.4 决策：老链接不带分数时**不猜**

- `parseChallenge` 读到老链接（没有 `undos`）→ `fromUndos = null`，
  **不做** `steps → undos` 的换算。
- 理由：cover 的步数恒为 `required − 1`，跟重来次数**没有数学关系**，
  硬换算出来的数字是编的。显示「最佳 0 次」只是信息缺失，
  显示「最佳 3 次」却是**假信息**。

## 七、换端口 + 进程为什么会「凭空消失」

### 7.1 用户说的「后端不通」其实不是端口问题

排查发现 `netstat` 上 8080/5173/5174 **全空**，Docker Desktop 守护进程也停了。

根因是**进程生命周期**，不是端口冲突：

- 上一轮的后端（`go run`）和前端（`vite`）都挂在 Cursor 的**终端会话**里，
  会话一结束进程就被回收 → 隔夜再打开，后端自然连不上。
- Docker Desktop 守护进程同理，停了之后 Postgres/Redis 容器一起消失。

**教训**：本地开发的服务不能用「终端里直接跑」的方式启动，必须脱离会话。

### 7.2 端口分配

| 服务 | 端口 | 说明 |
|---|---|---|
| 后端（Go） | **50001** | 用户指定 |
| 前端（Vite） | **50002** | 不能和后端同端口 |

改动的配置文件：

- `server/deploy/config.local.yaml` — `port/addr` → 50001
- `server/internal/core/config.go` — 新增 `SERVER_ADDR` 环境变量覆盖
- `games/line/vite.config.ts` — 端口 50002 + `strictPort: true` + `__API_BASE__` → 50001
- `games/line/vitest.config.ts` / `tools/preload.ts` — 同步 `__API_BASE__`

**为什么加 `strictPort: true`**：

Vite 默认遇到端口被占会**静默顺延**到下一个可用端口。上一轮就踩过 ——
用户打开 5173，看到的其实是**另一个项目**（WorkBuddy 的「数字消消乐」），
因为那个项目的 supervisor 会反复把 5173 拉起来，把我们挤走了。

`strictPort` 让它端口被占时**直接报错**，而不是偷偷换端口连到来路不明的服务。

### 7.3 新增一键启动脚本

`games/line/scripts/start-dev.ps1`：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\start-dev.ps1          # 启动
powershell -ExecutionPolicy Bypass -File scripts\start-dev.ps1 -Stop    # 停止
```

做三件事：拉起 Docker → 起后端并等 `/healthz` 通过 → 起前端。

**踩的两个坑**（都写进脚本注释了）：

1. **PowerShell 5.1 按 ANSI 读 UTF-8 文件**，中文注释全乱 → 解析报错。
   解决：文件存成 **UTF-8 with BOM**，并在脚本里设 `[Console]::OutputEncoding = UTF8`。
2. **仓库根目录定位**：一开始假设根在 `games/line` 上一级，
   结果 `go build` 在错的目录跑，报 `cannot find main module`。
   解决：改成从脚本目录**向上找**同时含 `server/go.mod` 和 `games/line` 的那一层。

### 7.4 依赖容器

不新建容器 —— 复用已有的 `mcp-test-pg`（15432）和 `fgame-redis`（6379），
它们随 Docker Desktop 自动启动且带 restart policy。

## 八、P0 · 点击位置和鼠标对不上（125px）

### 8.1 现象

用户报「鼠标和点击位置对不上」。不是完全点不动，而是**恒定偏移**，
所以看起来像「感觉不准」。

### 8.2 根因：渲染和输入用了两套不同的坐标变换

**渲染端**（`main.ts` 的 `frame()`）：

```ts
ctx.setTransform(1, 0, 0, 1, 0, 0);
ctx.scale(dpr * scale, dpr * scale);
ctx.translate(offsetX / dpr, offsetY / dpr);   // ← 这里
```

Canvas 的 `scale`/`translate` 是**右乘**的 ——
`scale(a) ∘ translate(t)` 等价于 `x' = a*(x + t)`，
所以平移量被平白乘了一个 `a`。实际偏移变成 `offsetX * scale`，
而正确值是 `offsetX * dpr`。

**输入端**（`toDesign`）算的是「设计坐标」，配合 `pick()` 用
`originX/originY/cell` 定位格子 —— 这套**本身是对的**。

所以错的是**渲染端**：格子画在了 A 处，命中判定按 B 处找。

### 8.3 实测数据（1920×1080）

`scale = 0.8096`、`offsetX = 656.4` → 横向偏 `offsetX × (1 − scale)` ≈ **125px**，
约等于一整格（格宽 134 设计px ≈ 108 屏幕px）。

| | 棋盘 X 范围（CSS px） |
|---|---|
| 实际渲染在哪 | `[564, 1106]`（像素实测 `[560, 1110]`）|
| 点击判定认为在哪 | `[689, 1231]` ❌ |

**为什么之前没发现**：设计上偏 125px ≈ 1.2 格，**横向**偏 1.2 格、纵向偏 0.9 格，
而真人拖拽路径本来就是斜的，肉眼很难察觉。

### 8.4 修法：抽出 `render/viewport.ts`，两端共用一个视口对象

新模块 `games/line/src/render/viewport.ts` 提供：

- `toCss(x, y)` — 设计 → 屏幕
- `toDesign(cssX, cssY)` — 屏幕 → 设计
- `toDevice(x, y)` — 设计 → 设备像素
- `applyTo(ctx)` — 把变换写进 2D 上下文

渲染端改成一行：

```ts
viewport.applyTo(ctx);
// 等价于 ctx.setTransform(dpr*scale, 0, 0, dpr*scale, offsetX*dpr, offsetY*dpr);
```

**为什么用 `setTransform` 而不是 `scale`+`translate`**：
变换右乘的顺序太容易写错（本 bug 就是这么来的）。`setTransform` 一次写死，
没有中间步骤可错。

输入端 `toDesign` 也顺带简化 —— 原来绕一圈
（`canvas.width/rect.width` → 设备像素 → `/dpr` → CSS 像素），
现在直接用 `rect.width`（CSS 像素）一次换算。

### 8.5 回归测试（新增 `test/viewport.test.ts`，7 个用例）

锁死三条不变量：

1. `toDesign` 与 `toCss` 严格互逆；
2. `toDevice` 与 `applyTo` 的变换严格互逆（含矩阵求逆验证）；
3. **渲染变换的平移量是 `offset * dpr`，不是 `offset * scale`** ——
   这正是本 bug 的核心断言。

外加一条端到端断言：「桌面 16:9 下渲染位置与命中位置一致（回归：曾偏 125px）」。

## 九、P0 · 埋点上报打不到后端

### 9.1 `/api/report` 是什么

**埋点批量上报接口**，不是玩法接口：

- **客户端** `src/analytics/tracker.ts`：所有 `reportEvent(...)` 先进
  `localStorage.event_buffer` 缓冲，攒够 20 条或切后台时批量 POST。
- **服务端** `internal/core/analytics.go`：每条事件
  `INSERT INTO events (uid, name, params, ts)`，params 存 JSONB。

网络面板里看到一串 `/api/report` 是**正常的后台行为**，看不到反而说明埋点没发出去。

### 9.2 Bug ①：用了相对路径

```ts
// 修复前
await platform.request('/api/report', 'POST', { events: batch }, ...);
```

相对路径会打到**前端 dev server**（Vite）而不是后端 → 404。

更糟的情况实测到了：浏览器里 `location.origin` 是 `https://3.jetbra.in`
（页面挂在某个反向代理后面），相对路径直接解析到**别人的域名**上。

**修法**：改用 `__API_BASE__`（构建期注入的后端地址），和 `net/api.ts` 保持一致。

### 9.3 Bug ②：接口强制鉴权，登录前的事件永远 401

客户端在 `login()` **之前**就开始埋点（`app_start` 是启动第一个事件），
那时还没有 token。而 `/api/report` 挂在 `auth` 分组（强制 Bearer）下 →
那批事件永远 401 → `web.ts` 的 `request()` 抛异常 → `tracker` 的 catch 吞掉 →
**事件永久卡在本地缓冲里**。

现象：`localStorage.event_buffer` 一直增长（实测堆到 12 条）。

**修法**：

- 新增 `core.OptionalAuthMiddleware` —— 有 token 就用 token 里的 uid，
  没有就记 uid=0（匿名），**不拒绝**请求。
- `/api/report` 单独挂它，不再放在 `auth` 分组。
- 客户端在 `login()` 成功后主动 `tracker.flush()` ——
  这样 `app_start` 那批能带上 uid（比等攒满 20 条更好）。

### 9.4 Bug ③：缓冲无上限

后端长期不可达时，缓冲会无限增长直到撑爆 localStorage
（localStorage 写满会让整个存储不可用）。

**修法**：`flush()` 的 catch 分支里，缓冲超上限时丢弃最旧的。

### 9.5 回归测试

- **TS** `test/tracker.test.ts`（6 个用例）：断言 URL 是绝对的后端地址、
  有/无 token 的两种 header、上报成功清空缓冲、失败保留、缓冲有上限。
- **Go** `internal/core/report_auth_test.go`（2 个用例）：
  断言 `/report` 路由挂了 `OptionalAuthMiddleware`、且**不在** `auth` 分组里；
  断言该中间件不含 `Abort()`。

## 十三、Bug ① · 服务端漏返 `unlockedSkins`，渲染循环直接死掉

### 13.1 现象

通关后画面**卡在结算动画**，「下一关」按钮点了毫无反应。
而且**没有任何网络错误**、没有任何报错提示 —— 像是按钮坏了。

### 13.2 定位过程

一开始怀疑是坐标变换（上一轮刚修过同类问题），但用 CDP 派发指针事件
点击「下一关」的设计坐标 `[375, 793]` —— **命中判定是对的**，
`pressedBtn` 也被设成了 `'next'`。

真正的线索是抓到的运行时异常：

```
Uncaught TypeError: Cannot read properties of undefined (reading 'length')
```

行号是**编译后**的 740。拉取 Vite 变换后的 `/src/main.ts` 对照，
定位到源码这一行：

```ts
drawHud(
  ctx, level.idx, progress.current.currentSkin,
  progress.current.unlockedSkins.length,   // ← 这里
  ...
);
```

`progress.current.unlockedSkins` 变成了 `undefined`。

### 13.3 根因：三层叠加

**第一层 · 服务端漏字段**

cover 模式的成绩接口 `/api/cover/progress` 返回的结构体是：

```go
type coverProgressResult struct {
    Passed       bool              `json:"passed"`
    IsNewBest    bool              `json:"isNewBest"`
    MaxLevel     int               `json:"maxLevel"`
    TotalTimeMs  int64             `json:"totalTimeMs"`
    TotalSteps   int               `json:"totalSteps"`
    UnlockedSkin *unlockedSkinInfo `json:"unlockedSkin"`
    Stars        int               `json:"stars"`
    // ← 没有 UnlockedSkins！
}
```

而经典模式的 `progressResult` **有** `UnlockedSkins` 字段。
客户端 `ProgressResult` 类型也声明了 `unlockedSkins: string[]`（非可选），
于是 TypeScript 编译通过、运行时拿到 `undefined` —— **类型系统没拦住**。

**第二层 · 客户端 `sync` 是整体覆盖语义**

```ts
sync(p: Partial<Progress>): void {
  this.progress = { ...this.progress, ...p };   // ← undefined 会覆盖掉旧值
}
```

调用方写的是 `progress.sync({ maxLevel: res.maxLevel, unlockedSkins: res.unlockedSkins })`。
`res.unlockedSkins` 是 `undefined` → 本地皮肤数组被**覆盖成 `undefined`**。

**第三层 · 一帧异常 = 渲染循环永久中断**（这才是最致命的）

```ts
function frame() {
  ...
  requestAnimationFrame(frame);   // ← 在函数末尾
}
```

`requestAnimationFrame` 在**函数末尾**调用，所以 `frame` 一旦抛异常，
这一行**永远执行不到** —— 渲染循环就此中断，画面停在最后一帧。
之后点任何按钮都没反应，因为根本没有事件处理在跑。

### 13.4 修法（三层都补）

1. **服务端**：`coverProgressResult` 补 `UnlockedSkins []string`，
   并把 `unlockedJSON` 反序列化成 `skinList`（`nil` 时兜成 `[]string{}`，
   避免 JSON 里出现 `null`）。
2. **客户端 `sync`**：**忽略 `undefined` 字段**。
   `undefined` = 「服务端没给这个字段」，保持本地旧值不动；
   显式传 `[]` 仍然合法（表示服务端确实说没有皮肤）。
3. **渲染循环兜异常**：把渲染主体拆成 `renderFrame(now, dt)`，
   `frame()` 里 `try/catch` 包住，异常打日志但**循环继续**。
   这样一帧出错不会让整个游戏变成砖 —— 甚至能自愈。

### 13.5 回归测试

**Go**（`cover_contract_test.go` 加 1 个用例）：
断言 `coverProgressResult` 序列化后**必须**有 `unlockedSkins` 字段且不为 `null`。

**TS**（`test/progress-sync.test.ts`，5 个用例，新增）：
- 缺字段不会覆盖已有值
- 缺字段后 `.length` 不抛
- 正常覆盖仍生效
- 显式空数组合法
- `currentLevel = maxLevel + 1`

## 十四、Bug ② · `maxLevel` 语义错位（差一格）

### 14.1 现象

修完 Bug ①，「下一关」能进第 2 关了。但玩家视角仍是「通关了还在原地」：

- 大厅主按钮写「**继续 第 1 关**」（应该是「第 2 关」）
- 地图上第 1 关是「当前关」，**第 2 关是锁着的**
- 地图吸底按钮写「继续第 1 关」
- 新用户一进来 `maxLevel` 是 1 而不是 0 —— **新玩家被跳过了第 1 关**

### 14.2 根因：服务端与客户端对同一个字段的理解差 1

| 端 | `maxLevel` 的语义 | 依据 |
|---|---|---|
| **服务端** | 最高**已通关**关号（`0` = 一关都没通） | `docs/连连看/17-数据模型.md`：「`max_level` \| 最高通关关卡」 |
| **客户端** | **下一个可玩**关号 | 地图三态判定 `locked = idx > maxLevel`、`current = idx === maxLevel` |

服务端 `UPDATE users SET max_level = GREATEST(max_level, $1)` 传的是 `lv.Idx`
（第几关通关就写几）。所以通关第 1 关后 `max_level = 1`。

而客户端拿 `maxLevel = 1` 当「当前关」→ 画成「第 1 关是当前、第 2 关锁着」。
**整体错一格。**

### 14.3 修法：把两种语义**显式分开**

不改成服务端存「下一个可玩关」（那会让排行榜和「最高关卡」统计全错，
而且要动历史数据），而是**客户端引入派生值**：

- `Progress.maxLevel` —— 保持与服务端一致 = **最高已通关关号**
  （排行榜、「最高关卡」统计卡、进度条百分比继续用它）
- `ProgressStore.currentLevel` —— 新增派生 getter = `maxLevel + 1`
  = **下一个可玩关**（大厅按钮、地图三态、地图吸底按钮、解锁判断用它）

配套改动：

- `MapViewState.maxLevel` → 重命名为 **`currentLevel`**，
  语义从「已通关最高关」改成「下一个可玩关」，三态判定同步调整：
  `done = idx < currentLevel`、`current = idx === currentLevel`、
  `locked = idx > currentLevel`。
- `HomePageState` 加 `currentLevel` 字段（不从 `maxLevel` 现场 +1，
  避免每个渲染点各自理解错）。
- `ProgressStore` 初始值 `maxLevel: 1` → **`0`**。
- 登录时 `maxLevel: loginRes.maxLevel || 1` → **`loginRes.maxLevel`**
  （`|| 1` 会把新用户的 0 变成 1，直接跳过第 1 关）。

### 14.4 顺手发现的一处 UI 隐患

地图吸底「继续」按钮的 y 位置我一开始按 `DESIGN_H - 120` 算，
结果点到的是**底部导航栏的「皮肤」Tab** —— 因为
`VIEW_BOTTOM = DESIGN_H - 196`（底部导航 120 + 按钮 62 + 间距），
按钮实际在 `y = 1144`。**布局没问题，是我算错了** ——
但这说明「地图吸底按钮」和「底部导航」在垂直方向只隔 76px，
点错了不会报错、只会静默切页。以后调这块要注意。
