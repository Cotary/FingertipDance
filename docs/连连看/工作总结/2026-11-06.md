### 2.2 巡检发现的 6 个 bug（全部已修）

#### ① P0 · 服务端 cover 关卡表**永远拉不下来**

- **现象**：客户端 `CoverLevelStore.init()` 一次性请求 `count=1000`，
  而服务端 `/api/levels-v3` 的 `count` 上限是 100 → 请求被 400 拒掉。
- **后果**：**服务端改了关卡，客户端永远看不到**，一直用内置表。
  上一轮刚做的「服务端 embed + `/api/levels-v3`」其实**完全没生效过**。
- **根因**：两端的分页参数没有对齐，且**失败是静默的**（catch 里只 `console.warn`）。
- **修法**：
  - 客户端先只拉 1 关**探版本号**（`fetchCoverTableVersion`），
    与内置表版本一致就**完全跳过下载**（省 300 KB 流量）；
    不一致才按 `count=100` 分批拉全量。
  - 任何一批失败就整体放弃 —— 半张表比内置表更危险（关号断层）。

#### ② P0 · `level_records` 没有模式维度，经典与 cover 记录互相覆写

- **现象**：服务端 `level_records` 主键是 `(uid, level_idx)`，
  而经典模式与 cover 模式**共用同一套关号空间**（都是 1..1000）。
- **后果**：
  - 玩家先玩经典第 5 关再玩 cover 第 5 关 → **同一行**，互相覆盖；
  - 更糟的是 `/api/progress/stars` 按 `steps / shortest` 算星级，
    cover 的 `shortest` 恒为 `required − 1` → cover 星级**全错**。
- **修法**：
  - 新增迁移 `003_cover_mode.sql`：`level_records` 加 `mode` 列（0=经典 / 1=cover），
    主键改成 `(uid, mode, level_idx)`；
  - `skips` 表同理加 `mode`（跳过次数也不该两种模式互相吃）；
  - 两端所有读写都带上 `mode`；
  - `/api/progress/stars` 加 `mode` 查询参数（`classic` / `cover`），
    因为两种模式关号重叠，混在一起返回客户端没法区分。

#### ③ P0 · cover 模式「跳过」按钮整条链路是坏的

- **现象**：`CoverProgressHandler` 直接拒绝 `skipped=true`（「cover 模式不支持跳过」），
  而客户端跳过时上报的是空路径 → **必然被拒**。
- **后果**：cover 模式下玩家卡在一关上**没有任何退路** —— 不能跳过、不能重开、
  提示也救不回来（走岔了剩余盘面无解时）。
- **修法**：新增 `/api/cover/skip`（`cover_skip.go`）：
  - 用 cover 表的 `required − 1` 写步数（不是经典表的 `shortest`）；
  - 推进最高关卡（否则卡死），但**不发皮肤、也不给星**。

#### ④ P0 · cover 模式挑战提交**必然失败**

- **现象**：客户端挑战走 `/api/challenge`，服务端用经典校验器 `ValidatePath`
  （起终点连线 + 单向块）。cover 的路径用它校验**长度都对不上**。
- **修法**：新增 `/api/cover/challenge`（`CoverChallengeHandler`），
  用 `ValidateCoverPath`；比较维度从「步数」改成**重来次数**。

#### ⑤ P1 · cover 模式**永远拿不到** premium 皮肤

- **现象**：服务端发皮肤靠读关卡表的 `unlockSkin` 字段，
  而 cover 关卡表**根本没有这个字段**（经典表有）。
- **后果**：黄金 / 星尘 / 星河三款 premium 皮肤在 cover 模式下**无法获得** ——
  而 cover 是现行玩法，等于这游戏没有任何可追求的目标。
- **修法**：
  - 关卡表加 `unlockSkin` 字段，生成工具写入（200→gold / 500→stardust / 900→galaxy，
    与经典模式的 `skinForLevel` 一致）；
  - 发皮肤的逻辑抽成**共享函数** `grantSkinForLevel` —— 之前 cover 模式
    是抄了一份逻辑但漏了字段，两份实现必然漂移。

#### ⑥ P2 · `/api/config` 报的是经典表的版本号与关数

- **现象**：`ConfigHandler` 只回 `levelVersion` / `levelCount`（经典表）。
- **后果**：客户端拿经典表版本去判断 cover 表要不要重拉 → **改了 cover 表客户端以为没变**。
- **修法**：新增 `coverLevelVersion` / `coverLevelCount` 字段；
  客户端 `boot()` 改用 cover 版本号；总关数统一走 `totalLevelCount()`。

## 三、关键决策与取舍

### 3.1 决策：`level_records` 加 `mode` 列，而不是加 `level_idx` 偏移

**否决的方案 A**：cover 的关号在数据库里加偏移（比如 +10000），避开与经典模式撞主键。
- 否决理由：关号偏移会让所有 SQL 都得记住「这个表里的 idx 要减 10000」，
  迟早有一处忘了。而且客户端上报的是真实关号，服务端还得来回换算，
  出错的地方比现在多。

**否决的方案 B**：经典模式与 cover 模式**彻底分表**（`level_records` / `cover_level_records`）。
- 否决理由：星级、好友榜、总步数统计都要同时查两张表，
  「玩家总步数」这种聚合查询会写两遍 SQL，逻辑分叉。
  而 `mode` 列已经能表达全部语义。

**采纳**：加 `mode` 列，主键 `(uid, mode, level_idx)`。
- 代价：多一次迁移（`003_cover_mode.sql`），需要重建主键约束。
- 收益：两种模式彻底隔离，但统计查询仍然是同一张表。

### 3.2 决策：cover 的「跳过」允许推进进度但**不给星、不发皮肤**

**否决的方案 C**：跳过也给星（和普通通关同等对待）。
- 否决理由：跳过是**花钱买过去的**，不是**打过去的**。
  给星会让「看广告跳过」变成刷星的最优解 —— 三星就白拿了，
  整个星级体系就废了。

**否决的方案 D**：cover 模式干脆不支持跳过（回到原来的行为）。
- 否决理由：玩家卡在一关上时**没有任何退路**是更严重的问题。
  卡关可能是因为盘面难、可能是因为玩家走岔了找不到出路，
  无论如何都得给一条「花钱买路」的出路。

**采纳**：允许跳过 → 推进最高关卡（否则卡死）→ 不发皮肤、不给星。

### 3.3 决策：挑战的比较维度改成「重来次数」

- 理由与星级口径**统一**：cover 模式步数恒为 `required − 1`，
  比步数等于所有人平手。既然星级已经按悔棋次数算，
  挑战也该用同一个维度 —— 否则「三星通关」和「挑战胜利」两套标准会打架。

### 3.4 决策：提示功能保持「实时求解」而不是查表

这一条**不是本轮改动**，但巡检时确认过现状是对的，记录在此避免以后被「优化」掉：

- 设计文档 §5.1 提过「参考解入库 → 提示 O(1) 查表」，但那只在玩家**严格沿着参考解走**时成立。
- 玩家走岔（走了另一条同样合法的哈密顿路径）后参考解就接不回去了，
  强行回退会让玩家的线突然倒退。
- 现状是实时求解剩余盘面（`coverHint.ts`），实测 11×11 盘只要几毫秒。

## 五、遗留问题与下一步

### 5.1 必须做（上线前）

1. **在有 PostgreSQL 的环境跑迁移 `003` 并验证**
   - 重点验证：主键重建在有数据的老库上不会失败；
     `DROP CONSTRAINT IF EXISTS level_records_pkey` 的约束名在 PG 上确实是这个。
   - 验证完再跑一遍端到端 curl：登录 → 拉 cover 关卡 → 通关上报 → 拉星级 → 跳过 → 挑战。

2. **`/api/progress/stars` 加了 `mode` 参数，老客户端会受影响吗？**
   - 现在 `mode` 默认值是 `classic`，老客户端不带参数 → 拿到的还是经典星级 → 行为不变。
   - 但**客户端已经切成拉 cover 模式**了 → 老服务端没有 `cover` 分支会返回 `mode 参数需为 classic 或 cover`。
   - → **服务端必须先于客户端上线**。目前两端在同一批改动里，部署顺序要注意。

3. **分享链接的 query 从 `steps` 改成了 `undos`**
   - 已经发出去的旧链接带 `steps=`，新代码解析不出来 → `fromUndos = 0`。
   - 影响很小（只是对方看不到你的重来次数），但**分享出去的老链接会显示「最佳 0 次」**。
   - 建议：`parseChallenge` 兼容读 `steps`（转成 undos 的近似值不靠谱，直接忽略即可）。

### 5.2 建议做（体验）

4. **premium 皮肤只有 3 个 milestone 点，cover 模式下玩家要打到第 900 关**
   - 中间（200→500、500→900）跨度很大，中间没有任何追求目标。
   - 可以考虑在 cover 模式下增加「每 50 关一个小奖励」之类的东西。

5. **关卡表体积**：客户端内置表 311 KB（gzip 后 77 KB 总 bundle）。
   - 微信小游戏首包限制 4 MB，暂时没问题；
   - 但如果以后关卡数翻倍，需要考虑分包或压缩 grid 编码。

### 5.3 明确不做（记录理由，避免以后重复讨论）

- **不做「两套关卡表合并」**：数据结构与规则完全不同，合并会让客户端每关都要判断走哪套逻辑。
- **不做「cover 模式提示改成查表」**：见 §3.4，走岔后查表反而更差。
- **不做「跳过也给星」**：见 §3.2。
